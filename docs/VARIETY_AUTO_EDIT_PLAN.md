# 長尺バラエティ全自動編集 計画書

- 作成日: 2026-10-02
- 状態: 2026-10-02 利用者が承認。§10 の判断事項はすべて確定。フェーズ0を対話セッションで実装中
- 対象: 本リポジトリ(Electron + React + TypeScript の動画編集アプリ)
- 前提とする方針: **本アプリ単体で、取り込みから完成品の書き出しまでを完結させる**(Premiere 等の外部ソフトでの仕上げは前提にしない)
- 主な実行環境: **Windows 10 / 11(64bit)**(2026-10-02 利用者が決定)。macOS は副対象とし、動作は維持するが性能目標は Windows で測る
- 基準機(性能目標を測る機材): Windows 11 / CPU 8コア以上 / **NVIDIA GeForce RTX 5090(VRAM 32GB)**/ **メモリ 約64GB**(2026-10-02 利用者が決定。メモリは利用者の記憶による概数のため、導入時に実機で確認する)
- メモリの使い方: 基準機では、書き出しのセグメント並列・カメラごとの解析の並列・プレビュー用のフレームキャッシュに合計 40GB までを使い、残りを OS と他のアプリに残す。並列数とキャッシュの量は起動時に実メモリ量から自動で決め、少ない PC では自動で絞る
- 最低動作環境: NVIDIA GeForce RTX 3060 相当(VRAM 8GB)以上。最低動作環境では「動くこと」までを保証し、性能目標は基準機で測る
- RTX 5090(Blackwell 世代)の注意: **CUDA 12.8 以降でビルドされたバイナリでないと GPU が使えない**。同梱する whisper.cpp・ONNX Runtime 等は、Blackwell 対応版であることを導入時に確認する(古い版は黙って CPU で動き、極端に遅くなる)
- GPU の前提: 重い処理(音声認識・話者埋め込み・顔検出・音声イベント検出・デコード・エンコード)は **CUDA / NVDEC / NVENC を第一の経路**として設計・最適化する。他社 GPU と GPU 無しの環境は「動くこと」までを保証し、性能目標の対象外とする

## 1. 目的

屋外ロケ型の長尺バラエティ(複数カメラ・ピンマイク・大量の発言テロップ・効果音・版面CG)を、
**収録素材一式を渡すだけで、放送/配信に耐える完成品まで自動で編集する**。

### 1.1 到達目標(定量)

| 指標 | MVP(フェーズ3完了時) | 最終目標(フェーズ5完了時) |
|---|---|---|
| 入力 | カメラ2〜4台 + ピンマイク2〜4本、収録計2〜6時間 | カメラ6台 + ピンマイク8本、収録計10時間 |
| 出力 | 16:9 / 1080p / 20〜60分の完成品 | 4K 出力にも対応 |
| 人手の修正時間(60分の完成品1本あたり) | 4時間以内 | 1時間以内 |
| 採用区間の一致度(人の完成版との比較、§7) | IoU 0.5 以上 | IoU 0.7 以上 |
| 発言テロップの文字誤り率(CER、整文前) | 10% 以下 | 5% 以下 |
| 話者の取り違え率(テロップ単位) | 5% 以下 | 2% 以下 |
| 全自動処理時間(収録4時間 → 60分の完成品) | 4時間以内(基準機) | 1時間以内 |

> 人手を一切介さず、テレビのバラエティ番組の水準を100%再現することは目標にしない。
> **「自動で8割まで仕上げ、人は確認と細部の修正だけをする」**状態を製品の完成形と定義する。
> そのため、自動処理の各工程が「自信の低い箇所」を必ず報告し、そこから人が直せることを要件に含める(§5.13)。

## 3. 現状の構成と、長尺バラエティに対する限界

現状はYouTubeショートの編集を前提に作られており、そのままでは目標に届かない。
**最大の制約はデータモデルと書き出しエンジン**で、ここを先に作り替えないと後続のどの機能も載らない。

| 領域 | 現状(該当箇所) | 長尺バラエティでの限界 |
|---|---|---|
| データモデル | `Project.clips[]` が1本の本編トラック(前から順に詰める方式)。PiP は4隅固定・倍率のみ(`src/shared/types.ts`) | 任意の位置・大きさ・不透明度のレイヤー合成、19層の重ね、キーフレームが表現できない |
| 書き出し | 1回の ffmpeg 実行で、**クリップ1本ごとに入力(`-i`)を1つ追加**し、1つの巨大なフィルタグラフで連結する(`src/main/ffmpegService.ts` 722行・927行・1049行) | 数千クリップでは入力数・メモリ・グラフの規模が破綻する。途中で失敗すると全部やり直しになる |
| テロップ描画 | ASS 字幕を libass で焼き込む(`src/main/assSubtitle.ts`、`subtitles=` フィルタ) | 多重縁取り・グラデーション・画像の組み込みなど、バラエティの定番装飾が出せない。画面表示(DOM)と書き出し(libass)で描画系が違い、ずれの温床になる |
| プレビュー | レイヤーごとに `<video>` 要素を重ねる(`PreviewPlayer.tsx`) | 同時に10本を超える映像は、デコード負荷とシークの同期が成り立たない |
| 音声認識 | `Xenova/whisper-base`(transformers.js、CPU)(`src/main/whisperService.ts`) | 風切り音・掛け合いの多いロケ音声では精度が不足する。数時間の素材では遅すぎる |
| 話者 | 概念が無い | 話者別テロップ・アングル切替の前提が欠けている |
| 画面比 | `'16:9' \| '9:16'` | 16:9 は既にあるので流用できる |
| タイムライン UI | クリップ1本ごとに DOM を描く(`Timeline.tsx`) | 数千クリップ × 27トラックでの操作性能は未検証 |

一方、**そのまま使える資産も多い**: 無音・フィラーの検出、ラウドネス正規化(2パス)、ダッキング、BPM解析、
キーワード連動SE、ハイライト検出(音声のみで長尺を速く絞る `longFormService.ts`)、プロキシ生成、
自動保存とクラッシュ復旧、テスト基盤(vitest 302件)、Gemini 連携。

## 4. 目標アーキテクチャ

### 4.1 全体像

```
[収録素材フォルダ]
      │
      ▼
① 取り込み・整理 ─ ② 同期 ─ ③ 文字起こし ─ ④ 話者分離
      │                                          │
      ▼                                          ▼
 解析ストア(素材ごとの解析結果をキャッシュ。工程ごとにやり直し可能)
      │
      ▼
⑤ 構成(LLM) ─ ⑥ カット ─ ⑦ アングル切替 ─ ⑧ テロップ ─ ⑨ SE・CG・BGM ─ ⑩ 音声仕上げ ─ ⑪ 色合わせ
      │
      ▼
 シーケンス(データモデル v2) ←→ 編集UI(人による確認・修正)
      │
      ▼
⑫ セグメント分割レンダラ ─ ⑬ 自動QC ─ [完成品]
```

設計原則:

1. **工程の分離と再実行**: 各工程は「入力 → 解析ストアへの出力」として独立させ、上流を直したら下流だけを再計算する。
   人が直した箇所には印を付け、再計算で上書きしない。
2. **画面と書き出しで同じ描画系**: テロップ・CGの描画は1つのレンダラ(§4.4)を画面表示と書き出しの両方で使う。
   これまでのバグの多く(BACKLOG の再発防止チェックリスト参照)は、画面と書き出しで描画系が違うことから生じている。
3. **ローカル処理を優先**: 音声認識・話者分離・顔検出はローカルで実行する。クラウドLLMに送るのは文字起こしと
   縮小した代表フレームだけに限り、送信の有無を設定で止められるようにする(未公開素材の扱い、§9)。
4. **Windows 前提の実装上の注意**: パスの長さ(260文字制限)と日本語・全角を含むパスを ffmpeg・ネイティブモジュールへ安全に渡す。
   ONNX のモデルは ONNX Runtime(CUDA / DirectML)で動かし、GPU が無い環境では CPU にフォールバックする。
   ネイティブのバイナリ(whisper.cpp 等)はインストーラに同梱し、利用者に別途のインストールを求めない(ffmpeg と同じ方針)。

### 4.2 データモデル v2

`Project` にバージョン番号を持たせ、v1(現行)からの移行関数を用意する。現行の Shorts 向け機能は v2 の上で動かす。

```ts
interface ProjectV2 {
  version: 2
  sequence: Sequence
  assets: MediaAsset[]
  multicamGroups: MulticamGroup[]
  speakers: Speaker[]
  telopStyles: TelopStyle[]       // 話者別・用途別のスタイルプリセット
  graphicLibraryRefs: string[]    // 版面CGライブラリ(§5.9)への参照
  analysis: AnalysisIndex         // 解析ストア内の結果への参照(本体はプロジェクト外にキャッシュ)
}

interface Sequence {
  width: number; height: number; fps: Rational   // 29.97 等を正確に扱うため有理数
  videoTracks: VideoTrack[]                       // 上のトラックほど手前に重なる。枚数の上限は設けない
  audioTracks: AudioTrack[]
}

type VideoItem = MediaItem | MulticamItem | TelopItem | GraphicItem
interface ItemBase {
  id: string; start: number; duration: number     // 時刻はシーケンス上の絶対秒(現行の「前から詰める」はUI側の操作として残す)
  transform: Transform                            // 位置・倍率・回転・不透明度・クロップ(キーフレーム可)
  origin: 'auto' | 'manual'                       // 自動生成か人の修正か。再計算で manual を上書きしない
  confidence?: number                             // 自動生成時の自信度(§5.13 のレビュー対象抽出に使う)
}
interface MulticamItem extends ItemBase { groupId: string; angleId: string; sourceOffset: number }
interface TelopItem extends ItemBase { text: RichText; styleId: string; speakerId?: string; kind: TelopKind }
type TelopKind = 'speech' | 'tsukkomi' | 'inner-voice' | 'situation' | 'location' | 'corner-title'
```

- 移行: v1 の `clips[]` は V1 トラックへ、`videoOverlayTracks` は V2 以降へ、`textOverlays` は TelopItem へ変換する。
  変換の往復テスト(v1 → v2 → 書き出し結果が同一)を既存の302件に加える。
- 保存形式: 数千アイテムでも読み書きが1秒以内に収まることを受け入れ条件にする。

### 4.3 書き出しエンジン(セグメント分割レンダラ)

現行の「1回の ffmpeg で全部」をやめ、次の方式に置き換える。
**実装済み(2026-10-02)**: `src/shared/sequence/segmentPlan.ts`(区切り方)・`src/main/segmentGraph.ts`(区間のグラフ)・
`src/main/segmentRenderer.ts`(並列実行・連結)。書き出し画面の「書き出し方式」で選べる(既定は従来の方式。試験中)。

1. シーケンスを**カット点で区切った 20〜90秒(目標45秒)のセグメント**に分割する。
   繋ぎの途中と両端では切らない。1区間で読む素材は 24本までに抑える(メモリは区間の長さではなく本数で決まるため)。
2. 各セグメントについて、そのセグメントに掛かる素材だけを入力にした**小さなフィルタグラフ**を組み、**並列に**書き出す。
   映像は中間コーデックを挟まず**最終の形式で直接エンコード**する(全区間で同じエンコーダ・同じ設定)。
   入力1つあたりのデコーダは1スレッドに絞る(並列は区間の単位で取る)。
3. 映像は concat demuxer で**再エンコードせずに**連結する
   (Windows は NVENC を第一とし、NVENC が実際に開けない環境はソフトウェアエンコードへ切り替える。QSV / AMF / VideoToolbox は未対応)。
   GeForce 系は NVENC の同時セッション数に上限があるため並列数は 4 とし、失敗したセグメントは1回だけ自動で再試行する。
4. 音声もセグメントごとに書き出す(無圧縮 WAV)。区間の長さは絶対位置のサンプル数の差で決めるので、29.97fps でも合計は全体と1サンプルも違わない。
   ダッキングとフェードが区間の頭で途中から始まらないよう、2秒手前から鳴らして切り落とす。連結後にラウドネスを2パスで掛けて AAC にする。
5. (未実装)セグメント単位でキャッシュし、**変更のあったセグメントだけを再レンダリング**する。途中失敗時もそこから再開できる。

実測(開発用コンテナ・4コア・GPU なし・libx264・720p):

| 企画 | 既存の書き出し | 新しいエンジン |
|---|---|---|
| 4本+繋ぎ2つ+ワイプ+BGM(ダッキング)+テロップ、7.6秒 | 229フレーム | 229フレーム。映像の PSNR は全フレームで 41.6dB 以上(平均 44.4dB)。BGM・ワイプの音は帯域ごとの音量が一致 |
| 0.75秒×400カット(繋ぎ40)+テロップ100、約5分 | **失敗**(ffmpeg が 13GB まで膨らんで落ちた) | 成功。53秒(2並列)、ffmpeg 合計の最大メモリ 1.8GB。8,840フレームの時刻に欠落・重複なし、音声と映像の尺の差 1ms |

受け入れ条件: 60分・V12・A8・3,000アイテムのシーケンスを、基準機で**実時間の1倍以内**、
メモリ使用 8GB 以下で書き出せること。セグメントの継ぎ目でフレームの欠落・重複、音ズレが無いこと(ffprobe で検証)。

### 4.4 テロップ・グラフィックのレンダラ

**一部実装済み(2026-10-02)**: `src/shared/telop/render.ts`(描画)・`layer.ts`(絵が変わる区間だけを並べる)。
書き出し方式が「長尺向け」のとき、プレビューも書き出しもこの関数で描く(標準の書き出しは従来の ASS のまま)。
装飾は従来の全項目に加えて、外側の縁(`extraStrokes`)と縦グラデーション(`gradientColor`)。
書き出しは画面のプロセスが絵の変わる区間ごとに透明 PNG を1枚だけ描き、区間ごとに concat demuxer の1入力として重ねる。
実測(灰色の背景・3本のテロップ): 書き出しとプレビューで、テロップの外接矩形の差は枠に対して 0.3% 以内。
未実装: 座布団(帯)・ルビ・縦書き・画像の組み込み・キーフレーム、標準の書き出しの置き換え。

- Canvas 2D(必要なら OffscreenCanvas + WebGL)で描く**共通レンダラ**を `src/shared` に置き、
  画面表示ではそのまま描き、書き出し時はアルファ付きの画像として出力して ffmpeg で `overlay` する。
- バラエティの定番装飾を一級の機能として持つ: 多重縁取り(内側・外側の2重以上)、グラデーション塗り、
  ドロップシャドウ、文字ごとの色(強調語)、ルビ、縦書き、テロップ帯(座布団)、画像の組み込み。
- アニメーションは「入り・出」のプリセット + キーフレーム。複雑なアニメーションのみフレームを連番で出力する。
- フォント: 利用者が持つ商用フォント(番組で使用中のもの)を読み込めるようにする。同梱は無償ライセンスのものに限る。
- ASS 経路は Shorts 向けに当面残し、v2 レンダラが同等の結果を出せることを確認してから廃止する。

### 4.5 プレビュー

段階的に置き換える。

1. **当面**: 全素材に低解像度のプロキシ(既存の `previewProxyService.ts` を拡張)を作り、表示するレイヤー数に上限を設ける。
   上限を超える区間は、セグメントレンダラの出力(§4.3 のキャッシュ)を再生する(Premiere のレンダリングバーと同じ考え方)。
2. **本命**: WebCodecs でデコードし、WebGL で合成するプレビューエンジン。テロップは §4.4 のレンダラをそのまま使う。

- **実装状況(2026-10-04)**: 本編の `<video>` を2つにし、切れ目の2秒前から**次のクリップを控えの要素に読み込んで頭の位置で
  待たせ**、切れ目で入れ替える(`lib/previewStandby`)。別のカメラへの切り替えも、同じ素材の飛び先(間を詰めた所)も対象。
  そのまま続くクリップは今の要素で流し続ける。ダッキングの測り口は要素ごとに持つ。
  - 実測(1080p の2台を 2〜4.5秒ごとに切り替えた 9分・165クリップ・テロップ165枚): 30秒の再生で進んだ本編が
    28.2秒 → **29.3秒**、画を出せないコマ 41 → **0**、シーク 90〜270ms → **13〜81ms**。映っている画を毎コマ追うと、
    逆戻り・飛び・クリップ外の画・2つ同時の表示はいずれも 0。BGM のダッキングは入れ替えの最中も 0.48〜0.50 で保たれた
    (以前は読み込み直しの瞬間に 0.86 へ戻っていた)。
  - WebCodecs のエンジンは、この方式で足りない所(多層の PiP・4K の素材を直接など)が実測で出たときに着手する。

## 5. 自動編集パイプラインの各工程

各工程に「技術」「受け入れ条件」を定める。技術は候補であり、着手時に実測して確定する(§8)。

### 5.1 取り込み・素材整理
- 素材フォルダを丸ごと指定し、カメラ・マイク単位に自動で分類する(機種メタデータ・ファイル名の規則・収録時刻)。
- 収録の実時刻(作成日時・タイムコード)で全素材を1本の時間軸に並べ、カメラごとの録画の途切れを把握する。
- プロキシ・波形・サムネイルを並列に先行生成する。
- 受け入れ: 6時間分・200ファイルの取り込みと分類が30分以内に終わり、分類の誤りを一覧で直せること。
- **実装状況(2026-10)**: 収録フォルダの走査・ffprobe(長さ・録画時刻・機種)・振り分け(フォルダ → 機種 → ファイル名の頭。
  マイクは録音時刻で続きと分かるものだけまとめる)と、「新しい回を作る」画面での修正まで実装(`shared/ingest/classify`・
  `main/footageService`)。プロキシの先行生成は既存の仕組み(再生できない形式だけ変換)を使う。
  **未確認**: 6時間・200ファイル規模での所要時間(模擬素材5本は 0.1 秒)。波形・サムネイルの先行生成は未実装。

### 5.2 マルチカム同期
- 音声の包絡線(ダウンサンプル)の相互相関で粗く合わせ、GCC-PHAT で詰める。
  録画時刻のメタデータを探索範囲の絞り込みに使う。
- 長時間の録音で生じる**クロックのずれ(1時間あたり数十ms)**を、区間ごとに区切って補正する。
- タイムコード同期の機材がある場合はそれを優先する。
- 受け入れ: 同期誤差 ±1フレーム以内を全組み合わせの95%以上で達成し、失敗した組み合わせは自信度付きで報告すること。
- **実装状況(2026-10)**: 包絡線(100Hz)の立ち上がりの相互相関 → GCC-PHAT(16kHz)で詰める → 最大全域木で全素材を並べる
  (`shared/sync/*`・別スレッドの `main/syncWorker`)。一致の判定基準は実測から決めた(確からしさ30・抜け具合1.8)。
  ピンマイクがあれば「カメラ × マイク」を背骨にして組の数を抑える。
  時計のずれは重なり10分以上の組で頭と終わりを測って求め、**機材ごとの時計の比**として全素材に当てはめる。
  タイムラインでは本編(基準カメラ)を基準の時計にし、マイクは速度(960kHz 経由の周波数の読み替え)で補正する。
  PiP のカメラは速度を持てないため、基準カメラの録画区間ごとの頭で合わせ直すだけ(区間の中でずれが積もる。20ppm・30分で最大 36ms)。
  - 実測(模擬素材: カメラ2台・Aは2本・ピンマイク2本・AAC/WAV混在・1本は時計 62.5ppm 速い): 同期の誤差はすべて 0.1ms 以内、
    書き出した音の各音の位置の誤差 0.06〜0.13ms。30分ぶんの処理は約4秒。
  - **未確認**: 実際のロケ素材(風切り音・カメラ間の距離による音の遅れ・数時間の収録)での成功率。
    録画時刻を探索範囲の絞り込みに使う処理と、タイムコードを優先する処理は未実装(録画時刻は同じ機材の中の補助にだけ使う)。
  - あわせて見つけた既存の不具合: 書き出しで等倍の音声にも atempo=1 が掛かり、**音が 19〜26ms 遅れて揺れていた**。等倍は素通しに直した。

### 5.3 文字起こし
- whisper.cpp(Windows は CUDA、NVIDIA 以外の GPU は Vulkan、macOS は Metal)で、日本語に強いモデル(large-v3-turbo、kotoba-whisper 等)を使う。単語単位の時刻を得る。
- VRAM の使い方: 基準機(32GB)では、音声認識(large-v3、約4〜5GB)・話者埋め込み・顔検出・音声イベント検出を**同時に常駐**させ、カメラ・マイクごとに並列で処理する。最低動作環境(8GB)では工程ごとに読み込み・解放する。どちらで動くかは起動時に VRAM 量から自動で決める。
- **ピンマイクの音声を優先**して認識し、カメラ音声は補助に使う。風切り音は認識の前段でノイズ除去(§5.10)する。
- 固有名詞(出演者名・地名・番組用語)の辞書を持ち、認識のプロンプトと後処理の補正に使う。
- 受け入れ: ロケ音声の評価セットで CER 10%以下(MVP)。4時間の音声を基準機で20分以内に処理すること。
- **実装状況(2026-10)**: whisper-large-v3-turbo(単語の時刻つき・ONNX)を別スレッドで実行(`main/asrWorker`)。
  Windows は DirectML(GPU)→ CPU の順に試す。kotoba-whisper は今の実行環境で読める形式の配布が無いため見送り。
  認識にかけるのは話者の判定で見つけた発話区間だけ(無音で決まり文句を出す誤りを避け、時間も短くなる)。
  - 実測(開発環境の CPU・4bit、JSUT と Common Voice の文で作った2人の掛け合い 1分49秒・24発話): CER 8.3%
    (話者A 3.5% / 話者B 13.1%。B の誤りの多くは「わたし→私」「八→8」のような表記の違いで、実際の聞き違いは
    「写真→シャンシン」「解毒剤→ゲドクタイ」「停戦→定選」「木曽川→基礎川」など)。処理は CPU で 182 秒。
  - **未確認**: RTX 5090(DirectML)での速度と動作、風切り音のある実際のロケ音声での CER、固有名詞の辞書(未実装)。

### 5.4 話者分離
- **ピンマイクの割り当てを最も強い手がかりにする**(マイク = 出演者の対応を最初に1回だけ登録する)。
  ピンマイクが無い区間は、声の特徴量(sherpa-onnx 等の話者埋め込み)のクラスタリングで補う。
- 出演者の声の特徴を回をまたいで保存し、2回目以降は名前付けを不要にする。
- 掛け合いで声が重なる区間を検出し、両者のテロップを出す。
- 受け入れ: テロップ単位の話者の取り違え 5%以下(MVP)。
- **実装状況(2026-10)**: ピンマイクの音量で話者を決める(`shared/diarize/micTurns`)。各マイクの音量を
  「その人が話すときの普段の大きさ」でそろえ、一番大きいマイクの持ち主を話者にし、近い大きさなら声の重なりとして両方残す。
  マイクの名前を出演者名にすると、それが話者名になる(同じ収録フォルダの構成なら次の回にも引き継ぐ)。
  - 実測(上の掛け合い・かぶり -20dB): 発話の検出 24/24、話者の正解 24/24。
  - **未確認・未実装**: 0.5 秒程度の短い重なりは「重なり」として出なかった(両者の発言はそれぞれ正しい話者で認識できている)。
    ピンマイクの無い区間の、声の特徴による話者分離(話者埋め込み)と、回をまたいだ声の登録は未実装。

### 5.5 構成(LLM)
- 文字起こし(話者付き)・音声イベント(笑い・歓声、§5.6)・縮小した代表フレームの説明文を入力に、
  LLM で**チャプター分け、見どころの評価、不要区間(移動だけ・待機・段取り)、目標尺に合わせた構成案**を作る。
- 数時間分は一度に入らないため、区間ごとの要約 → 全体構成の2段で処理する。
- 出力は「採用区間のリスト(元素材の時刻)+ 理由 + 自信度」とし、理由を人が読めるようにする。
- LLM 提供元は抽象化し、既存の Gemini 連携を初期実装とする。

- **実装状況(2026-10)**: 文字起こしを話のまとまり(場面)に分け(`shared/structure/scenes`)、場面ごとに
  点数・見どころ/普通/不要・理由を付ける。Gemini の鍵があれば AI(送るのは話者つきの文字起こしだけ。40場面ずつに分けて頼む)、
  無ければ発話の密度・掛け合い・声の重なり・感嘆から簡易の点数。仕上がりの長さに収まるよう点数の低い場面から落とす。
  「構成」タブで残す/落とすを手で直し、作り直せる。
  - **AI の頼み先(2026-10-03)**: 既定は**このPCの AI**(node-llama-cpp。無料・素材が PC の外に出ない)。
    GPU は CUDA → Vulkan → なしの順に自動で選び、GPU のメモリ 16GB 以上なら Qwen2.5 14B、それ未満は 7B(4bit)。
    出力は JSON スキーマから作った文法で縛る(場面の ID を必須の項目にして、抜けを起こさない)。
    Gemini(鍵が要る)と「使わない」も「構成」タブで選べる。モデルは初回だけダウンロードして userData/models に置く。
    - 実測(CPU のみの開発環境): 7B は Electron の外で 3 場面を約40秒で妥当に判定(会話の無い場面を「不要」に)。
      1.5B は判定が逆になることがあり、実用にしない。アプリ内の通しは 1.5B で確認し、構成の判定 → カット → 演出テロップの
      提案まで AI の答えがつながることを確かめた(提案は自信が低く、自動では置かれなかった)。
    - **既知の制約**: CPU だけで動かすと、モデルの重みを1度に確保する大きさ(3B で約2GB・7B で約4GB)が
      Electron のメモリ確保(PartitionAlloc)の上限に当たり、読み込み中にプロセスが落ちる(Linux で確認)。
      GPU で動かすとモデルは GPU のメモリに載るので当たらない。落ちたときは理由を示し、簡易の点数で続ける。
  - **笑い・歓声(2026-10-03)**: 基準カメラの音を 10 秒の窓(5 秒ずらし)で AudioSet の分類モデル
    (AST・`Xenova/ast-finetuned-audioset-10-10-0.4593`、元は BSD-3)に掛け、笑い・歓声の語を含む分類の点数を足す。
    点数は**分類ごとの独立した確率(sigmoid)**で読む(パイプラインの既定の softmax では、会話に混ざった笑いが
    0.01 前後に薄まって拾えない)。実測で、笑いが混ざった窓は 0.05〜0.13、会話だけの窓は 0.00 だったため、
    しきい値は笑い 0.04・歓声 0.05。続けて超えた窓は1回に数える。GPU は DirectML(fp16)→ CPU(8bit)。
    場面ごとの回数を簡易の点数(1分に2回で +25)と見どころの判定(2回以上で見どころ)に足し、AI には
    「(笑い○回・歓声○回)」を場面の頭に添えて渡す。テスト回では笑いを足した場面に「笑い 1」が付き、見どころになった。
  - **AI の答えの崩れ対策(2026-10-04)**: 小さいモデル(1.5B)は、同じ言葉を繰り返して文字列を閉じないまま
    長さの上限に達することがあり、その頼み(最大40場面ぶん)がまるごと答えなしになっていた(同じ問いで約半分)。
    出力の形に文字数・個数の上限(見出し30字・理由120字・演出テロップの文 24字)を入れて文法で必ず閉じるようにし、
    崩れたら繰り返しを抑える設定でもう1回頼む(5回中5回答えた)。崩れたときに頼みの枠を返していなかった不具合も直した
    (同じ回の後の頼みまで答えられなくなりうる)。演出テロップは、頼み文の例をそのまま写した答え(1.5B は11件すべて
    「いや早すぎ!」だった)と同じ文の繰り返しを捨て、「答えられなかった」と「提案が無い」を記録で分けて示す。
  - **未確認**: RTX 5090(CUDA)での 14B の判定の質と速さ、Windows の CPU だけで動かした場合。Gemini での判定の質。
    本物のロケ素材(屋外の騒音・BGM の下)での笑い・歓声の拾い方。代表フレームの説明は未使用。

### 5.6 カット
- 採用区間の中を、発話の単位で刻んで間を詰める(バラエティのテンポ。間の長さは番組ごとに調整可能)。
- 既存のフィラー・無音検出を流用する。ただし**笑い・リアクションの間は残す**(音声イベント検出で笑い声を判定)。
- 受け入れ: 発話の途中で切れる箇所が 1% 以下。

- **実装状況(2026-10)**: どのマイクも鳴っていない 0.7 秒より長い間を 0.3 秒まで詰める(`shared/cut/tighten`)。
  笑い・リアクションは音として鳴っているので残る。発話の区間の中では切らない。

### 5.7 アングルの自動切替
- 規則 + 採点で選ぶ: 話している人の顔が映るカメラ / 笑い・驚きのリアクションには反応した人 /
  移動中・風景は引きの画 / 1ショットの最短・最長の長さ / 同じアングルでの不自然なジャンプカットを避ける。
- 顔検出(ONNX の軽量モデル)で「顔が映っているか・大きさ・向き」を採点に使う。
- 受け入れ: 人の完成版とのアングル一致率 60% 以上(MVP)、明らかな破綻(顔が無いアングルを話者で選ぶ等)が 1% 以下。

- **実装状況(2026-10)**: 規則による切り替え(`shared/angles/choose`)。話者の替わり目でその人を映すカメラ
  (新しい回を作る画面で「主に映す人」を登録)へ、カットのつなぎ目では必ず別のカメラへ、1ショット 2〜8 秒、
  録っていない時間は録っているカメラで埋める。本編のカメラの音は使わず、声はピンマイク、周りの音は基準カメラの音を 35% で流す。
  - 実測(カメラ2台・出演者2人・途中に25秒の無言の模擬素材 2分14秒): 無言の場面は「不要」で落ち、間を詰めて 1分49秒 → 1分29秒。
    出演者B の発言中にカメラB が映っていたのは 13/13。書き出した音の、マイク2本・カメラの音の位置の差は 0.1ms 未満。
  - **未実装**: 顔の検出(誰が映っているか・顔の大きさ)。今は「主に映す人」の登録が頼り。PiP の速度補正と同じく、
    カメラの時計のずれは素材ごとの速度でしか補正していない。

### 5.8 テロップ
- **発言テロップ**: 話し言葉を読みやすいテロップへ整える(言い淀みの除去、改行位置、1行あたりの文字数)。
  **発言の内容を変えないこと**を厳守し、整文の前後を必ず保存して比較できるようにする(LLM による言い換え・捏造の防止)。
- **話者ごとのスタイル**: 色・縁取り・配置(左右の出し分け)を話者に結び付ける。
- **演出テロップ**: ツッコミ・心の声・状況説明・地名・コーナー名の候補を LLM が自信度付きで出し、
  自信度の高いものだけを自動配置、残りは提案として表示する。
- **配置の自動調整**: 顔検出の結果を使って顔を隠さない位置へずらす。セーフエリアと、テロップ同士の重なりを避ける。
- 受け入れ: 発言テロップの話者・時刻の正しさ 95%以上、顔へのかぶり 1%以下。

- **実装状況(2026-10)**:
  - 発言テロップ: 言いよどみ(発言の頭・区切りの後の えー/あのー/えっと 等)の除去、行頭禁則と助詞・句読点を優先した改行、
    利用者が登録する用語の辞書(誤 → 正)。発言の言い換え・要約はしない(`shared/telop/polish`)
  - 話者ごとのスタイル: テロップスタイルの「自動で使う場面」で話者に割り当てる。同時に出る下のテロップは1段ずつ上に積む(`telop/stack`)
  - 顔を避ける配置: OpenCV YuNet(MIT・同梱)で、テロップが出ている時間の真ん中の画の顔を探し、下のテロップが顔に掛かれば上へ、
    上下とも掛かれば要確認(`telop/avoidFaces`)。実測(顔を画面の下に置いた模擬素材): 顔のカメラの場面の 12 枚が上へ移り、
    顔の無いカメラの場面は下のまま。顔の検出と音声認識はそれぞれ別プロセスで動かす(onnxruntime を1つのプロセスで2回読めないため)
  - 演出テロップ: Gemini がツッコミ・心の声・状況説明・地名・コーナー名を自信度つきで提案し、0.8 以上は自動で置き、残りは「演出テロップ」タブで選ぶ
    (`telop/effects`)。**未確認**: 提案の質(この開発環境に鍵が無い。答えの検証はテスト済み)
  - **未実装**: 左右の出し分け、セーフエリアの確認、誤字の疑い・放送禁止語のチェック(§5.12 の自動チェックと一緒に)

### 5.9 SE・版面CG・BGM
- **版面CGライブラリ**: 利用者の定型CG素材(アルファ付き .mov 等)を登録し、
  「きっかけ」(発話のキーワード・笑い・場面の種類)を素材ごとに付ける。既存のキーワード連動SEを映像素材へ拡張する。
- **SE**: ツッコミ・強調・場面転換に合わせた配置。番組ごとの「SEの癖」を過去回から学ぶ(§7)。
- **BGM**: チャプターの雰囲気を LLM で分類し、利用者のBGMライブラリのタグと照合する。切り替えはチャプターの境目。既存のダッキングを使う。

- **実装状況(2026-10)**: 自動編集の「SE・BGM」工程(仮編集を入れた後)。素材は利用者の**番組素材フォルダ**から選ぶ
  (新しい回の画面で指定。フォルダ名が分類: `SE/ツッコミ`・`SE/場面転換`・`BGM/楽しい`・`BGM/穏やか` など。英語などの言い換えも可)。
  - SE: 演出テロップの出だしに種類の SE(ツッコミ・心の声・状況・地名・コーナー)、場面の変わり目に場面転換の SE。
    同じ分類は順番に使い、0.6秒以内に重ねない(`shared/finish/sound`)
  - BGM: 場面の雰囲気(AI の判定に「楽しい/穏やか/緊張/感動/移動」を足した。AI を使わないときは見どころ → 楽しい、ほか → 穏やか)。
    同じ雰囲気が続く場面は1曲で通し、雰囲気が変わる所で曲を替える。曲が短ければ繰り返す。前後はフェード。音量 0.3、ダッキング入り
  - 自動のトラック(SE(自動)・BGM(自動))は作り直すと入れ替わる。手で直したトラックは消さずに残す
  - 実測(2人の会話の模擬素材・模擬の番組素材フォルダ): 場面転換の SE 1、BGM 3 本(30秒の曲を繰り返し)。
    書き出した音の BGM は、声のあるところで声の無いところより **10.0 dB** 下がった(ピンマイクの声にダッキングが反応)
  - 版面CG: ワイプのトラックに置き場所「全面(CG)」を足した(縁なし・縦横比を保って画面に収め、透過はそのまま重ねる)。
    `CG/<きっかけの言葉>/` の素材を、その言葉(2文字以上・長い言葉を優先)を含むテロップの出だしに置く。CG どうしは重ねず、
    長い素材は 8 秒で切る(`shared/finish/cg`)。プレビューで再生できない透過付きの素材(ProRes 4444・QuickTime Animation など)は、
    透過を保つ VP9(WebM)でプレビュー用に変換する(H.264 にすると背景が黒くなる)。
    - 実測: ProRes 4444(透過付き)の CG が、発言テロップ「水をマレーシアから…」の出だし(0.49秒)に自動で置かれ、
      書き出し・プレビューとも透過部分に本編が見え、テロップは CG の上に出ることを画で確認
  - 静止画(PNG・JPEG・WebP)の CG: 静止画を「ワイプ・全面(CG)のトラックにだけ置ける素材」として読み込めるようにした(本編・収録フォルダには入れない)。
    書き出しは同じ画を必要な秒数ぶんシーケンスのフレームレートで流し(`-loop 1`)、プレビューは画像のまま重ねる。番組素材フォルダの CG に
    静止画を置くと 3 秒出す。実測: 透過 PNG の CG が書き出し・プレビューとも透過部分に本編が見える形で重なった
  - 曲の繰り返しの継ぎ目は重ねてクロスフェードにした(1.5秒)
  - **未実装**: 番組ごとの SE・CG の癖の学習(§7)

### 5.10 音声仕上げ
- ピンマイクとカメラ音声のミックス(話者の声はピンマイク、環境音はカメラ)。
- 風切り音・走行音のノイズ除去(DeepFilterNet / RNNoise 等)。
- ラウドネス: 配信向け -14 LUFS(既存)に加えて、放送向け -24 LKFS(ARIB TR-B32)を選べるようにする。

- **実装状況(2026-10)**: 自動編集の「ピンマイクのノイズ除去」工程(色合わせの後)。RNNoise(ffmpeg の arnndn)で、
  笑い声も声として残すモデル(rnnoise-models の leavened-quisling。著作権の対象外と明記されたもの。同梱)を使う。
  ノイズを除いた音声を1回だけ作ってキャッシュ(userData/clean-audio、FLAC)に置き、素材をそれへ差し替える。
  プレビュー・書き出し・話者の判定・文字起こしが同じ音を読む。arnndn の遅れ(480 サンプル = 10ms)は頭を詰めて消す
  (実測: 詰めたあとの遅れ 0 サンプル)。素材一覧の右クリックで外せる。キャッシュが無い PC で開くと元の録音へ自動で戻す。
  - 実測(きれいな声に雑音を足した模擬素材): 無音部分の雑音が 街なかの雑音 -40.3 → -60.1 dBFS、強い風 -31.2 → -56.5 dBFS。
    声の損ない(SDR)は街なかで 13.5 → 13.2 dB(ほぼ損なわない)、強い風では 3.9 → 9.9 dB に改善。
    ffmpeg 標準の afftdn(+低域カット)は無音部分の雑音を 8dB ほどしか下げられず、10ms の遅れも出たので採らなかった。
    処理の速さは実時間の約 120 倍(4時間のマイクで約2分)
  - 雑音を足したピンマイクで自動編集を通すと、話者の判定は正解と同じ 24 発話(出演者A 12・B 12)
  - ダッキング: BGM は、本編から分離した音に加えて、ピンマイク(出演者の声のトラック)にも反応して下げる
  - **未実装**: 環境音(カメラの音)の扱いの調整、残響の除去

### 5.11 色合わせ
- カメラ間の色味・明るさの差を、同時刻のフレームの統計で合わせる。番組用 LUT の読み込み。

- **実装状況(2026-10)**: 自動編集の「カメラの色合わせ」工程(タイムラインに並べた直後)。基準カメラ以外のカメラごとに、
  基準カメラと**両方が録っている時間**から8か所の画を取り(160×90)、R・G・B それぞれの分布(5・25・50・75・95 の百分位)が
  基準に重なるよう「出力 = 入力 × 倍率 + 足し込み」を最小二乗で求める(`shared/color/match`)。倍率 0.7〜1.4・足し込み ±12% を上限にし、
  差がほとんど無ければ掛けない。補正は素材に持たせ(同じカメラの素材すべてに効く)、書き出しは ffmpeg の lutrgb、
  プレビューは SVG の feComponentTransfer(sRGB で計算)で同じ式を掛ける。素材一覧の右クリックで外せる(元に戻すで戻る)。
  - 実測(カメラB だけ暗く青くした模擬素材・2台): 基準カメラA との分布のずれ(5点の平均・8bit)が
    R 28.8 → 8.6、G 21.2 → 9.0、B 23.0 → 8.0。残りは2台の画角の違い(映っている物の違い)。
    プレビューと書き出しの色は同じ画で一致(各チャンネルの平均の差 0.1 未満)。
  - **未実装**: 番組用 LUT の読み込み、露出が大きく外れた素材(上限を超える差)の要確認表示

### 5.12 書き出しと自動QC
- §4.3 のレンダラで書き出したあと、自動で検査する: 黒味・フリーズ・無音区間、ラウドネス、
  テロップのはみ出し・誤字の疑い(辞書照合)・放送禁止語、セグメントの継ぎ目。

- **実装状況(2026-10)**: 書き出しが終わると、そのまま自動で確認し、書き出しダイアログの下に一覧で出す。
  項目を押すとダイアログを閉じてその位置へ移る(テロップならそのテロップを選ぶ)。
  - 映像・音声(`shared/qc/media`・`main/qcService`): ffmpeg を1回通して、黒味(0.5秒以上)・フリーズ(2秒以上。黒味のぶんは除く)・
    無音(-50dB 未満が2秒以上)・ラウドネス(基準 ±1 LU)・トゥルーピーク(基準の上限 +0.5 dB まで)。映像は縮めて測る(約25倍速)
  - テロップ(`shared/qc/telop`): 縁取りを含めてタイトルセーフ(画面の 90%)からのはみ出し、文字数に対して短すぎる表示
    (1秒10文字・最短0.5秒)、利用者が登録した「確認する言葉」、用語の辞書の「誤」の表記の残り
  - 実測(問題を仕込んだ20秒の素材をアプリで書き出し): 仕込んだ7件(黒味・静止画・無音・はみ出し・短い表示・確認する言葉・表記)を
    すべて検出し、誤検出なし。ラウドネス -14.0 LUFS。書き出し 16秒のあと、確認は 1.4秒
  - **未実装**: セグメントの継ぎ目の検査、誤字の疑い(辞書に無いもの)。放送禁止語は既定の一覧を持たず、利用者が登録する

### 5.13 人による確認・修正(全工程共通)
- 「自信の低い箇所」一覧から該当箇所へ飛び、その場で直せるレビュー画面を設ける。
- 人の修正は `origin: 'manual'` として保存し、再計算で上書きしない。修正内容は §7 の学習データとして蓄積する。

- **実装状況(2026-10)**: 自動編集の各工程の「自信の低い箇所」を1つの一覧(自動編集の画面の右「要確認」)にまとめた(`lib/reviewItems`)。
  同期(音が合わない・食い違い・同じ機材の重なり)、声の重なり、上下とも顔に掛かるテロップ、合わせられなかったカメラの色、
  ノイズ除去ができなかったピンマイク、自信が低く置かなかった演出テロップの提案、書き出し後の確認の項目。
  「移動」で編集画面のその位置へ移り(テロップならそれを選ぶ)、「直す」で直すタブへ移る。「このままでよい」はプロジェクトに保存する。
  画面の下のバーに「要確認 N」を出し、押すと一覧を開く。
  - 人の修正: 自動で置いたテロップを人が直すと印(`edited`)が付き、仮編集を作り直しても文字と見た目を残す(時刻だけ新しい仮編集に合わせる)。
    人が消したテロップは鍵を覚え、作り直しても足し直さない(演出テロップを選び直したときは置き直す)(`shared/telop/manual`)
  - 実測(アプリで通し): テロップを1つ直し、1つ消してから仮編集を作り直すと、直した文字は残り、消したものは戻らなかった
  - 本編の人の修正: 作り直す直前に、今の本編を前に自動で組んだ本編と**共通の時間軸**で比べ、削った区間・足した区間・替えたカメラを読み取って
    前の判断に重ねて覚え(新しい判断が勝つ)、作り直した仮編集に当て直す(`shared/roughCut/overrides`)。足した区間は間を詰めない。
    本編のクリップの右クリックに「アングルを ○○ に替える」を足した(そのカメラが同じ時間を録っていなければ選べない)。
    実測(アプリで通し): 1本のアングルを替え、1本を削除してから作り直すと、削った区間(23.41〜28.08秒)は戻らず、
    替えたカメラ(12.68〜18.32秒をカメラB)は保たれ、本編の長さも同じ(92.50秒)。削った所のつなぎ目は、作り直しで別のカメラへ切り替わる
    (同じカメラのまま時間が飛ぶのを避ける規則)
  - **未実装**: 修正内容を学習データとして集めること

  (区間1つの ffmpeg のメモリ: 1080p で 9.3GB → 数百 MB、4K の書き出し全体で 13.5GB 超で停止 → 2.6GB で完走。出力は従来と全フレーム一致し、20秒のテストでは 16秒 → 6秒に速くなった)。

  - 文字起こしの高速化: 同じマイクで続く発話を 28 秒までの1つの窓にまとめて認識し、単語の時刻で元の発話へ振り分ける(発話の外の単語は捨てる)。

  **未着手**: 処理時間の目標(収録4時間 → 1時間以内)の実機での測定と、GPU(RTX 5090)での各工程の速さの確認

### 6.1 フェーズ0の進め方(既存の自動開発との両立)

本リポジトリでは BACKLOG.md に基づく自動実行(実装・検証・バグ狩り・補充)が1時間おきに同じブランチへ push している。
データモデル v2 は全ファイルに波及するため、そのまま進めると衝突が常態化する。次のいずれかを利用者が選ぶ(§10)。

- **案B(採用)**: 自動実行を止めず、v2 を「新旧モデルの並存 → 機能単位の移行 → 旧モデル削除」の小さな段階に分けて進める(期間は長くなる)。

## 7. 評価方法(手本データ)

参考画面のプロジェクトは連番(#296)の番組シリーズであり、**過去回の人の編集結果は最良の評価データかつ学習データ**になる。

- **評価セット**: 過去回3〜5本ぶんの「収録素材一式 + 人が編集した完成プロジェクト(Premiere から FCP7 XML として書き出したもの)+ 完成動画」。
- **XML の読み込み機能**を評価専用に作る(採用区間・カット点・アングル・テロップの文字と時刻を抽出する)。
  仕上げを本アプリで完結させる方針とは矛盾しない(人の編集結果を読むためだけに使う)。
- **測る指標**: 採用区間の IoU、カット点の一致率(±0.5秒)、アングル一致率、テロップの再現率・CER・話者の正しさ、処理時間。
- **回帰の防止**: 指標を自動で計算するスクリプトを用意し、工程を変更するたびに比較する。
- **学習**: テロップの色・位置・文字数、SEの種類と頻度、間の長さ、ショットの長さの分布を過去回から集計し、番組スタイルの既定値にする。

- **実装状況(2026-10)**: 新しい回の画面の「過去回から学ぶ…」で、人が仕上げた過去回のプロジェクト(.veproj・複数可)を選ぶと、
  **間の長さ**(発言テロップどうしの間の中央値と 90%点 → 詰める間・残す間)、**1ショットの長さ**(本編クリップの 10%・90%点)、
  **1分あたりの SE の数**、**BGM と周りの音の音量**を集計する(`shared/style/showStyle`)。本どうしは中央値でまとめ、
  自動編集が壊れない範囲に収める。学んだ値は、カット・アングルの切り替え・周りの音の音量・SE の数の上限(演出テロップの SE を優先して残す)・
  BGM の音量に使う。「既定に戻す」で学ぶ前の値へ戻る。
  - 実測: 周りの音 60%・BGM 20% に直した過去回1本から学ばせて新しい回を自動編集すると、周りの音 60%・BGM 20% で組まれ、
    間は 1.2秒を超えたときだけ詰める(既定は 0.7秒)ので仕上がりが 1分29秒 → 1分37秒になった
  - Premiere の FCP7 XML(xmeml)を読めるようにした(`shared/import/fcp7`)。本編(一番下の映像トラック)・音声トラック(Audio Levels の音量つき)・
    文字のジェネレーター(テロップ)を秒で読む。「過去回から学ぶ…」で XML も選べる(10分を超える録音は声・周りの音として SE・BGM の集計から外す)。
    SE が1つも無い回からは SE の頻度を学ばない(0 を学ぶと以後 SE が置かれなくなるため)
  - **テロップの文字数・表示の長さ(2026-10-03)**: 発言テロップ(演出テロップは除く)が10枚以上ある回から、
    改行で分けた行の長さの 90%点(空白は数えない)を**1行の文字数**、表示時間の 10%点を**最短の表示時間**として学ぶ
    (8〜24字・0.5〜3秒に収める)。発言テロップの区切り(仮編集・「文字起こしからテロップ」の両方)に使う。
    実測: 1行18字・1.8秒で作った XML から学ばせると、同じ素材の発言テロップの1行が 14字 → 18字になり、
    1.8秒に満たない枚は 1.8秒まで延びた(カットの切れ目と次のテロップは越えない)。
    テロップの色・位置は、話者ごとのテロップスタイル(§5.8)で決めるため学ばない。
  - 評価: 自動編集の画面の「構成」タブの「人の完成版と比べる…」で、完成版の XML と今の仮編集を**共通の時間軸**で比べ、
    採用区間の一致度(IoU)・カット点の一致(±0.5秒、再現率と適合率)・アングルの一致を出す(`shared/eval/compare`)。
    完成版のクリップは素材のファイル名でこの回の収録素材に結び付け、結び付かないものは数を示して比較から外す。
    - 実測(アプリで): 仮編集そのものを XML にしたものは IoU・カット点・アングルとも 100%。頭の3本を落としたものは IoU 84%(計算どおり)
  - **未実装**: テロップの色・位置・文字数の学習、Premiere のマルチカメラ(ネストしたシーケンス)の展開、指標の自動記録(工程を変えるたびの比較)

## 8. 技術選定(候補と確定方法)

| 用途 | 第一候補 | 代替 | 確定方法 |
|---|---|---|---|
| 音声認識 | whisper.cpp + large-v3-turbo / kotoba-whisper | 現行 transformers.js | 評価セットで CER と処理時間を比較 |
| 話者分離 | ピンマイク割り当て + sherpa-onnx の話者埋め込み | pyannote(Python 同梱が必要) | 取り違え率を比較 |
| 音声イベント(笑い等) | PANNs / YAMNet(ONNX) | 音量・スペクトルの規則 | 笑い検出の適合率・再現率 |
| 顔検出 | YuNet 等の軽量 ONNX モデル(ONNX Runtime + CUDA / DirectML) | — | 速度と、ヘルメット・逆光での検出率 |
| ノイズ除去 | DeepFilterNet | RNNoise(ffmpeg `arnndn`) | 主観評価 + 認識の CER 改善量 |
| LLM | 既存の Gemini 連携 | ローカル LLM(基準機の VRAM 32GB なら、量子化した中規模モデルを手元で動かせる)/ 他社 API。抽象化して差し替え可能にする | 構成案の評価(人の完成版との IoU) |
| レンダリング | ffmpeg(セグメント分割・並列) | — | §4.3 の受け入れ条件 |

モデルとライブラリは、**商用利用可能なライセンス**のものに限る(着手時にライセンスを一覧で記録する)。

## 9. リスクと対策

| リスク | 影響 | 対策 |
|---|---|---|
| ロケ音声(風・走行音・掛け合い)で認識精度が出ない | テロップ全体の品質 | ピンマイク優先、ノイズ除去の前処理、固有名詞辞書、評価セットでの早期実測 |
| LLM が発言を言い換え・捏造する | 出演者の発言の誤り(放送上の重大事故) | 発言テロップは「整形のみ」に制限し、元の文字起こしとの差分検査を自動QCに含める |
| データモデル v2 の移行で既存機能が壊れる | 既存利用者への影響 | 移行の往復テスト、既存テスト全件、書き出しの実測比較 |
| 自動開発(Routine)との衝突 | 開発の停滞 | §6.1 の案A/案B |
| 未公開素材の外部送信 | 情報管理上の問題 | ローカル処理を優先、外部送信は代表フレームと文字起こしのみ・設定で停止可能 |
| 長尺での処理時間・メモリ | 実用性 | セグメント単位の処理と再開、解析結果のキャッシュ、GPU 利用 |
| フォント・SE・BGM・CGのライセンス | 権利侵害 | 利用者の保有素材を読み込む方式とし、同梱は商用可のものに限る |
