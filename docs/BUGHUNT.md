# バグ狩り（1時間おき / 潜在バグを探して即修正する）

このファイルは**バグ狩りロール専用**です。他のロールは書き込みません。
`BACKLOG.md` に書くと、実装・補充・検証の3ロールと毎回衝突するため分けてあります。

## このロールの立ち位置

| ロール | 見るもの | 動くとき |
|---|---|---|
| 検証 | **直近のコミットが壊していないか** | 壊れているときだけ直す |
| バグ狩り（これ） | **前からずっと壊れていたもの** | 毎回1件見つけて直す |

検証ロールは「壊れていなければ何も変更せず終了」なので、**最初から間違っていたコードは永久に拾えません**。
実際、60fps素材が常に30fpsで書き出されていた不具合は、尺が合っていてエラーも出ないため、
検証を何十回通しても素通りしていました。そこを掘るのがこのロールです。

## 1回の実行でやること

**1件だけ**見つけて、**その場で直して**、**push するまで**が1セット。
見つけて報告するだけで終わらせない。直せないものを見つけたら、次項の手順で候補に残す。

### 手順

1. **担当領域を1つ選ぶ。** 下の「領域の巡回表」で**最終掃引が一番古いもの**。
   同じ領域を続けて2回選ばない。
2. **`BACKLOG.md` の「再発防止チェックリスト」を全部読む。**
   これが探すための眼鏡です。各項目を「この領域でこれに違反している箇所はないか」という
   grep の観点に翻訳して、順に当てていく。項目数が多いので、当てた項目と結果を手元に控える。
3. **怪しい箇所を見つけたら、直す前に「本当に壊れているか」を実測で確かめる。**
   ここを飛ばすと、壊れていないものを「直して」しまう。実際に何度も起きています
   （呼び出し方を間違えて2件を誤検知、クリップ終端での分割を不具合と誤認、など）。
   実測とは、アプリを起動して同じ操作をする・ffprobe で数字を読む・DOM の値を読む、のいずれか。
4. **直す。** 進め方は `BACKLOG.md` の「実装の進め方」（設計 → 実装 → 単体 → 結合）に従う。
5. **同じ種類が他にないか grep で洗う。** 1箇所だけ直すと、残りが黙って壊れたままになる。
   （実例: 書き出しの `fps=30` を直したら、画面側にも `1 / 30` が3箇所あった）
6. **チェックリストに1行足す**（`BACKLOG.md` の「再発防止チェックリスト」）。
   既存項目と同じことを言い換えただけなら足さない。既存項目で拾えたなら、そう報告する。
7. このファイルの巡回表の日付と「見つけたもの」を更新して、コード変更と一緒にコミットする。

### 何も見つからなかったとき

**でっち上げない。** 「異常なし」で終えてよい。ただし巡回表は更新して、
**どのチェックリスト項目をどう当てて、なぜシロと判断したか**を1〜2行残すこと。
これが残っていないと、次回また同じ当て方をして同じ時間を溶かします。

### 直すのが大きすぎたとき

無理に大改造しない。`BACKLOG.md` の「候補」欄に
「◯◯の修正（バグ狩りで発見。症状は△△、原因の見当は□□）」として1件残し、
このファイルにも記録して終える。**症状と再現手順は必ず数字付きで書く。**

## 優先順位

同じ日に2つ怪しいものが見つかったら、**編集作業が止まる/出力が壊れるほう**を先に直す。

1. 出力が壊れる（尺ズレ・音ズレ・映像の欠落・書き出し失敗）
2. 編集内容が失われる（Undoで戻らない・保存で消える・参照が切れる）
3. 画面と出力が食い違う（プレビューで決めた見た目が出力で別物）
4. 操作が効かない・効きすぎる
5. 表示崩れ・文言

### 2026-08-13 AI連携（2周目の10件目）
この領域は Gemini 応答の要素ごとの coerce・YouTube の `items` の欠落・好み学習の浅マージを
既に直してあるので、**まだ当てていない眼鏡**（「生の英語メッセージをそのまま画面に出して
いないか」の**Web API版**、および「失敗したときに利用者は次に何をすればよいか分かるか」）で
見直した。

やり方は前回のIPC境界と同じで、**コードを読む前に実機で失敗させた**。利用者と同じ操作
（キーを入れてボタンを押す）で、`.error-text` に出た文字をそのまま読んでいる。

実測（**実機**。①④は本物の通信、③⑤⑥は公式のエラー本文・`null` 応答を `fetch` に返させた）:

| 場面 | 修正前に画面へ出た文字 | 修正後 |
|---|---|---|
| 通信できない(圏外・プロキシ断) | **`Failed to fetch`**(15文字) | インターネット接続を確認して…(50文字) |
| YouTube 利用上限(403) | **117文字の英語 + `<a href="/youtube/v3/getting-started#quota">` タグ**(高さ 67.2px) | 利用上限に達しました。時間をおいて…(44文字) |
| Gemini 混雑(503) | **`The model is overloaded. Please try again later.`** | 一時的に応答できませんでした。しばらく待って… |
| Gemini の応答が `null` | **`Cannot read properties of null (reading 'titles')`** | 期待した形の結果が返りませんでした。もう一度… |
| 正常な応答(回帰) | エラー表示なし・題名/説明/固定コメントが出る | **同じ** |

`Failed to fetch` は `fetch` が**通信できないときに例外を投げる**ため。`res.ok` の分岐には
来ないので、`try/catch` の無い経路は全部ここで生の英語になる。利用上限のほうは相手の
`error.message` をそのまま投げていたためで、**YouTube の文言には `<a>` タグが入っている**。
`null` のほうは自分のコードが落ちた例外文で、利用者にはアプリが壊れたようにしか見えない。

直したのは**読む側の1箇所**。`httpJson.ts` に `fetchJson()`(通信失敗・HTTPエラーを日本語化)と
`parseModelJsonObject()`(応答がオブジェクトかを見る)、`describeBodyFailure()`
(**HTTP 200 のまま本文で失敗を伝える** Jamendo 用)を置き、**11経路すべて**を通した。
原因の判定は HTTP コードと `error.errors[].reason` / `error.status` で行う——英文の
パターン照合だけにすると、相手が文言を変えた日から黙って未知扱いに戻る。
見慣れない原因は捨てず、タグを落として120文字で切って残す。

単体48件。**エラー本文は本物を使った**（不正キーの2件は実際に YouTube / Gemini を叩いて
取得した `API key not valid. Please pass a valid API key.`）。境界値は 400/401/403/429/500/
502/503、本文が空・HTML・配列・`null`・`error` が文字列・`message` が数値、原文1000文字、
タグだけの本文、モデル応答の `null`/配列/数値/文字列/`true`/空文字/途中で切れたJSON。
正常応答がそのまま返ることも対で確認している。

**検算**: 期待どおりに直ったので、**成功時のデータの流れを壊していないか**を実機で測り直した
（11経路のうち単体では追えない画面側）。YouTube 急上昇は 2件のカードと再生数「1.2万回」が
出て、`items` に `null` が混ざっても残りが出る（前回の修正も生きている）。Jamendo 検索は
曲名・作者が出る。Jamendo が **200 で `failed`** を返す経路も、生の
`Your credential is not valid` から「キーが受け付けられませんでした…」に変わった。

同種を洗ったところ、JSON を読む外部API呼び出しは **11箇所**
（YouTube 4・Gemini 6・Jamendo 1・Freesound 1 のうち Gemini は分析/チャット/メタデータ/
ショート/採点/演出/説明文）で、**全部が素通しだった**。残った `fetch` は
サムネイル画像の取得1箇所だけで、こちらは失敗しても `null` を返して画面に出さない作り。
main 側（VOICEVOX・ダウンロード・ffmpeg）は既に日本語になっている。

### 2026-08-13 解析系（2周目の9件目）
この領域は無音検出のしきい値・BPMの手直し導線を既に直してあるので、
**まだ当てていない眼鏡**（「自動検出の結果を画面に出すなら、外れていたときに手で直せる
導線があるか」を**一歩進めて「そもそも結果が画面に見えているか」**）で見直した。

見つけたのは、**スマートクロップ（被写体の自動検出）の結果が、画面に一切出ていなかった**こと。
`.preview-frame video` は `object-fit: contain` 固定で、**`fillCrop` も `cropCenter` も
プレビューでは読まれていない**。書き出しとサムネイル生成は `scaleToFrameFilter` で
切り抜くので、**画面と出力が別物**になる。

実測（**実機**・利用者と同じ操作。9:16 プロジェクトに 1280x720 の素材
（左1/3赤・中央1/3緑・右1/3青）を置き、インスペクタと同じ `updateClipCrop` で
設定を変えて、プレビュー枠を `capturePage` して画素を数えた。書き出しは同じ
プロジェクトを 720p で書き出してフレームの画素を数えた）:

| 場面 | 画面(修正前) | 画面(修正後) | 書き出し |
|---|---|---|---|
| ① クロップOFF | 黒68.5 / 赤10.5 / 緑10.8 / 青10.3 | **同じ**（回帰なし） | 黒68.4 / 赤10.5 / 緑10.5 / 青10.5 |
| ② ON・位置0.5 | **①と同じ画素** | **緑 99.1%** | **緑 100%** |
| ③ ON・位置0.1 | **①と同じ画素** | **赤 99.1%** | **赤 100%** |
| ④ ON・位置0.9 | **①と同じ画素** | **青 99.1%** | **青 100%** |

つまり修正前は、**クロップのON/OFFも、切り取り位置 0.1〜0.9 も、画面は4通りとも同じ画素**。
「切り取り位置」の2本のつまみと「被写体を自動検出」ボタンは、**押しても画面が変わらない**ので、
**外れているかどうかを判断する手段が書き出ししか無かった**。

`object-fit: cover` + `object-position` に切り替えた。ただし**同じ数字は同じ場所を指さない**:
ffmpeg の `crop` は素材内の位置（`iw*cx - ow/2` を 0〜`iw-ow` に収める）だが、
CSS の `object-position` は**はみ出し量に対する比**。換算を `@shared/videoFrame` の
`cropObjectPosition()` に置き、書き出しの式のすぐ隣に並べた。

単体45件。**期待値は比の式を書き写さず、書き出し側の式を画素で再現して作った**
（`scale=...:increase` → `min(max(0, iw*c - ow/2), iw-ow)` → はみ出しで割る）。
横に切る11点・縦に切る7点・端の張り付き4件・境界値（未設定/NaN/±Infinity/負/1超/0/1）・
縦横比が 0/負/NaN/Infinity・素材と出力の比が同じ（切る所が無い→中央）。
**±Infinity は書き出しに合わせて端へ倒す**——実測で ffmpeg の `crop` に `Infinity` を
入れると右端（青100%）、`-Infinity` で左端（赤100%）になると確かめてから決めた。
NaN だけは中央に倒す（ffmpeg は右端になるが、値としての意味が無い）。

**検算**: 期待どおりに出たので、①**切る向きを変えて**もう一度測った。16:9 プロジェクトに
720x1280 の素材（上1/3赤・中1/3緑・下1/3青）を置くと、縦0.1/0.5/0.9 で画面は
**赤100% / 緑100% / 青100%**、書き出しも同じ。②残っていた黒 0.8〜0.9% は
枠の実寸が 133x**236.39** と端数を持つため `capturePage` の矩形を丸めた分で、
端数の出ない 16:9 側（420.27x236.39 → 420x236）では**黒 0.0%**だった。
③書き出しは4通りとも**バイト単位で同一**（81,804 / 81,527 / 81,527 / 81,527 B）——
画面だけを直したことを数字で確認した。

同種を洗ったところ、`Clip` が持つ「見え方を変える設定」は
`speed` / `transitionIn` / `fillCrop` / `cropCenter` / `blurBackground` の5つ。
速度は `playbackRate`、ぼかし背景は `PreviewBlurBackdrop` で画面に効いており、
**クロップの2つだけが読まれていなかった**。
`transitionIn`（つなぎ）はプレビューが `PreviewPlayer.tsx` の中で一度も読んでおらず、
クロスフェードは画面では再現されない。ただしこれは1枚の `<video>` では表現できない
（2本を重ねて再生する必要がある）**別の作り**の話で、クロップのように
「同じ絵を別の位置で切る」だけでは済まないため、今回の1件とは分けた。
サムネイル生成（`generateFrameDataUrl`）は最初からクロップを渡していた。
PiP は型に `fillCrop` を持たず、書き出しも `scale=w:-2` で切らないので食い違いは無い。

**同種が1件残っているので `BACKLOG.md` の「候補」に記録した**: トリムのモーダルの映像は
素材そのままで、「被写体を自動検出してクロップ位置を調整」を押しても**適用するまで
1画素も変わらない**（実測: 検出後も3色すべて見えたまま。適用後のプレビューは緑100%）。
プレビューと同じ関数が使えるが、モーダルには**プロジェクトの縦横比の枠が無い**ため
レイアウトの作り替えが要る＝今回の1件には大きすぎると判断した。

### 2026-08-13 プレビュー再生（2周目の8件目）
この領域は PiP の余白を既に直してあるので、**まだ当てていない眼鏡**
（「同期」＝再生位置を追う仕組みが、編集が入っても保たれるか）で見直した。

まず速度の扱いを確かめた（音声は `inPoint + (playheadTime - startTime) * speed`、
本編は `playbackRate = speed` と rAF 側の `/ speed`、PiP は型に `speed` を持たない）。
ここは全経路で筋が通っていた。**シロを先に確定させてから**、
「覚えておいた1件を、あとで同じ一覧から探す」箇所に絞った。

見つけたのは、**再生中に編集を1つすると、次のクリップの境目で先頭へ戻る**こと。
`timedClips` は `useMemo(..., [project])` で、**project が少しでも変わると中身が同じでも
作り直される**。一方 `activeTimedClipRef` は「1つ前の配列の」オブジェクトを持ったままで、
境目の判定が `timedClips.indexOf(tc)` という**同一性の照合**だった。
`indexOf` は **-1** を返し、`timedClips[-1 + 1]` が **`[0]` = 先頭のクリップ**になる。
例外も警告も出ず、**「次へ進んだ」動作そのものに見える**。
テロップを足す・素材を読み込む・クリップを選ぶなど、**映像の並びと無関係な編集でも起きる**。

実測（**実機**・利用者と同じ操作。2秒の素材を3本並べて境目は 2.0 と 4.0 秒。
1.5秒から再生し、0.1秒ごとに再生位置を22回読む）:

| 場面 | 到達した最大の再生位置 | 先頭へ飛んだか |
|---|---|---|
| ① 再生だけ（対照） | 3.54 秒 | いいえ |
| **② 再生しながらテロップを1つ足す（修正前）** | **1.96 秒** | **はい** |
| **② 同じ操作（修正後）** | **3.69 秒** | **いいえ** |

修正前の軌跡: `1.66 1.76 1.86 1.96 → 0.02 0.08 0.18 …`（以降そこを繰り返し、
**2.0秒より先へ二度と進めない**）。修正後: `1.66 1.76 1.86 1.96 2.01 2.08 … 3.69`。

照合を ID に変えた（`findTimedClipById` / `nextTimedClip` を `timelineMath.ts` に追加）。
**見つからないときは「先頭」ではなく「決められない」を返す**——消えたクリップの次は
決められないので、`-1 + 1 = 0` のような「それらしい値」を作らない。
併せて、一覧が作り直されたら ref を**今の一覧の同じ ID の物へ差し替える**
（覚えている1件は `start`/`outPoint` まで編集前のまま凍っているため）。
差し替えは**読み込み直しを伴わない**——再生中に毎回読み込み直すと音が飛ぶ。

単体25件。作り直した配列でも次が正しく引けること、境界値は
並びが空・current が null/undefined・1本だけ・**再生中のクリップが消えた**（先頭ではなく
「無し」）・**尺0秒のクリップを挟んだ場合**・200本の末尾、そして `findTimedClipById` の
ない ID / null / undefined / 空文字。同じ配列内での従来動作も3件で確認した。

**検算**: 期待どおりの結果が出たので、**修正を stash で外して同じ probe を流し直した**。
`indexOf` に戻すと `先頭へ飛んだか=true` / 最大 1.96 秒が**再現した**（対照の①は
どちらでも 3.54 秒で不変）。同じ手順・同じ素材で、**測れていること**を確かめてから戻した。

同種を洗ったところ、`indexOf` で並びの中の位置を求めているのは他に
`TextOverlayPanel` の「何番目のクリップか」表示だけで、こちらは**同じレンダーで作った
配列から `findTimedClipAt` で取り出した物**をそのまま渡しているので同一性が成り立つ。

1. 最初の実測は「既定ズームで左端を引き切れば自分の終端(4.0)にくっつくはず」と読んで

### 2026-08-13 音声（2周目の3件目）

### 2026-08-13 書き出しパイプライン（2周目の1件目）

### 2026-08-12 解析系（ハイライト・BPM・無音・スマートクロップ）
無音検出だけが `noise=-30dB` の**絶対しきい値の決め打ち**だった。素材の録音レベルは

(`longFormService` には「固定のdBしきい値はマスタリングの違う素材で破綻する」と
コメントまである)、**無音検出だけが取り残されていた**。

実測（同じ構造の素材=音2秒/無音1秒/音2秒/無音1秒/音2秒、音量だけ変えたもの。
実機のIPC経由でも同じ数字を確認）:

### 2026-08-12 プレビュー再生（同期・プロキシ・PiP）
PiP(ワイプ)を隅から離す余白が、書き出しとプレビューで**基準の辺が違っていた**。
書き出しは `margin = round(出力幅 * 0.04)` を **x にも y にも**使うのに、プレビューは
CSS の `top/bottom: 4%`。**`top`/`bottom` の `%` は親の高さ基準**なので、同じ「4%」でも
別物になる。しかも**縦横比によってズレの向きが逆になる**。

実測（実機のDOM実寸 vs 書き出しフレームの画素。scale=0.3 / bottom-right）:

| | 書き出し | プレビュー(修正前) | プレビュー(修正後) |
|---|---|---|---|
| 9:16 の縦の余白(高さ比) | **2.25%**(43.2/1920) | **4%** | **2.25%** |
| 縦の余白(枠の幅に対する比) 9:16 | **4.07%** | 7.11% | **4%** |
| 縦の余白(枠の幅に対する比) 16:9 | **4.06%** | 1.36% | **4%** |
| 横の余白 | 4.06% | 4% | 4% |
| PiPの幅 | 幅の30%(576/1920) | 30% | 30% |

書き出しの実測は 1080p の書き出しフレームをPNGに落として赤いPiPの画素範囲を数えたもの
(16:9 1920x1080 で右78px・下78px、9:16 1080x1920 で右44px・下44px、720p でも比は同じ)。
規則を `src/shared/pipLayout.ts` に出して両方が同じ関数を呼ぶ形にし、プレビューは
枠の実寸(幅)を ResizeObserver で測って **px で指定**するようにした
(CSS の `%` では縦方向を幅基準にできないため)。
単体17件OK(0・負・NaN・±Infinity・極小・巨大、および `Math.round` した値が従来と同一)。
回帰: **書き出しはバイト単位で完全一致**(13,126バイト)。出力は1ピクセルも変えていない。

**掃引中に別の問題を見つけたので候補に残した**: 16:9 プロジェクトでは
`.preview-frame` が縦横比を保てず横に潰れており(実測 694x236.41 = 2.94、あるべき 1.78)、
`object-fit: contain` で映像は 420.28x236.41 に収まる一方、**PiP は枠基準なので
左右の黒帯(136.86px)の上に描かれる**。9:16 は `height: 100%` を使っているため正しい。
CSS レイアウトの作り替えと広範な回帰確認が要るので `BACKLOG.md` の「候補」へ数字付きで記録。
そのため今回の一致確認は、枠と映像が一致している **9:16 側で行った**。

同種を洗ったところ、PiPの幅(`scale`)は書き出し・プレビューとも**幅基準で一致**、
テロップの `customPosition` は正規化座標を各軸の辺に掛けるので一致しており、
基準の辺が食い違っていたのは PiP の縦の余白だけだった。

### 2026-08-12 タイムラインUI（ドラッグ・トリム・スナップ・選択）
音声クリップ/PiPクリップのトリム(`mediaTrimDrag`)だけが、マウスの移動量
(`px ÷ pixelsPerSecond` = **タイムライン秒**)を `inPoint`/`outPoint`(**素材秒**)へ
そのまま足しており、**速度で換算していなかった**。本編クリップのトリム(`trimDrag`)には
最初から `* prev.speed` がある。等倍では正しく動くので気付けない。
分離音声は本編クリップの速度をミラーする(2倍速のクリップから分離すると `speed=2`)ため、
**利用者が普通に踏む**経路。

実測（実機Electron / xvfb / 40px per second のタイムライン / 素材10秒・in=2 out=6 start=2）:

| 操作 | 修正前 | 修正後 | 期待 |
|---|---|---|---|
| speed=1 右へ+40px | 幅 +40px | 幅 +40px | +40px |
| speed=1 左へ+40px | 左端+40px / 終端0px | 同左 | 終端は動かない |
| **speed=2 右へ+40px** | **幅 +20px**(out 6→7) | **幅 +40px**(out 6→8) | +40px |
| **speed=2 左へ+40px** | 終端が **+20px 動く** | **終端 0px** | 動かない |

境界値も実機で確認: 右へ+400px → out=10(素材の終端でクランプ)、右へ-400px → out=2.2
(最小尺0.2)、左へ-400px → in=0/start=1(素材先頭)、左へ+400px → in=5.8/start=3.9
(最小尺。終端は 3.9+0.1=4.0 で元と同じ)、speed=0.5 右へ+40px → out=6.5(タイムライン+1秒)。
回帰: PiP(速度を持たない型)は右+40px→out=7、左+40px→in=3/start=3 で従来どおり。

**測り方の失敗を1件記録**: 最初の測定は out が素材の終端(10秒)に張り付いた状態で
ドラッグしたため「幅の増分0px」となり、症状が出ていないように見えた。
伸ばす余地を作ってから測り直して初めて 20px/40px の差が出た。
「何も起きなかった」を正常と読まないこと。

同種を洗った結果、タイムライン秒↔素材秒の換算は他に
`trimDrag`(本編/`* prev.speed` あり)・`rollTrim`(ストア側で speed 込みでクランプ)・
レーザー分割(`splitClipAtTime` がストア側で換算)・`splitAudioClipAtTime`
(`* (c.speed || 1)` あり)・音声クリップの表示幅(`audioClipDuration` で `/speed`)があり、
**すべて処理済み**。移動系のドラッグ(`audioDrag`/`videoOverlayDrag`/`overlayDrag`)は
`startTime` しか触らないので換算不要。漏れていたのは `mediaTrimDrag` の1箇所だけだった。

### 2026-08-12 IPC境界（main↔renderer・エラー処理・並行実行）
main→renderer の通知は `event.sender.send` の2箇所だけで、**プレビュープロキシ側にだけ
`isDestroyed()` ガードがあり、書き出しの進捗は無防備**だった。`send` は破棄済みの
webContents に対して `TypeError: Object has been destroyed` を投げる（Electron 実機で確認。
`win.close()` の直後は `isDestroyed()` がまだ false で、少し待つと true になる）。
投げる場所が ffmpeg のイベントハンドラの中なので `ipcMain.handle` の外、つまり
**どこにも捕まらず main プロセスごと落ちる**。
実測（1080p・40秒・実機Electron / 書き出し開始1.0秒後にウィンドウを閉じる）:
修正前 `uncaughtException: Object has been destroyed` でアプリ異常終了、書き出し先に
**48バイト・moov atom not found の再生できないファイル**が残る。
修正後は書き出しが最後まで走り、**1200フレーム / 映像40.000秒・音声40.000秒**で完走。
対照（修正前のままウィンドウを閉じない）は 14.0秒・進捗21回で完走したので、
原因が「閉じたこと」であることも確かめた。
単体: 生きている相手には境界値（0 / 100 / -1 / 33.333333 / 空文字 / null / undefined）が
そのまま届き例外0件、破棄済みの相手には1000回連続で送っても例外0件。
ガード無しの式は1回で TypeError になることも並べて確認（テストが空振りしていないことの裏取り）。
回帰: ウィンドウが生きている場合の進捗送信は修正前後とも21回、出力も同一。
Linux/Windows は最後のウィンドウを閉じるとアプリ自体が終了するため、
利用者が踏むのは**ウィンドウを閉じてもアプリが残る macOS**（`electron-builder.yml` の
ビルド対象に含まれる）。実測はその挙動に合わせて `window-all-closed` を握って行った。
同種を洗ったところ main→renderer の送信は他に無く、進捗コールバックを渡している
IPCハンドラも書き出しとプレビュープロキシの2つだけだったので、両方を共通の
`notifySender` に通す形にした。

### 2026-08-12 音声（ミックス・ダッキング・正規化・分離音声）
書き出しの音声の枝がどこも形式を固定しておらず、libavfilter の形式交渉で
**グラフ全体が一番安い形式へ引きずられていた**。`aresample=async=1` が本編の枝にあるため、
モノラル素材が1本混ざると「変換の少ない側」としてモノラルが選ばれる。
実測（48kHzステレオの本編＋モノラルBGM 1本）: 修正前 **44.1kHz・1ch**、
左だけに入れた音（素材 L -21.1dB / R -91.0dB）が中央に潰れて 1ch -20.4dB。
修正後は **48kHz・2ch**、L -19.8dB / R -25.9dB で定位が残る。
音声を分離したクリップがあると `anullsrc` の決め打ち 44100 に道連れで落ちる件、
既定ONの音量正規化を通すと `loudnorm` の内部 192kHz が漏れて**出力が96kHz**になる件も
同じ原因だったので、音声の全5経路（本編・`anullsrc`・PiP・音声トラック・`loudnorm` の後ろ）に
`aformat=...:sample_rates=48000:channel_layouts=stereo` を掛けて塞いだ。
検算: モノラルBGM版とステレオBGM版が 0-4s / 4-6s とも -21.1dB / -24.1dB で一致（同じ扱いになった）。
回帰: ステレオBGM・本編のみ・44.1kステレオ素材は修正前後とも -24.1dB で不変。
無音（音声なし素材）-91.0dB、PiPの発音区間 1〜4s、速度2倍のBGMが0-2sで終わることも不変。
全15ケースで映像と音声のストリーム長が一致（クロスフェード時 5.000s / 150フレームも不変）。
ffmpeg のモノラル→ステレオ変換は各chが -3dB（電力は保存）である点も実測した。
同種を洗ったところ、波形画像の `aformat=channel_layouts=mono` は画像用で意図的、
`silencedetect` は解析のみ、プレビュープロキシは既に `-ac 2`、書き出しのグラフを
組む場所は `exportProject` の1箇所だけだった。
