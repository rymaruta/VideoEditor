# バグ狩り（1時間おき / 潜在バグを探して即修正する）

このファイルは**バグ狩りロール専用**です。他のロールは書き込みません。
`BACKLOG.md` に書くと、実装・補充・検証の3ロールと毎回衝突するため分けてあります。

## このロールの立ち位置

| ロール | 見るもの | 動くとき |
|---|---|---|
| 検証 | **直近のコミットが壊していないか** | 壊れているときだけ直す |
| バグ狩り（これ） | **前からずっと壊れていたもの** | 毎回1件見つけて直す |

検証ロールは「壊れていなければ何も変更せず終了」なので、**最初から間違っていたコードは永久に拾えません**。
実際、60fps素材が常に30fpsで書き出されていた不具合は、尺が合っていてエラーも出ないため、
検証を何十回通しても素通りしていました。そこを掘るのがこのロールです。

## 1回の実行でやること

**1件だけ**見つけて、**その場で直して**、**push するまで**が1セット。
見つけて報告するだけで終わらせない。直せないものを見つけたら、次項の手順で候補に残す。

### 手順

1. **担当領域を1つ選ぶ。** 下の「領域の巡回表」で**最終掃引が一番古いもの**。
   同じ領域を続けて2回選ばない。
2. **`BACKLOG.md` の「再発防止チェックリスト」を全部読む。**
   これが探すための眼鏡です。各項目を「この領域でこれに違反している箇所はないか」という
   grep の観点に翻訳して、順に当てていく。項目数が多いので、当てた項目と結果を手元に控える。
3. **怪しい箇所を見つけたら、直す前に「本当に壊れているか」を実測で確かめる。**
   ここを飛ばすと、壊れていないものを「直して」しまう。実際に何度も起きています
   （呼び出し方を間違えて2件を誤検知、クリップ終端での分割を不具合と誤認、など）。
   実測とは、アプリを起動して同じ操作をする・ffprobe で数字を読む・DOM の値を読む、のいずれか。
4. **直す。** 進め方は `BACKLOG.md` の「実装の進め方」（設計 → 実装 → 単体 → 結合）に従う。
5. **同じ種類が他にないか grep で洗う。** 1箇所だけ直すと、残りが黙って壊れたままになる。
   （実例: 書き出しの `fps=30` を直したら、画面側にも `1 / 30` が3箇所あった）
6. **チェックリストに1行足す**（`BACKLOG.md` の「再発防止チェックリスト」）。
   既存項目と同じことを言い換えただけなら足さない。既存項目で拾えたなら、そう報告する。
7. このファイルの巡回表の日付と「見つけたもの」を更新して、コード変更と一緒にコミットする。

### 何も見つからなかったとき

**でっち上げない。** 「異常なし」で終えてよい。ただし巡回表は更新して、
**どのチェックリスト項目をどう当てて、なぜシロと判断したか**を1〜2行残すこと。
これが残っていないと、次回また同じ当て方をして同じ時間を溶かします。

### 直すのが大きすぎたとき

無理に大改造しない。`BACKLOG.md` の「候補」欄に
「◯◯の修正（バグ狩りで発見。症状は△△、原因の見当は□□）」として1件残し、
このファイルにも記録して終える。**症状と再現手順は必ず数字付きで書く。**

## 優先順位

同じ日に2つ怪しいものが見つかったら、**編集作業が止まる/出力が壊れるほう**を先に直す。

1. 出力が壊れる（尺ズレ・音ズレ・映像の欠落・書き出し失敗）
2. 編集内容が失われる（Undoで戻らない・保存で消える・参照が切れる）
3. 画面と出力が食い違う（プレビューで決めた見た目が出力で別物）
4. 操作が効かない・効きすぎる
5. 表示崩れ・文言

### 2026-08-17 プロジェクト入出力（6周目の7件目）

**まずチェックリストの該当項目が既に効いているかを確かめた。** 保存は隣に書いてから
rename する形（途中で落ちても元が残る）、`.veproj` の検証は多段、読み込みの失敗は
日本語——ここは3つとも既に入っていた。**入っていた仕組みそのものが別の代償を
払っていないか**へ視点を移して見つけた。

**症状**: プロジェクト名に長い名前を付けると、**名前は付けられるのに保存だけできない**。
保存の瞬間に生の英語 `ENAMETOOLONG: name too long, lstat '/…'` が出る。

**原因**: 一時ファイル名を `${filePath}.saving-${pid}-${連番}.tmp` と**保存先の名前から**
作っていた。パス1要素の上限は **255バイト**なので、足した約22バイトぶん、
**利用者が使える名前が先に上限に当たる**。しかも `catch` の中の `rmSync` が投げるため、
外へ出る文言が本当の原因（`rename` の失敗）ではなく**後始末の `lstat`** になっていた。

**実測（Node レベル / 同じ名前へ直に書いた場合と並べた）**

| 名前の長さ | `saveProjectFile`（修正前） | 同じ名前へ直に `writeFileSync` |
|---|---|---|
| 日本語 76文字（235バイト） | 保存できる | 書ける |
| **日本語 77文字（238バイト）** | **`ENAMETOOLONG`** | **書ける** |
| 日本語 82文字（253バイト） | `ENAMETOOLONG` | 書ける |
| 半角 232文字（239バイト） | 保存できる | 書ける |
| **半角 233文字（240バイト）** | **`ENAMETOOLONG`** | **書ける** |

直書きが 255バイトまで通ることが、**失われていたのが足したぶんそのもの**である証拠。

**実測（実機 / ダイアログのあとに UI が呼ぶのと同じ `window.api.saveProject`）**

| 操作 | 修正前 | 修正後 |
|---|---|---|
| 日本語 76文字の名前で保存 | 保存できた | 保存できた（変わらず） |
| **日本語 77文字の名前で保存** | **失敗（`lstat` の `ENAMETOOLONG`）** | **保存できた** |
| 日本語 82文字（253バイト） | 失敗 | **保存できた** |
| 日本語 100文字（307バイト・OSの上限超え） | 失敗（文言は `lstat`） | 失敗（文言が **`rename`** ＝本当の原因） |
| 保存先に残る `.tmp` | 0 | 0（変わらず） |

**検算・回帰**: 保存したものを読み戻して**中身が一致するか**まで見た（クリップ2件 /
テロップ1件 / 素材1件、`true`）。上書き保存は2回目の内容で読み戻せ（名前「2回目」・
クリップ3件）、自動保存も従来どおり（`autosave.veproj` あり・名前「自動保存のテスト」・
クリップ2件）。単体は境界値込みで **22項目すべて期待どおり**（1文字 / ドットだけの名前 /
空白と記号 / 親がファイル→`ENOTDIR` / ディレクトリ無し→`ENOENT` / 255バイトちょうど /
上限超えは正しく `ENAMETOOLONG`）。

**測り方で2回まちがえた**（期待どおりに見えたときほど疑うこと）:
`chmod 0o500` で `EACCES` を期待した項目は、**root で動かしているので許可ビットが
無視され**て通ってしまった（親をファイルにする形へ差し替え）。
「文言に `open` が出るはず」も外れ——短い一時名では**書き込みは成功し、失敗は rename へ
移る**ので、実際の文言を見てから `rename` を含み `lstat` を含まないことへ直した。

**同種の掃引**: 名前を足して別のファイル名を作っている箇所は4つ。
プレビュープロキシの `.partial.mp4`（ハッシュ16桁・**32バイト**）と自動保存の
`-discarded`（`autosave.veproj`・**25バイト**）は元が固定長なので影響なし。
`audioLibraryService` は `${UUID}-${曲名を slice(0,80)}.${拡張子}` で、
**文字数で切っているせいで日本語72文字の曲名から 257バイト → `ENAMETOOLONG`**（実測）。
今回は1件だけ直す原則に従い、`BACKLOG.md` の候補へ数値付きで残した。

### 2026-08-17 タイムラインUI（6周目の6件目）

**この領域は既に何度も直してあるので、まず「算数」を全部測り直した。** ドラッグの
移動量が理論値と合うかを、**8種類 × 速度2通り**で実機で測った（ズーム1倍＝40px/秒、
80px 引いたらタイムライン秒は 2.000秒、素材の秒は速度倍）。

| 測ったもの | 結果 |
|---|---|
| 本編クリップの左右トリム / 音声・PiP の移動と右トリム / テロップの移動と右トリム（速度1倍・2倍） | **16通りすべて理論値と一致** |
| 2倍速クリップの**分離音声**の右トリム | 素材の秒 **4.000秒**・画面の幅 **80px** ちょうど（1倍でも 2.000秒 / 80px）。「速度で割り戻す」は効いている |
| `pushHistory` を通らない `project` 書き換え | 前回のストア掃引で 94本中6本、すべて正当と確認済み |
| mouseup の「動いたか」判定 | 5箇所すべてに入っている（ドラッグ測定でも余計な履歴は出なかった） |
| 並べ替えの案内線と実際に入る位置 | どちらも `dropIndexAt` から出ている |
| ズーム範囲 / ビートグリッドの本数 | 0.25〜4倍に制限、BPM は `clampBpm` 済み |

**ここまで全部シロ。当たったのは「畳み込み」の側だった。**

**症状 → 原因。** スナップの案内線を画面へ出す `activeSnapGuideTime` は、
ドラッグ状態を `??` で並べた式。ところが `snapGuideTime` を持つドラッグ状態は**5つ**
あるのに、この式には**4つしか並んでいなかった**——`videoOverlayDrag`（PiP クリップの
移動）だけ抜けていた。PiP のドラッグは案内線の位置を**正しく計算している**のに、
それを出す側が読んでいないので、画面には一度も出ない。

**実測（実機・xvfb・同じ条件で音声と PiP を並べる）。**
本編クリップ 0〜4秒 を置いて候補を 0 と 4 に作り、音声クリップと PiP クリップを
どちらも 6秒から同じだけ左へ引いた。

| 引いた量 | 音声クリップ（対照） | PiP クリップ |
|---|---|---|
| −40px（候補から遠い） | なし | なし |
| −84px（4.0秒へスナップ） | **`left: 160px`** | **なし** |
| −244px（0.0秒へスナップ） | **`left: 0px`** | **なし** |
| 離したあとの開始位置 | 4.0 / 0.0 | **4.0 / 0.0（同じように吸い付いている）** |

**落ちる位置は同じなのに、線だけ出ない。** 利用者から見ると PiP だけ「クリップが勝手に
飛んだ」ようにしか見えず、何に揃ったのかを確かめる手段が無い。
しかも「線が出ない」は「スナップしていないから出ない」と**見分けが付かない**ので、
**同じ操作を別のレーンで並べて測る**まで気付けなかった。

**直し方。** 抜けていた `videoOverlayDrag?.snapGuideTime` を式に足した（1行）。
併せて「`snapGuideTime` を持つ状態は全部ここへ並べる」ことをコメントで明示した。

**修正後の実測（同じ表を修正前後で回した）。**

| | 修正前 | 修正後 |
|---|---|---|
| PiP を 4.0秒へスナップ | **なし** | **`left: 160px`** |
| PiP を 0.0秒へスナップ（境界値） | **なし** | **`left: 0px`** |
| PiP が候補から遠い | なし | なし（変わらず） |
| 音声・テロップの移動（3条件） | 160px / 0px / なし | **すべて変化なし** |
| トリムの案内線4種（本編・音声・PiP・テロップ） | 160px | **すべて変化なし** |

**境界値の 0px が出ることを別に確かめてある。** 畳み込みが `||` だったら
「先頭にぴったり合ったとき」だけ線が消える——時刻は 0 が正当な値なので、
`??` でなければならない。

**同種の掃引。** 6つのドラッグ状態を `grep -c` で数え、畳み込みの式に現れる数と
突き合わせた。`rollDrag` は案内線を持たない（隣との境界を動かすだけで揃える相手が
いない）ので対象外。もう1つの列挙する導出 `previewProject` は `trimDrag` だけを見るが、
これは**本編トラックの並びが後続クリップまで組み直される**ためで、音声・PiP・テロップは
自分のドラッグ状態から直接位置を描くので通す必要が無い——**対象外の理由を書いておく**。

チェックリストに
**「種類ごとに分かれた状態を1つの値へ畳み込む導出は、種類を数え上げ切っているか」**
を追加（数え方＝型の数と式の数を突き合わせる、`||` だと 0 が消える、も併せて）。

### 2026-08-17 ストア（6周目の5件目）

**まず不変条件を機械的に測った。** この領域はチェックリストに「ストアの全アクションを
機械的に走査して、`project` を書き換えるのに `pushHistory` を通らないものを洗い出す」と
書いてあるので、そのとおりにした上で、**実機で1操作ずつ動かして数えた**。

| 測ったこと | 結果 |
|---|---|
| `project` を書き換えるのに `pushHistory` を通らないアクション | 94本中 **6本**。すべて正当（新規作成・開く・復元・裏の変換結果・undo・redo） |
| 39操作を実機で実行 → 履歴がちょうど1件増え、取り消し1回で完全に元へ戻るか | **39操作すべて期待どおり**（ID再生成・リンク追従・一括操作を含む） |
| ID を作り直す/消すアクションが参照を張り直しているか | `applyClipReplacement` / `removeLinkedAudioFor` と、`project` が変わるたびに走る購読の同期で網羅されていた |

**ここまでは異常なし。そこで逆を測った**——「同じ値を入れ直したとき」に何が起きるか。
21操作に今と同じ値を渡すと、**15操作が中身を1バイトも変えないまま履歴を1件積んで**いた。
その中に、**中身を実際に壊すもの**が1つ混ざっていた。

**症状 → 原因。** 「全テロップを一括シフト」は
`Math.max(0, o.startTime + delta)` を**1件ずつ**掛けていた。0 にぶつかった
テロップだけがその場に残るので、**テロップ同士の間隔が縮む**。
壊れるのは「動かしすぎたとき」だけなので、行き過ぎたと気付いて同じ量を逆へ適用しても
**元に戻らない**。自動テロップは1件ずつが発話に合わせた時刻を持っているため、
**縮んだぶんだけそのテロップが音とずれたまま**になる。

**実測（実機・xvfb・利用者と同じ操作＝入力欄に打って「逆方向に適用」→「適用」）。**
テロップ3件を 1〜3 / 5〜7 / 9〜11（間隔 **4,4**）に置いた。

| | 修正前 | 修正後 |
|---|---|---|
| 逆方向に3秒 | **0〜2 / 2〜4 / 6〜8**（間隔 **2,4**） | 0〜2 / **4〜6 / 8〜10**（間隔 **4,4**） |
| 移動量 | **-1 / -3 / -3**（バラバラ） | **-1 / -1 / -1**（全員同じ） |
| そのあと正方向に3秒 | **3〜5 / 5〜7 / 9〜11**（間隔 **2,4** のまま） | 3〜5 / **7〜9 / 11〜13**（間隔 **4,4**） |
| ずらした直後の再生位置 4.5秒に出るテロップ | **無し**（間隔が壊れて穴が空いた） | **有り** |

最後の行がいちばん分かりやすい症状で、**画面から1件消える**。

**直し方。** 頭打ちを**要素ではなく移動量の側**に掛けた。動かせる余地は
「一番早いテロップが 0 まで下がれる分」で、そこで止めれば**全員が同じ量だけ動く**。
端で止まったぶんの位置は原理的に戻らないが、**間隔は保たれる**——この2つを分けて考える。
併せて、動かす量が 0 に潰れるとき（0 秒を指定した・これ以上左へ動かせない）と
数値でない値（`1e309` は入力欄を通って `Infinity` になる）では**何も変えない**ようにした。

**回帰。**
- 頭打ちに当たらない普通のシフト（+2秒）は**修正前と同じ数字**: 時刻 7/11/15・移動量 2/2/2。
- 取り消しは修正前と同じく**1回で完全に元へ戻る**（履歴の増分も1件）。
- 単語ハイライトの時刻も本文と同じだけ動く（テロップ開始 − 最初の単語開始 = **0**、
  テロップ終了 − 最後の単語終了 = **0**）。
- 単体26件（境界値: 0 / NaN / ±Infinity / テロップ0件 / 1件だけ / 既に先頭が0 /
  2000件で例外が出ないこと）すべて期待どおり。

**同種の掃引。** 集合を丸ごと動かすアクションは `shiftAllTextOverlays` **1本だけ**だった。
`.map()` の中に頭打ちがある他の2本は別物で、`duplicateClips` の `Math.max(...indices)` は
挿入位置を求めているだけ、`addKeywordSeClips` の `Math.max(0, p.startTime)` は
**新しく作るクリップ**の置き場所なので 1件ずつで正しい。
`Timeline.tsx` の `Math.max(0, original* + delta)` は7箇所あるが、
**どれも1本だけを掴んで動かすドラッグ**なので per-item のままが正しい。

**手を付けなかったもの（数字つきで候補へ）。** 上で見つけた「同じ値を入れ直すと
履歴が1件積まれる」15操作は、`BACKLOG.md` の候補に残した。UIから素で届くのは
**押せば必ず届くボタン系**で、実測（保存直後 → `ExportPanel` の**いま選ばれている方**の
縦横比ボタンを押す）で `isDirty` **false → true**・`past` **2 → 3**・`aspectRatio` は
**9:16 のまま**。閉じるときに「保存されていない変更があります」が出て自動保存も走り出す。
15箇所に散るため、共通の関門を置くかを含めて別途1件として扱うのが妥当と判断した。

### 2026-08-17 音声（6周目の3件目）

**症状 → 原因。** BGM トラックのクリップと PiP の音声を、タイムライン上の位置まで
ずらしているのは `adelay=${ms}|${ms}`。これは「1ch目を ms、2ch目を ms」という
**チャンネルごとの**指定で、**書いた数を超えるチャンネルは既定でずらされない**
（`adelay` の `all` の既定が 0）。

ステレオへ畳むのは**その後ろ**の `audioFormatFor` なので、`adelay` の時点では
**素材のチャンネル数のまま**。5.1ch の素材だと 3〜6ch目（センター・LFE・リア）が
**0秒地点から鳴り始め**、畳んだあとステレオに混ざって出てくる。
チャンネル数を気にしていない利用者からは「置いていない場所で音が鳴る」としか見えない。

**実測（実機・xvfb・利用者と同じ操作＝BGM を足して開始位置を 2秒へ）。**
本編は無音の12秒なので、0〜2秒に音があればそれは BGM が早く漏れている。
対照として同じ素材の 2ch 版でも同じ操作をした。

| 置いたもの | 0〜2秒（無音のはず） | 2〜6秒 |
|---|---|---|
| BGM **5.1ch** | **mean -39.8dB / max -34.8dB** | mean -35.0dB |
| BGM 2ch（対照） | mean **-91.0dB** / max -91.0dB | mean -38.1dB |
| PiP **5.1ch** | **mean -39.8dB / max -34.8dB** | mean -35.0dB |

**症状はもっと具体的に出る。** 素材の 1.0〜1.2秒だけビープにした 5.1ch の BGM を
2秒地点に置くと、書き出しで鳴る区間は（silencedetect -50dB）:

| | 鳴る区間 |
|---|---|
| 修正前 | **0.99〜1.21秒** と **2.99〜3.21秒**（2回） |
| 修正後 | **2.99〜3.21秒**（1回だけ） |

ずれなかった4チャンネルが、**2秒早いこだま**として重なっていた。

**直し方。** `adelay=${ms}:all=1`（最後に書いた遅延を残りのチャンネル全部に使う）。
数を数えて `|` を並べる形は採らなかった——`probeAudioChannels` は失敗しても
`undefined` を返す作りなので、**チャンネル数が分からなかった素材だけ穴が残る**。
`all=1` なら数を知らなくてよい。

**修正後の実測。** 0〜2秒は **-91.0dB**（デジタル無音）。鳴り始めは silencedetect で
**1.9989秒**。0〜1.95秒は 0.05秒刻みで測ってすべて max **-91.0dB** で、
1.95〜2.00秒だけ max -69.5dB が残るが、これは AAC が立ち上がりの窓で出す前鳴りで、
2ch の対照でも同じ位置に出る。

**回帰。** 音声の組み方11通りを修正前後で並べ、**5.1ch の1行以外は md5 が完全に同一**:

| 組み方 | 修正前 → 修正後 |
|---|---|
| BGM ステレオ / モノラル / 先頭(0秒)から / フェード1秒 / 音量1.5倍・トラック0.8 / 速度2倍 / ダッキングON / 同じトラックに2本 / PiP ステレオ音声 / 音量正規化 | **10通りとも md5 変化なし** |
| BGM **5.1ch**（今回の対象） | `b8ab726e…` → **`fd831fb1…`** |

実機の 2ch BGM の書き出しも **md5 まで完全に同一**（`d8b981a8…`）。
単体21件（生成される `adelay` の形＝0秒・端数・負値・3600秒・PiP、および
1ch/2ch/6ch/8ch の実挙動と「遅延0なら修正前と同じ値」）はすべて期待どおり。

**測り方を1回間違えた。** 単体Aで `adelay` を出てきた順に拾ったところ NG が4件出たが、
これは**PiP の枝が BGM トラックより前に積まれる**ためで、実装ではなくテストの
取り違えだった。枝のラベル（`atrk0_0` / `pipaudio0`）で見分ける形に直したら全部通った。
単体Bはラベルに依存しない測り方だったので最初から正しく、**片方が正しいことが
もう片方の誤りを見つける手がかりになった**。

**同種の掃引。** チャンネルごと・要素ごとの並びを外部ツールへ渡しているのは
`adelay` の2箇所だけで、両方直した。他の音声フィルタ（`amix` / `asplit` /
`acrossfade` / `apad` / `atrim` / `volume` / `afade` / `atempo` /
`sidechaincompress`）は**個数が要素に依存しない**引数しか取らない。
波形画像の枝は先頭で `aformat=channel_layouts=mono` を通すのでチャンネル数に依存せず、
プレビュー用の変換の `-ac 2` は 1ch/3ch以上の扱いが既に入っている。

チェックリストに
**「外部ツールへ『要素ごとの並び』で渡す引数は、要素の数が素材によって変わらないか。
足りない分は既定で『何もしない』になる」**を追加。

### 2026-08-17 テロップ・字幕（6周目の2件目）

**症状 → 原因。** テロップには文字が**2つ**ある。利用者が打ち込む `text` と、文字起こしが
返した `words`（1語ずつの時刻つき）。単語ハイライト（カラオケ）がONのとき、
**画面も書き出しも `words` だけ**を描いていたので、**本文を打ち直しても何も変わらなかった**。

自動テロップとAIショートの発言テロップは**既定でハイライトON**なので、
**文字起こしから作ったテロップは全部これを踏む**。聞き間違いを手で直すのは
その機能を使う一番の理由なのに、そこが黙って無視されていた。

**実測（実機・xvfb・利用者と同じ操作＝パネルの入力欄に打ち直す）。**
対照として、同じ操作をハイライトOFFのテロップにも掛けた。

| | ストアの `text` | 画面の文字 | 書き出しの md5 |
|---|---|---|---|
| ハイライトON / そのまま | こんにちはせかいです | こんにちはせかいです | `262c7d72…` |
| ハイライトON / **打ち直した** | こんにちは**世界**です | **こんにちはせかいです** | **`262c7d72…`（打つ前と同一）** |
| ハイライトOFF / そのまま（対照） | こんにちはせかいです | こんにちはせかいです | `5e368e9e…` |
| ハイライトOFF / 打ち直した（対照） | こんにちは世界です | こんにちは**世界**です | `7741bbc4…`（変わる） |

対照が追従していることを先に見てから本命を測った——**0件や「変わらない」は
「守れた」とも「そもそも測れていない」とも読めてしまう**ため。

**直し方。** 「打ち直したら `words` を捨てる」は採らなかった。捨てると時刻が失われ、
**取り消しても戻らない**。代わりに `@shared/captionWords.ts` に
**「その単語列はまだ本文を綴っているか」**の判定を1つ置き、画面（`PreviewPlayer`）と
書き出し（`assSubtitle`）が**同じ関数を呼ぶ**形にした。データは残るので、
取り消して元の文字に戻せば色付きもそのまま戻る。

判定は**空白まで含めて厳密**にした。改行を1つ入れただけでも `words` から描くと
**その改行が出ない**ので、「打ったのに出ない」が小さく残る。
色が付かないのは画面で見えるが、打った文字が出ないのは見えない——**見えない方を残さない**。
作成時は3経路とも `words` をそのまま連結したものが `text` になっている
（`whisperService.buildWordSegment` / 自動テロップ / AIショートの発言テロップ）ので、
打ち直していない限りこの判定は必ず通る。

**修正後の実測。**

| | 修正前 | 修正後 |
|---|---|---|
| ハイライトON / そのまま | `262c7d72…` | **`262c7d72…`（完全に同一）** |
| ハイライトON / 打ち直した | `262c7d72…` | **`7741bbc4…`** |
| ハイライトOFF / そのまま | `5e368e9e…` | 変化なし |
| ハイライトOFF / 打ち直した | `7741bbc4…` | 変化なし |

**検算。** 打ち直したカラオケテロップの出力（`7741bbc4…`）は、**同じ文字を
ハイライトOFFで焼いたものと md5 まで一致**した。「それらしく変わった」ではなく
「本来あるべきものと1バイトも違わない」ところまで確かめられている。

**回帰。**
- 長いカラオケテロップ（全角48文字・9:16 720p・折り返しあり、打ち直していない）は
  **md5 が完全に同一**（`e94d2cdf…`）。前回この領域で直した「カラオケも折り返す」は無傷。
- 打ち直しを**取り消す**と色付きが戻る（画面の span 数 **3 → 0 → 3**）。
  修正前は打っても span 数 3 のまま＝画面が変わらなかった。
- 単体22件（境界値: `words` が undefined / 空配列 / 本文も単語も空 / 空白だけ /
  時刻が NaN・Infinity / `style` ごと欠け / `text` が undefined）はすべて期待どおり。

**測り方を1回間違えた。** 修正前の数字を採るとき `git stash push` に**未追跡の新規ファイル**を
混ぜたためコマンドごと失敗しており、「修正前」として測ったつもりの回が**修正後のコードで
走っていた**。取り消しの span 数が前後で同じ値だったので気付けた——
チェックリストの「テストが動いていること自体を先に確かめたか」がそのまま当たった。

**同種の掃引。** `words` を描いているのは画面と書き出しの2箇所だけで、両方とも
共通の判定を通した。`keywordSe.detectKeywordSeMatches` も `words` を読むが、
**キーワードの照合は `overlay.text`（打ち直した方）で行い、`words` は鳴らす時刻を
細かくするためだけ**に使う（見つからなければテロップ先頭に倒れる）ので対象外。
同じ形（利用者が編集できる値と、機械が作った派生の値が並んでいる）を型から洗うと
`customPosition` ⇔ `position` と `linkOffset` ⇔ `startTime` があるが、
どちらも**書き込む側で辻褄を合わせて済んでいた**（位置を選び直すと `customPosition` を
落とす／`startTime` を動かすと `linkOffset` を計算し直す）。

チェックリストに
**「同じ内容を2つの形で持っているとき、描く側が『利用者が打つ方』ではなく
『機械が作った方』だけを読んでいないか」**を追加。

### 2026-08-17 書き出しパイプライン（6周目の1件目）

長く残っていた候補「細切れに分割したクリップを書き出すと映像だけ音声より長い」を落とした。
前の2ロールが「断片ごとの丸めが積み上がる」筋を実測で否定し、
**「余分な4フレームは `trim` より後ろで増えている」**まで詰めてくれていたので、そこから測った。

**症状 → 原因。** 無音カットで6断片になったタイムライン（合計 24.999411秒、断片ごとに
`round(尺×30)` すると 150/150/120/120/120/90 = **750枚**）を書き出すと、
映像 **754枚 / 25.133984秒**に対し音声 **24.999000秒**。

`trim` は入力の時刻を**そのまま通す**ので、切り出し位置がフレーム境界から外れていると
（無音カットの境界は `silencedetect` の生値なので**必ず外れる**）その枝の先頭が
**pts 0 ではなく pts 1** から始まる。`concat` は前の枝の**終端の時刻**で次をずらすため、
繋ぎ目ごとに**1フレームぶんの隙間**が空き、CFR で詰めるエンコーダが複製フレームで埋める。

**直し方を2回間違えた。実測していなければ両方とも通していた。**

| `fps=30` だけ | 754枚（変わらず） | — |

  確定済みなのだから、時刻は「n枚目 = n/30秒」と**置き直して**しまうのが正しい。

**検算。** 輝度の段差で繋ぎ目の位置を数えたところ、**301 / 422 / 663 → 300 / 420 / 660**

### 2026-08-16 解析系（5周目の9件目）

シロだったもの:

| 当てた項目 | 結果 |
|---|---|
| 解析が返すのは素材の秒。画面に出す前にタイムラインの秒へ直したか | 無音カット・フィラーカット・テキスト編集は `toTimelineSeconds`、自動テロップは `tc.start + (seg.start - inPoint) / speed` を通している |

**既存のチェックリスト項目そのもの**だが、中身は「**直したのは共通モジュールだけで、

通っているのに、**長尺スキャンの `buildWindowCandidates` は自前で平均・標準偏差を数えており、
絶対値のフロアしか持っていなかった**。

実機（33秒の録画・地の声 -44.08dB・8〜10 / 16〜18 / 24〜26秒に山 -41.0dB）で
`scanLongFormWindows` を走らせた実測:

|---|---|---|

内容は頭の3秒しか違わない。録画ボタンを先に押して数秒黙っているだけで、長尺スキャンが
**候補を1件も返さなくなる**。統計を並べると、ばらつき **1.2 → 12.0**、しきい値
**-41.5 → -37.6** と、素材の最大音量（-41.0）を追い越していた。

単体テストでも期待値を2件間違えた（頭10秒を暗騒音にすると 8〜10秒の山**そのもの**が

テスト側の誤りで、実際の出力と突き合わせて直した。

単体は境界値込み17件（空・全部デジタル無音・NaN と Infinity のみ・1件だけ・平坦な素材・

外していないか**」を当てた。当たった。

`AUDIO_FORMAT` は形式の交渉を止めるために `sample_fmts=fltp` を固定している。ところが
swresample は畳み込みの行列が 1 を超えるとき**整数形式なら行列を正規化する**
(`rematrix_maxval` の既定 1.0)のに、**浮動小数では既定が無制限**で正規化が外れる。
つまり `fltp` の固定が、止めたかった交渉とは無関係の**畳み込みの安全装置**まで外していた。

実測（同じ音を 2ch と 5.1ch の2ファイルにして、実機で書き出す）:

| | 修正前 | 修正後 |
|---|---|---|
| 5.1ch の BGM | mean **-7.4 dB** / peak **-4.1 dB** | mean **-15.1 dB** / peak **-11.8 dB** |
| 2ch の BGM（回帰） | -18.1 dB / -14.9 dB | **md5 まで一致** |
| モノラルの BGM（回帰） | -15.1 dB / -11.9 dB | **md5 まで一致** |

**割れている**ことも確かめた。無相関な 5.1（現実の素材に近い）を通すと、修正前は
mean -9.7 dB・peak -0.5 dB で **143サンプルが 0dBFS に張り付く**。大きめの 5.1 では
**240,000サンプル**。修正後はどちらも張り付きゼロ。

同種の掃引で**試聴用プロキシにも同じ穴**が見つかった。`-ac 2` の裏も同じ swresample で、
しかもここを通るのは AC-3 / DTS のように**そのまま再生できない音声＝まさに 5.1 を運ぶ形式**。
実機で AC-3 5.1 の素材を取り込んでプロキシを作らせたところ、修正前は
mean **-13.1 dB**・peak **0.0 dB**・**34サンプル張り付き**、修正後は **-18.7 dB / -5.9 dB**・
張り付きゼロ。1ch は既存のモノラル経路、2ch は素通りで、どちらも分岐が変わらない。

検算（「そもそも測れていたか」を疑って3点）:

1. **修正後の値は自分で決めた数字ではないか** — `sample_fmts` を `s16` にしただけの
   参考値と突き合わせた。無相関な 5.1 で **-17.4 / -8.1 dB**、大きい 5.1 で
   **-4.1 / -1.0 dB** と、修正後の値と**完全に一致**。ffmpeg 自身の標準の畳み込みに
   戻しただけであることを裏取りした
2. **相関のある音だけの話ではないか** — 6チャンネルすべて別々の乱数にした素材でも
   同じ 7.7 dB の差が出た
3. **測定器の確認** — lavfi の `sine` はピーク **-18.1 dB** しか出ないので、
   最初に作った「素材」がそもそも静かだった。フルスケールのサイン波が -21.1 LUFS と
   出た時点で気付き、`volume` で狙った値へ合わせ直してから測り直している

**「ラウドネス正規化が -14 LUFS に届かない」は候補に残した**（`BACKLOG.md`）。
既定ONで画面には「YouTube推奨値」と書いてあるのに実測 **-16.1 LUFS**、
音の幅も **9.5 → 6.6 LU** に潰れる。原因は `loudnorm` の1パス使用で、
ズレは音の幅に比例する（LRA 0.0 → -14.0 / 3.0 → -13.8 / 9.5 → -16.0）。
2パスなら **-13.2 LUFS・LRA 9.5 のまま**になることまで確認済みだが、測定パスに
書き出しと同じ音声グラフが要るため `exportProject` の組み立てを切り出す必要があり、
バグ狩り1件には収まらないと判断した。

### 2026-08-15 プレビュー再生（4周目の1件目）

この領域は「PiPの余白」「再生中の編集で先頭へ戻る」「開いたときにプロキシが作られない」を
既に直してある。今回は**まだ当てていない眼鏡**として
「**DOM要素に命令で書き込む再生パラメータが、読み込むときにしか設定されていないのでは**」
を当てた（既存の「設定を足したらプレビューにも効かせたか」は**仕組みが無い**話で、
こちらは**仕組みはあるのに書き込む場所が読み込み経路の中にしかない**という別の失敗）。

`playbackRate` を書いているのは `loadClipForTime` だけで、これは**読み込み直しかシークの
ときしか走らない**。つまり**いま映っているクリップの速度を変えても要素は古い速度のまま**。
しかも再生位置の計算 `globalTime = start + (currentTime - inPoint) / speed` は新しい速度を
すぐ使うので、**速度を上げたのに再生位置がゆっくりになる**という逆向きの見え方になる。
シークすれば直るので、再現条件が掴めないまま「たまに変」で終わる。

実測（**実機**・利用者と同じ操作。20秒の素材1本、1秒ぶん再生して進みを測る。同じ probe を修正前後で）:

| 場面 | 修正前 rate / 再生位置の進み | 修正後 rate / 再生位置の進み |
|---|---|---|
| ① 等倍で再生中（対照） | 1 / 1.00 秒/秒 | 1 / 1.00（同じ） |
| **② 再生したまま2倍にする** | **1 / 0.50** | **2 / 1.00** |
| ③ 止めてシークし直してから再生 | 2 / 1.00 | 2 / 0.98（同じ） |
| **④ 止めて4倍にしてから再生（シークなし）** | **2 / 0.50** | **4 / 1.00** |
| ⑤ 回帰: 再生しながらテロップを1つ足す | 1 / 1.02 | 1 / 1.00（乱れなし） |

素材の秒の進みも 1.99 / 3.97 と理論値（速度そのもの）に一致した。
④の方が普通の手順（止める→速度を選ぶ→再生）で、**そちらも壊れていた**。

直しは `timedClips` の effect（既に「今の配列の同じクリップへ差し替える」ために存在する）で、
**速度が変わっていたら `playbackRate` だけ入れ直す**。読み込み直しはしない——
`currentTime` を入れ直すことになり音が飛ぶ（既存コメントが明示している）。

**代入の定義域も実測してからガードを足した。** Chromium は範囲外を**代入した時点で投げる**:
`-1` / `16.1` / `0.0624` は `NotSupportedError`、`NaN` / `±Infinity` は `TypeError`、
通ったのは **0.0625〜16 ちょうど**（0.0625 と 16 は通り、0.0624 と 16.1 は投げる）。
代入は `useEffect` の中なので、投げると**その場で React のエラー画面**——
`speed` は保存ファイル由来で `normalizeLoadedProject` は数値の範囲まで見ていないため、
**速度が壊れた `.veproj` を開いただけでアプリが使えなくなる**。
`toPlaybackRate()` を `lib/playbackRate.ts` に置き、代入する3箇所すべてを通した。

単体26件（UIが出す9段階はそのまま、境界値は 0.0625 ちょうど / 0.0624 / 0.05 / 16 ちょうど /
16.1 / 100、壊れた値は 0・負・NaN・±Infinity・undefined・null・文字列・真偽値、
そして**どんな入力でも 0.0625〜16 に収まる**こと）。期待値の根拠は上の実測値そのもの。

grep 掃引で**同種をもう1件見つけて直した**。`playbackRate` の代入は3箇所あり、
**ぼかし背景の映像には最初から1つも無かった**。実測（4倍速）:

| | 修正前 | 修正後 |
|---|---|---|
| 背景の `playbackRate` | **1**（本編は 4） | **4** |
| 本編と背景のズレ | **0.29 秒** | **0.12 秒**（等倍時の 0.16 と同程度） |

背景が追いつけていたのは「0.3秒ずれたら合わせ直す」仕組みに引きずられていたからで、
つまり**再生中ずっとシークし続けていた**。等倍では両方 1 なので誰も気付かない。

**シロと判断したもの（次回同じ当て方をしないための記録）**:
- **速度を変えても音は消えない**。UIが出す 0.25〜4 の全段階で、本編の `<video>` に
  AnalyserNode を挟んで実効値を測ったところ **RMS 0.088 前後で一定**（muted も false）。
  Chromium が高速再生で音を落とす、という想定は外れだった。
  **測り方の失敗を1件記録**: 最初は5秒の素材に `duration: 10` と宣言して測ったため、
  速度2以上で `currentTime` が 5.00（素材の終端）に張り付き **RMS 0** になった。
  「高速だと無音になる」と読み違えるところで、`ended` と `currentTime` を併せて出して初めて
  測定の失敗と分かった。20秒の素材に替えて測り直した。
- `volume` / `muted` / `currentTime` は最初から `[その値]` を依存に持つ effect に分かれており、
  設定を変えればその場で効く。
- `SourceViewer` のシャトル速度は `Math.min(4, ...)` と `Math.abs` で 1〜4 に収まるので
  定義域を外さない。
- PiP（`VideoOverlayClip`）は型に速度を持たないので、そもそも入れる値が無い。
- **トランジションはプレビューに一切出ない**（`PreviewPlayer.tsx` に `transition` の語が
  1つも無い）。書き出しは `xfade` で前後を重ねるので、**タイムライン/プレビューの尺と

### 2026-08-15 音声（ミックス・ダッキング・正規化・分離音声）（4周目の3件目）

チェックリストのうち音の枝に当たるもの——「利用者が受け取る成果物の形式を処理系の交渉結果
まかせにしていないか」「プレビューと書き出しで別のエンジンを使う設定はパラメータを共通化

**この領域は既に3周してあるので、今回は読むより先に測った。**

まず、これまで一度も数字で確かめていなかった3つを実測してシロを確認した。

- **合成の規則**（`amix=...:normalize=0` は本当に素通しで足しているか）:
  同じBGMを2トラックにすると mean **-24.1 → -18.1 dB**、max **-20.7 → -14.8 dB**。
  理論値 +6.02 dB に対して +6.0 / +5.9 dB。シロ。
- **フェードのカーブ**（`afade` の既定 `tri` と `fadeGainAt` の直線が一致するか）:
  フェードイン2秒の定常比が、窓の中心 0.55 / 1.05 / 1.55 秒で
  **-11.2 / -5.6 / -2.2 dB**。理論値 -11.2 / -5.6 / -2.21 dB と一致。シロ。
- **ラウドネス正規化**（UIが謳う「YouTube推奨値」に本当に乗るか）:

  OFFでは素材の値をそのまま再現。目標 -14 に対して 0.1 LU 以内。シロ。

当たったのは4つ目、**チャンネル数の変換**。形式は `AUDIO_FORMAT` で固定してあるのに、
**固定する途中の倍率**がプレビューと書き出しで違っていた。

- 書き出し（ffmpeg / swresample）は、モノラルを左右へ **`1/√2` = -3.01 dB** で配る。
- プレビュー（Chromium）は Web Audio の規定どおり **等倍**で左右へ複製する。

実測（同じ 200Hz・同じ振幅の波形を mono/stereo の2ファイルにして、同じ企画で書き出し）:

| | モノラル素材 | ステレオ素材 | 差 |
|---|---|---|---|
| 書き出し mean（修正前） | **-30.1 dB** | -27.1 dB | **3.0 dB** |
| 書き出し max（修正前） | **-27.1 dB** | -24.0 dB | **3.1 dB** |
| 書き出し mean（修正後） | -27.1 dB | -27.1 dB | **0.0 dB** |
| 書き出し max（修正後） | -24.0 dB | -24.0 dB | **0.0 dB** |
| プレビュー実効値（`<audio>` 要素 / `OfflineAudioContext`） | 0.04427 | 0.04427 | 0.0 dB |

**効くのは全体の音量ではなく「素材どうしの比」。** モノラルのナレーションとステレオのBGMを
画面で耳で釣り合わせても、書き出すとナレーションだけが 3dB 引っ込む。しかも
**ラウドネス正規化をONにしても直らない**（混ぜ終わった全体を -14 LUFS へ揃えるだけで、
中の比は動かないため）。尺もチャンネル数もサンプルレートも合っているので、
ffprobe で素性を見ていても気付けない。

直し方は、**1ch と分かっている素材にだけ** `aresample=...:rematrix_volume=√2` を前置きする
（規則は `src/shared/audioUpmix.ts` に1箇所置き、書き出しとプレビュー用変換の両方が読む）。
`rematrix_volume` は変換行列全体に掛かるので、**ステレオに通すと逆に +3dB 持ち上がる**
（実測 -24.1 → -21.1 dB）。チャンネル数は書き出しの直前に、タイムラインが実際に使う
素材だけ ffprobe で数える。答えが返らなければ**補正しない側に倒す**（書き出しを止めない）。

単体（ffprobe の返り値を差し替えて境界値まで）: 1ch=補正あり / 2ch・6ch・0ch・-1ch・NaN・
Infinity・1.5ch・欠落・文字列 "1"・ffprobe失敗=補正なし、かつ全ケースで形式固定は残る。11件OK。

検算（「そもそも測れていたか」を疑う）: 左右を別々に測り直した。
モノラル素材 → L **-24.0** / R **-24.0**（等倍で複製）。
左だけに音を入れたステレオ素材 → L **-24.1** / R **-91.0**（**分離は保たれている**＝
「全部同じ数字になっただけ」ではない）。出力はいずれも aac / 48000 / 2ch のまま。

回帰: 2トラック合成 +6.0 dB・フェード -11.2/-5.6/-2.2 dB・正規化 -14.0 LUFS はいずれも
修正前と同じ。ステレオ素材3本の書き出しは 15.000秒 / 450フレーム、音声 15.000秒 / 48000 / 2ch で
`5bd72be` の尺固定も生きている。

- **プレビュー用の変換**（`previewProxyService` の `-ac 2`）が同じ規則で -3dB していた。
  つまり**同じモノラルでも、H.264 の素材はそのまま再生されて等倍、HEVC の素材はプロキシ経由で

  修正後 **-23.7 dB**（AAC の誤差ぶんを含めて等倍）。同じ共通モジュールを通して直した。

チェックリストには「チャンネル数・サンプル形式などの暗黙の変換を処理系まかせにしていないか。
画面と出力で変換規則が違えば、素材によってだけ音量が変わる」を追加した。既存の

### 2026-08-15 テロップ・字幕（4周目の2件目）
この領域は BorderStyle・エスケープ・縦余白・仮想キャンバス・固定倍率・折り返し・左右余白を

どちらもキャンバス1920基準に換算。1文字「あ」・背景ON・不透明）:

| 80 | 32.02 | **6** → 32 | 12.01 | **6** → 12 |

`\xbord32\ybord12` で **96x64px** と、どちらも理論値ぴったり）。

ASS に出る `\xbord`/`\ybord` が理論値と一致し `\bord` を書かないこと、小数の2桁丸め、

②画面側の実測値が修正前と完全に一致することを確かめ、「出力を画面に合わせた」のであって

### 2026-08-15 書き出しパイプライン（4周目の1件目）
巡回表が3周したので4周目。この領域は fps・音声形式・PiP余白・画素形式・**音声側の尺揃え**を
既に直してあるので、**まだ当てていない眼鏡**——というより、
チェックリストの「映像と音声を別々に連結するなら1本ごとに同じ尺ちょうどへ揃えたか」の
**見つけ方をそのまま実行した**（「片方に尺を渡していて、もう片方に渡していない」ものを見る）。
音声の枝には `apad`+`atrim=0:<尺>` があるのに、**映像の枝には何も無かった**。

見つけたのは、**素材の映像が音声より短いと、クリップを並べるほど映像が前へずれる**こと。
尺の判定に使う `duration` は**コンテナ全体の長さ**なので、末尾に音声だけが残る録画物では
クリップの尺として渡した秒数ぶんの映像が**そもそも無い**。映像と音声は別々に `concat`
するので、足りない分が1本ごとに累積する。前回直した音声側の**鏡像**。

実測（`exportProject` を本物の ffmpeg で走らせ、`ffprobe` で数えた。
素材は**映像4.000秒(120フレーム)・音声5.000秒**、コンテナは 5.000秒。これを尺5秒で3本）:

| | 修正前 | 修正後 |
|---|---|---|
| 映像のストリーム長 | **12.000秒** | **15.000秒** |
| 映像のフレーム数 | **360** | **450**（理論値 15×30fps） |
| 音声のストリーム長 | 15.000秒 | 15.000秒 |
| 映像と音声の差 | **3.000秒** | **0.000秒** |
| 音声のビープ位置 | 0 / 5 / 10秒（正しい） | 同じ |
| 1本だけ | 映像4.000秒 | 映像5.000秒・150フレーム |

つまり修正前は、2本目の映像が**1秒**、3本目が**2秒**先行し、**最後の3秒は絵が無かった**。

直しは映像の枝に `tpad=stop_duration=<尺>:stop_mode=clone,trim=duration=<尺>` を挟む1本。
**足りない分を埋める処理と長すぎる分を切る処理を対で**置くのは音声側と同じ考え方で、
埋めるのは**最後のフレームのまま**（黒で埋めると、足りないことを隠してしまう）。

単体151件（組み立てた `-filter_complex` を偽 ffmpeg で捕まえ、映像の枝ごとに
`trim` と `tpad` の秒数が理論値 `(outPoint-inPoint)/speed` と一致するか・`tpad` が `trim` の
前にあるか・`stop_mode=clone` かを照合。本数 1/3/8、速度 0.25/0.5/1/2/4、

壊していないこと）。**修正前のコードに当てると 151件中 129件が落ちる**。

**回帰**: 映像と音声の長さが同じ普通の素材では、通常3本・クロスフェード3本・2倍速3本の
いずれも出力が**md5 まで完全に同一**（`6c03a027…` / `6d027e70…` / `7aa40a57…`）。

**結合（実機）**: 利用者と同じ操作（「動画」ボタンで取り込む → タイムラインに3本 → 書き出し）で
**映像 15.000秒・450フレーム / 音声 15.000秒**。アプリが認識した素材の長さは 5秒だった。

**検算**: 期待どおりに直ったので、①埋めた区間の**画素を数えた**——4.5/9.5/14.5秒の平均色は
**B=253.4** で素材の青（B=254.0）と同じ、つまり黒で埋めてはいない。
②修正前のコードで同じ単体を流し、129件が落ちることを確認した。

**直し方の失敗を1件記録**: 最初は `trim` のあとに `setpts=PTS-STARTPTS` を付けていた。
尺は 12.000 → **15.040秒**になり一見直ったように見えたが、**フレーム数を数えると 450 に対し
376 しか無かった**（`nb_frames` を見ていなければ通していた）。最小の再現で切り分けると、

### 2026-08-14 音声（3周目の3件目）
この領域は `aformat`・`atempo` の連鎖・フェードの正規化・分離音声・音量つまみ(100%超)を
既に直してあるので、**まだ当てていない眼鏡**（「見え方を変える設定をプレビューにも

**直せる大きさのバグは見つからなかった。** 見つけた1件は書き出しにしか無い機能の話で、

**見つけたもの(候補へ): ダッキングがプレビューに一切効かない。**
実測（**実機**。クリップ音量0.8・トラック音量1.5・フェード1秒のBGM。
`el.volume` は 1 で頭打ちになるので、アプリが作る `GainNode.gain` を捕まえて読んだ）:

| 時刻 | ダッキングOFF | ダッキングON |
|---|---|---|
| 0.0秒 | 0（フェード開始） | 0 |
| 0.5秒 | 0.60 | 0.60 |
| 1.0〜3.0秒 | **1.20** | **1.20** |
| 5.5秒 | 0.60 | 0.60 |

つまり画面側は**ON/OFF で完全に同一**。一方、同じ構成を書き出すと BGM の帯域(1kHz以下)が
mean **-24.1dB → -27.5dB**（**-3.4dB**）下がる。Web Audio にサイドチェーン入力が無いため、
本編音声を `AnalyserNode` で実時間に測って `GainNode` を動かす作りが要る
（しかも `createMediaElementSource` は戻せないので「必要なときだけ付け替える」形にする）。
**今回の1件には大きすぎる**と判断した。

**シロと判断したもの（次回同じ当て方をしないための記録）**:
- **5.1ch の素材**: `adelay=2000|2000` は**2チャンネルしか遅らせない**ので、最小の再現
  （`-af` で直接掛ける）では 5.1 のSEが **0秒と2秒の二重に鳴る**。ところが**アプリの
  グラフでは踏まない**——枝の末尾に `aformat=...channel_layouts=stereo` があり、
  複合フィルタの形式交渉が**上流までステレオを伝える**ため `adelay` に届く時点で 2ch に
  なっている。実測（5.1のSEを2秒に置いて書き出し）: 無音 0.00〜2.00 / 音 2.00〜3.00 で
  **ステレオ素材と同じ**。`all=1` を足しても出力は変わらない（ステレオでも同一）。
  **「最小の再現で壊れた」ことは「アプリで壊れている」ことを意味しない。**
- **フェード・音量・速度**: 画面側は共通モジュール(`fadeGainAt` / `audioClipGain`)を
  通しており、実測でも 0.5秒地点 0.60 = 1.20 × 0.5 と理論値どおり。書き出しの
  `afade`(atempo の後ろ)と同じ時間軸。
- **枝ごとの形式固定**: 本編・BGM・PiPの音声いずれも末尾に `aformat` があり、
  `amix` の手前で 48kHz/ステレオに揃っている（グラフを実際に出力して確認）。
- **履歴の合体**: 音量・フェード・トリム・開始位置のスライダーはすべて合体キー付きの
  `pushHistory`（`trackVolume:` / `audioVolume:` / `audioFade:` / `audioTrim:` /
  `audioStart:`）で、1回の調整で履歴が埋まらない。
- **PiPの音声**: `adelay` で絶対位置に置いてから `amix` するので、1本ごとの尺の差が
  累積しない（前回直した本編の `concat` とは別の作り）。

**測り方の失敗を1件記録**: ミュートが `GainNode` 経由でも効くかを確かめようとして、
`AudioContext.prototype.createGain` を差し替えて `AnalyserNode` を挟んだが、
**ミュートしていない状態でも信号のピークが 0** のままだった（＝何も測れていない）。
アプリの接続順と差し替えの順序が合っていない。ピークで測るなら
**「鳴っているはずの場面で 0 でないこと」を先に確かめてから**本命に入ること。

### 2026-08-14 テロップ・字幕（3周目の2件目）

**libass は空白でしか行を分けない**ため、空白の無い日本語は1行のまま伸び続け、
フレームの外へ出て左右が切れる。画面(CSS)は文字単位で折り返すので**収まって見える**。
併せて、折り返す幅そのものも食い違っていた——画面は CSS の `left/right: 5%`、
書き出しは ASS の `MarginL/R=40`(1920キャンバスの **2.08%**)。

実測（**実機**・利用者と同じ操作。16:9 プロジェクトに既定スタイルのテロップを1枚置き、
プレビュー枠を `capturePage`、同じプロジェクトを 720p で書き出してフレームの画素を
**同じ数え方**で数えた。文字は全角の連続）:

| テロップ | | 修正前 | 修正後 |
|---|---|---|---|
| 全角200文字 | 画面 | 5行（インク 5.24%〜94.52%） | **同じ** |
| 全角200文字 | 書き出し | **1行**（インク **0%〜100%** = 両端が切れて読めない） | **5行**（13.75%〜86.25%） |
| 全角45文字 | 画面 | 2行 | **同じ** |
| 全角45文字 | 書き出し | **1行** | **2行** |

**最小の再現**でも確かめた（黒画像に ASS を焼くだけ）: 全角200文字 → 1行・0%〜100%、
**ゼロ幅空白(U+200B)を1文字ごとに挟んでも 1行のまま**、英語(空白区切り)は3行に折り返す。
つまり回避策として空白系の文字を挟むのは効かない。

直し方は2つで1つ:
1. 左右の余白を `@shared/textStyle` の `TEXT_MARGIN_H_RATIO` に1本化（縦と同じ形）。
   CSS からは数字を消し、ASS の `MarginL/R` は `round(幅 × 比)` で出す。
2. **libass が折り返せない並びだけ、こちらで `\N` を入れる**（`wrapAssLines`）。
   空白で区切られた並びは libass 自身が折り返せるので触らない——先回りして割ると
   二重にかかって不自然な位置で切れる。幅は全角1em・半角0.5em の**見積もり**
   （main プロセスに字送りを測る手段が無いため。実フォントより広めに見積もり、
   **切れるより手前で折る**側へ倒す）。

単体40件（折り返しの行数と「上限以下」であること・文字が欠けないこと、半角は2倍入ること、
空白区切りは単語の途中で割らないこと、元の改行を保つこと、境界値は
空文字・ちょうど上限・上限+1・0・負・NaN・Infinity・0.5em・1万文字・絵文字、
そして ASS 側で MarginL/R が比から出ること・改行数が理論値
`ceil(200 / floor((幅-余白×2)/文字サイズ))-1` と一致すること・短いテロップには改行を
入れないこと・背景ありは箱と文字の改行位置が同じこと・タイプライター/自由位置でも
折り返すこと・別解像度でも比であること）。

**検算**: 期待どおり直ったので、①**回帰**として短いテロップ（「こんにちは世界」）を
修正前後の ASS で焼き比べた——**画素数110・x=284〜355・y=320〜329 と完全に同一**
（中央寄せの短い行は余白の変更に影響されない）。②**測り方の失敗を1件記録**:
最初の実測はプロジェクトが既定の 9:16 のままなのに書き出しだけ 16:9 で回しており、
**枠の比が違うものを見比べていた**（画面 132.97x236.38 に対し出力 1280x720）。
`setAspectRatio('16:9')` を入れて測り直した。

同種を洗ったところ、**libass に文字を渡すのは書き出しの `subtitles=` 1箇所だけ**。
サムネイルの文字入れは renderer の canvas に `fillText` していて折り返しを持たないが、
**その canvas 自体が成果物**（画面 = 出力）なので食い違いは起きない。

**残りを候補に1件記録**: 見積もりが実フォントより広いぶん、行が必要より早く折れる。
実測では libass の全角1文字は **0.81em** で、200文字の出力インク幅は画面の 89.29% に対し
**72.5%**（行数はどちらも5行で一致）。字送りを実測して渡す仕組みが要るため今回は見送った。

### 2026-08-13 AI連携（2周目の10件目）

### 2026-08-13 解析系（2周目の9件目）
この領域は無音検出のしきい値・BPMの手直し導線を既に直してあるので、
**まだ当てていない眼鏡**（「自動検出の結果を画面に出すなら、外れていたときに手で直せる
導線があるか」を**一歩進めて「そもそも結果が画面に見えているか」**）で見直した。

見つけたのは、**スマートクロップ（被写体の自動検出）の結果が、画面に一切出ていなかった**こと。
`.preview-frame video` は `object-fit: contain` 固定で、**`fillCrop` も `cropCenter` も
プレビューでは読まれていない**。書き出しとサムネイル生成は `scaleToFrameFilter` で
切り抜くので、**画面と出力が別物**になる。

実測（**実機**・利用者と同じ操作。9:16 プロジェクトに 1280x720 の素材

プロジェクトを 720p で書き出してフレームの画素を数えた）:

### 2026-08-13 プレビュー再生（2周目の8件目）
この領域は PiP の余白を既に直してあるので、**まだ当てていない眼鏡**
（「同期」＝再生位置を追う仕組みが、編集が入っても保たれるか）で見直した。

まず速度の扱いを確かめた（音声は `inPoint + (playheadTime - startTime) * speed`、
本編は `playbackRate = speed` と rAF 側の `/ speed`、PiP は型に `speed` を持たない）。
ここは全経路で筋が通っていた。**シロを先に確定させてから**、
「覚えておいた1件を、あとで同じ一覧から探す」箇所に絞った。

見つけたのは、**再生中に編集を1つすると、次のクリップの境目で先頭へ戻る**こと。
`timedClips` は `useMemo(..., [project])` で、**project が少しでも変わると中身が同じでも
作り直される**。一方 `activeTimedClipRef` は「1つ前の配列の」オブジェクトを持ったままで、
境目の判定が `timedClips.indexOf(tc)` という**同一性の照合**だった。
`indexOf` は **-1** を返し、`timedClips[-1 + 1]` が **`[0]` = 先頭のクリップ**になる。
例外も警告も出ず、**「次へ進んだ」動作そのものに見える**。
テロップを足す・素材を読み込む・クリップを選ぶなど、**映像の並びと無関係な編集でも起きる**。

1. 最初の実測は「既定ズームで左端を引き切れば自分の終端(4.0)にくっつくはず」と読んで

   候補を 3.9 に置いて初めて再現した。**「ちょうど閾値」は当てにならない。**
2. 単体でも同じ罠を踏んだ。`snapTime(3.2, [3.0], 0.2)` を「距離ちょうど閾値だからくっつく」
   と書いて落ちた。`3.25 - 3.0 = 0.25`（2進で正確に表せる）に変えて意図どおりに測れた。

クランプ自体は必要な守りだったが、その結果**つまみの上半分が画面では完全に死んでいた**。
書き出しの `volume=` には上限が無いので、そこで食い違う。

実測（**実機**・利用者と同じ操作でBGMトラックを作りつまみを動かす。画面側は
アプリが作る `GainNode`／要素の `volume` を捕まえて、実際に掛かる倍率と
`AnalyserNode` で信号のピークまで読んだ。書き出しは同じ構成を ffmpeg に通して
`volumedetect`）:

| つまみ | 画面(修正前) | 画面(修正後) | 信号のピーク(修正後) | 書き出し |
|---|---|---|---|---|
| 50% | 0.50倍 (-6.02dB) | **同じ**(回帰なし) | — | -31.9dB |
| 100% | 1.00倍 (0.00dB) | **同じ**(回帰なし) | 0.0111 | -25.9dB |
| **150%** | **1.00倍 (0.00dB)** | **1.50倍 (+3.52dB)** | 0.0166 | -22.3dB (+3.6) |
| **200%** | **1.00倍 (0.00dB)** | **2.00倍 (+6.02dB)** | 0.0221 | -19.9dB (+6.0) |
| **300%** | **1.00倍 (0.00dB)** | **3.00倍 (+9.54dB)** | 0.0332 | -16.3dB (+9.6) |

つまり**画面と出力の差は最大 +9.5dB**（約3倍）あった。信号のピークは
0.0111 : 0.0166 : 0.0221 : 0.0332 = 1 : 1.50 : 1.99 : 2.99 と倍率どおりに増えていて、
数字を入れただけでなく**実際に音が大きくなっている**ことまで確認した。

必要になったときだけ Web Audio の `GainNode` に付け替える形にした。
`createMediaElementSource` は要素につき1回しか呼べず**戻せない**ので、常時経由にすると
`AudioContext` が動かない環境で音が消える——頭打ちより悪い。**1倍を超える音量を実際に
要求されたときにだけ**付け替え、失敗したら今までどおり `el.volume` に倒す。
実測でも 100%以下では `GainNode` が1つも作られていない（＝従来の経路のまま）。

音量の式そのものも `@shared/audioGain` の `audioClipGain()` に1本化して、
書き出しとプレビューが同じ関数を呼ぶようにした。

単体44件（`audioClipGain` にトラック/クリップ音量の 0・0.5・1・1.5・2・3・NaN・±Infinity・負・
未設定の組み合わせ、`toElementVolume` の 0〜3・負・NaN・±Infinity、`needsWebAudioGain` の
境界 1 ちょうど / 1.0000001、そしてつまみ7段で「修正後の画面 = 書き出し」）。

回帰:
- **書き出しはつまみ5段すべてバイト単位で同一**（163029 / 163050 / 163005 / 162998 / 163036 B）
- ミュートは `GainNode` 経由でも効く（信号のピーク 0.0332 → **0** → 解除で 0.0332 に復帰）
- 100%以下は `GainNode` を作らず `el.volume` のまま

**副産物**: 音量に `NaN` / `Infinity` が入ったプロジェクト（手で編集したファイル）では、
修正前は `volume=NaN` がそのまま渡って**書き出しが丸ごと失敗**していた
（`ffmpeg exited with code 234`）。共通化した `audioClipGain` が使えない数を等倍に
倒すので、修正後は 1.0 と同じ -25.9dB で書き出せる。

**測り方の失敗を3件記録**:
1. 最初の実測で 300% だけ信号のピークが **0** になった。倍率の問題ではなく、
   **4秒のBGMが測り終える前に鳴り終わっていた**だけ。30秒の素材に変えたら素直に並んだ。
2. 「修正前」を測るための `git stash` が2回とも失敗していたのに気付かず、
   **修正後のコードを2回測って「前後で同じ」と読みかけた**。1回目は `cd` でスクラッチに
   居たため `not a git repository`、2回目は新規ファイル `audioGain.ts` が未追跡で
   `-u` を付けていなかったため。**stash したら「消えたか」を必ず確かめること。**
3. 単体の境界値表で、自分が書いた `toElementVolume(Infinity)` が 0(無音)を返していた。
   「0〜1に丸める」と名乗る関数が上限超えだけ無音にするのは筋が通らないので、
   NaN だけ 0 に倒す形へ直した。**期待値の表を先に書いたから見つかった。**

### 2026-08-13 テロップ・字幕（2周目の2件目）
この領域は「縁取り・影の換算」「ASS のエスケープ」「BorderStyle」を既に直してあるので、
**まだ当てていない眼鏡**（「画面と出力で同じ規則を2箇所に書いていないか」

|---|---|---|---|---|

| 上寄せ | 上から 8.05% | 上から 8.05% | 上から 9.03% | 元から一致（回帰なし） |

単体38件。`textMarginVPx` の境界値（0・負・NaN・±Infinity・1・480/720/1080/2160）で

左右余白（CSS `5%` の比 ⇔ ASS `MarginL/R=40` の出力px固定。4K では 5% 対 1.04%）と

`fontSize` の意味が変わって既存プロジェクトの見た目が動くため、移行方針を決めないと
入れられない＝今回の1件には大きすぎると判断した。

### 2026-08-13 書き出しパイプライン（2周目の1件目）
巡回表が一周したので2周目。この領域は fps・音声形式・PiP余白・無音しきい値を既に直してあるので、
**まだ当てていない眼鏡**（「利用者が受け取る成果物の形式を、環境や経路まかせにしていないか」
「値の変換を交渉に委ねていないか」）で見直した。

見つけたのは、**映像の画素形式だけが何も固定されていなかった**こと。音声は
`AUDIO_FORMAT`（`aformat`）で合流の手前を全部固定してあるのに、映像側は素通しだった。
`xfade` は yuv444p を好むため、**4:2:0 の素材しか無いタイムラインでも、繋ぎを
「クロスフェード」にしただけでグラフ全体が 4:4:4 に引き上げられ**、libx264 が
**High 4:4:4 Predictive** で書き出す。エラーも警告も出ず、尺もフレーム数も音量も正しいので、
毎時の検証では絶対に落ちない。

実測①（`exportProject` 直叩き / 1280x720・4:2:0素材2本 → 480p）:

| タイムライン | 修正前 profile/pix_fmt | 修正後 |
|---|---|---|
| 繋ぎなし | High / yuv420p (971,468 bps) | **同じ**（バイト単位で同一・回帰なし） |
| **クロスフェード** | **High 4:4:4 Predictive / yuv444p** (1,213,027 bps) | **High / yuv420p** (956,833 bps) |
| クロスフェード+ぼかし背景 | **High 4:4:4 Predictive / yuv444p** | **High / yuv420p** |
| クロスフェード+PiP | High / yuv420p | **同じ**（`overlay` が 4:2:0 に引き戻していた） |
| テロップのみ | High / yuv420p | **同じ**（回帰なし） |

つまり**利用者が使った機能の組み合わせ次第で、成果物の画素形式が黙って変わっていた**。
PiP を足すと 4:2:0 に戻る、という一貫性の無さがそのまま症状になっている。

実測②（**実機**・利用者と同じ操作。素材を読み込み → タイムラインに2本 →
インスペクタで繋ぎを「クロスフェード1秒」→ 720p で書き出し）:

| | 修正前 | 修正後 |
|---|---|---|
| profile / pix_fmt | **High 4:4:4 Predictive / yuv444p** | **High / yuv420p** |
| 映像の尺 / 音声の尺 | 19.000000 / 19.000000 | **同じ** |
| フレーム数 | 570 | **同じ** |
| 音量 mean / max | -24.1 / -20.7 dB | **同じ** |
| ファイルサイズ | 2,520,133 B | **1,804,115 B（-28.4%）** |
| ビットレート | 1,061,108 bps | **759,627 bps（-28.4%）** |

4:4:4 は元素材に無い色差情報が増えるわけではないので、**同じ絵に +28% のビットレートを
払ったうえ、ハードウェアデコーダや一般的な再生環境が扱えない profile になっていた**。

出力の直前に `format=yuv420p` を1枚挟んで固定した。`previewProxyService` は最初から
`-pix_fmt yuv420p` を付けており、**書き出しだけが素通しだった**。

単体21件（クリップ1本 / 2本 / 8本、繋ぎの長さ 0・0.01・0.5・1e9・NaN・負、
type=none、テロップのみ、PiP 0/1/3枚、全部盛り、ぼかし背景、fillCrop、音声なし素材、速度4倍）で

修正前のコードに同じ21件を当てると**全件 NG**になる（＝テストが効いている）。

回帰は15シナリオで確認し、**影響の無い11シナリオはバイト単位で出力が同一**、

1. 単体の偽 ffmpeg を「引数を書いて即 exit 1」にしたら、fluent-ffmpeg が spawn 前に走らせる
   `-codecs` などの能力調査まで潰れ、**グラフを組み立てる前に落ちていたのに全件 NG に見えた**。
   能力調査だけ本物に流す形にして直した。
2. 修正後の結合で、before と**バイト単位で同じ数字**が出た。焦って「効いていない」と

### 2026-08-12 解析系（ハイライト・BPM・無音・スマートクロップ）
無音検出だけが `noise=-30dB` の**絶対しきい値の決め打ち**だった。素材の録音レベルは
撮り方で何十dBも変わるので、**小さく録れた素材では話している区間まで無音**になる。
ハイライト検出も長尺スキャンも既に「平均+標準偏差」の相対にしてあり
(`longFormService` には「固定のdBしきい値はマスタリングの違う素材で破綻する」と
コメントまである)、**無音検出だけが取り残されていた**。

実測（同じ構造の素材=音2秒/無音1秒/音2秒/無音1秒/音2秒、音量だけ変えたもの。
実機のIPC経由でも同じ数字を確認）:

| 素材の最大音量 | 修正前の候補 | 修正後の候補 |
|---|---|---|
| -0.0dB | 2件 2.00-3.00 / 5.00-6.00 | **同じ**(回帰なし) |
| -18.1dB | 2件 2.00-3.00 / 5.00-6.00 | **同じ**(回帰なし) |
| **-44.1dB** | **1件 0.00-8.00(全域が無音)** | **2件 2.00-3.00 / 5.00-6.00** |
| **-84.3dB** | **1件 0.00-8.00(全域が無音)** | **2件 2.00-3.00 / 5.00-6.00** |
| 全域デジタル無音(-91.0dB) | 1件 0.00-8.00 | **同じ**(回帰なし) |

しきい値を `max(-90, min(-30, 素材の最大 - 12))` にした。**従来より厳しい側にしか
動かない**ので、大きく録れている素材は今までどおり -30dB で切る。

**下限(-90dB)は実測で決めた**: 相対だけにすると全域無音の素材でしきい値が -103dB になり、
**デジタル無音ですら0件**になった。`silencedetect` にしきい値を振って測ったところ
-90dB では検出でき、**-96.3dB 以下は常に0件**。16bit の量子化下限(-90.3dB)とも一致する。
最初この下限を入れずに単体を回して3件落ちたので気付けた。

単体12件すべてOK(音量4段階・全域無音・全域音・部分区間・区間長0・範囲外・音声なし素材)。
同じ単体を修正前のコードで回すと3件が落ちる(小音量2件と、小音量素材の部分区間)。
解析が2パスになる(`volumedetect` → `silencedetect`)が、`-vn` で音声だけデコードする。

同種を洗ったところ、音量を見る検出器は他に `highlightService`(平均+標準偏差の相対)と
`longFormService`(同じく相対、コメントで明記)があり、どちらも**既に相対化済み**。
絶対値のままだったのは無音検出だけだった。
BPM検出の `offsetSeconds` は Timeline 側が `clip.startTime` を足し、`autoEdit` 側は
足していないが、**`autoEdit` はその値を使っていない**(bpm だけ使う)ので実害なし——
誤検知しかけたので記録しておく。

### 2026-08-12 プレビュー再生（同期・プロキシ・PiP）
PiP(ワイプ)を隅から離す余白が、書き出しとプレビューで**基準の辺が違っていた**。
書き出しは `margin = round(出力幅 * 0.04)` を **x にも y にも**使うのに、プレビューは
CSS の `top/bottom: 4%`。**`top`/`bottom` の `%` は親の高さ基準**なので、同じ「4%」でも
別物になる。しかも**縦横比によってズレの向きが逆になる**。

実測（実機のDOM実寸 vs 書き出しフレームの画素。scale=0.3 / bottom-right）:

| | 書き出し | プレビュー(修正前) | プレビュー(修正後) |
|---|---|---|---|
| 9:16 の縦の余白(高さ比) | **2.25%**(43.2/1920) | **4%** | **2.25%** |
| 縦の余白(枠の幅に対する比) 9:16 | **4.07%** | 7.11% | **4%** |
| 縦の余白(枠の幅に対する比) 16:9 | **4.06%** | 1.36% | **4%** |
| 横の余白 | 4.06% | 4% | 4% |
| PiPの幅 | 幅の30%(576/1920) | 30% | 30% |

### 2026-08-12 タイムラインUI（ドラッグ・トリム・スナップ・選択）
音声クリップ/PiPクリップのトリム(`mediaTrimDrag`)だけが、マウスの移動量
(`px ÷ pixelsPerSecond` = **タイムライン秒**)を `inPoint`/`outPoint`(**素材秒**)へ
そのまま足しており、**速度で換算していなかった**。本編クリップのトリム(`trimDrag`)には

分離音声は本編クリップの速度をミラーする(2倍速のクリップから分離すると `speed=2`)ため、
**利用者が普通に踏む**経路。

実測（実機Electron / xvfb / 40px per second のタイムライン / 素材10秒・in=2 out=6 start=2）:

| 操作 | 修正前 | 修正後 | 期待 |
|---|---|---|---|
| speed=1 右へ+40px | 幅 +40px | 幅 +40px | +40px |
| speed=1 左へ+40px | 左端+40px / 終端0px | 同左 | 終端は動かない |
| **speed=2 右へ+40px** | **幅 +20px**(out 6→7) | **幅 +40px**(out 6→8) | +40px |
| **speed=2 左へ+40px** | 終端が **+20px 動く** | **終端 0px** | 動かない |

境界値も実機で確認: 右へ+400px → out=10(素材の終端でクランプ)、右へ-400px → out=2.2
(最小尺0.2)、左へ-400px → in=0/start=1(素材先頭)、左へ+400px → in=5.8/start=3.9
(最小尺。終端は 3.9+0.1=4.0 で元と同じ)、speed=0.5 右へ+40px → out=6.5(タイムライン+1秒)。
回帰: PiP(速度を持たない型)は右+40px→out=7、左+40px→in=3/start=3 で従来どおり。

**測り方の失敗を1件記録**: 最初の測定は out が素材の終端(10秒)に張り付いた状態で
ドラッグしたため「幅の増分0px」となり、症状が出ていないように見えた。
伸ばす余地を作ってから測り直して初めて 20px/40px の差が出た。
「何も起きなかった」を正常と読まないこと。

同種を洗った結果、タイムライン秒↔素材秒の換算は他に
`trimDrag`(本編/`* prev.speed` あり)・`rollTrim`(ストア側で speed 込みでクランプ)・
レーザー分割(`splitClipAtTime` がストア側で換算)・`splitAudioClipAtTime`

`startTime` しか触らないので換算不要。漏れていたのは `mediaTrimDrag` の1箇所だけだった。

### 2026-08-12 IPC境界（main↔renderer・エラー処理・並行実行）
main→renderer の通知は `event.sender.send` の2箇所だけで、**プレビュープロキシ側にだけ

webContents に対して `TypeError: Object has been destroyed` を投げる（Electron 実機で確認。
`win.close()` の直後は `isDestroyed()` がまだ false で、少し待つと true になる）。
投げる場所が ffmpeg のイベントハンドラの中なので `ipcMain.handle` の外、つまり
**どこにも捕まらず main プロセスごと落ちる**。
実測（1080p・40秒・実機Electron / 書き出し開始1.0秒後にウィンドウを閉じる）:
修正前 `uncaughtException: Object has been destroyed` でアプリ異常終了、書き出し先に
**48バイト・moov atom not found の再生できないファイル**が残る。
修正後は書き出しが最後まで走り、**1200フレーム / 映像40.000秒・音声40.000秒**で完走。
対照（修正前のままウィンドウを閉じない）は 14.0秒・進捗21回で完走したので、
原因が「閉じたこと」であることも確かめた。
単体: 生きている相手には境界値（0 / 100 / -1 / 33.333333 / 空文字 / null / undefined）が
そのまま届き例外0件、破棄済みの相手には1000回連続で送っても例外0件。
ガード無しの式は1回で TypeError になることも並べて確認（テストが空振りしていないことの裏取り）。
回帰: ウィンドウが生きている場合の進捗送信は修正前後とも21回、出力も同一。
Linux/Windows は最後のウィンドウを閉じるとアプリ自体が終了するため、
利用者が踏むのは**ウィンドウを閉じてもアプリが残る macOS**（`electron-builder.yml` の
ビルド対象に含まれる）。実測はその挙動に合わせて `window-all-closed` を握って行った。
同種を洗ったところ main→renderer の送信は他に無く、進捗コールバックを渡している
IPCハンドラも書き出しとプレビュープロキシの2つだけだったので、両方を共通の
`notifySender` に通す形にした。
