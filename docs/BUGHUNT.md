# バグ狩り（1時間おき / 潜在バグを探して即修正する）

このファイルは**バグ狩りロール専用**です。他のロールは書き込みません。
`BACKLOG.md` に書くと、実装・補充・検証の3ロールと毎回衝突するため分けてあります。

## このロールの立ち位置

| ロール | 見るもの | 動くとき |
|---|---|---|
| 検証 | **直近のコミットが壊していないか** | 壊れているときだけ直す |
| バグ狩り（これ） | **前からずっと壊れていたもの** | 毎回1件見つけて直す |

検証ロールは「壊れていなければ何も変更せず終了」なので、**最初から間違っていたコードは永久に拾えません**。
実際、60fps素材が常に30fpsで書き出されていた不具合は、尺が合っていてエラーも出ないため、
検証を何十回通しても素通りしていました。そこを掘るのがこのロールです。

## 1回の実行でやること

**1件だけ**見つけて、**その場で直して**、**push するまで**が1セット。
見つけて報告するだけで終わらせない。直せないものを見つけたら、次項の手順で候補に残す。

### 手順

1. **担当領域を1つ選ぶ。** 下の「領域の巡回表」で**最終掃引が一番古いもの**。
   同じ領域を続けて2回選ばない。
2. **`BACKLOG.md` の「再発防止チェックリスト」を全部読む。**
   これが探すための眼鏡です。各項目を「この領域でこれに違反している箇所はないか」という
   grep の観点に翻訳して、順に当てていく。項目数が多いので、当てた項目と結果を手元に控える。
3. **怪しい箇所を見つけたら、直す前に「本当に壊れているか」を実測で確かめる。**
   ここを飛ばすと、壊れていないものを「直して」しまう。実際に何度も起きています
   （呼び出し方を間違えて2件を誤検知、クリップ終端での分割を不具合と誤認、など）。
   実測とは、アプリを起動して同じ操作をする・ffprobe で数字を読む・DOM の値を読む、のいずれか。
4. **直す。** 進め方は `BACKLOG.md` の「実装の進め方」（設計 → 実装 → 単体 → 結合）に従う。
5. **同じ種類が他にないか grep で洗う。** 1箇所だけ直すと、残りが黙って壊れたままになる。
   （実例: 書き出しの `fps=30` を直したら、画面側にも `1 / 30` が3箇所あった）
6. **チェックリストに1行足す**（`BACKLOG.md` の「再発防止チェックリスト」）。
   既存項目と同じことを言い換えただけなら足さない。既存項目で拾えたなら、そう報告する。
7. このファイルの巡回表の日付と「見つけたもの」を更新して、コード変更と一緒にコミットする。

### 何も見つからなかったとき

**でっち上げない。** 「異常なし」で終えてよい。ただし巡回表は更新して、
**どのチェックリスト項目をどう当てて、なぜシロと判断したか**を1〜2行残すこと。
これが残っていないと、次回また同じ当て方をして同じ時間を溶かします。

### 直すのが大きすぎたとき

無理に大改造しない。`BACKLOG.md` の「候補」欄に
「◯◯の修正（バグ狩りで発見。症状は△△、原因の見当は□□）」として1件残し、
このファイルにも記録して終える。**症状と再現手順は必ず数字付きで書く。**

## 優先順位

同じ日に2つ怪しいものが見つかったら、**編集作業が止まる/出力が壊れるほう**を先に直す。

1. 出力が壊れる（尺ズレ・音ズレ・映像の欠落・書き出し失敗）
2. 編集内容が失われる（Undoで戻らない・保存で消える・参照が切れる）
3. 画面と出力が食い違う（プレビューで決めた見た目が出力で別物）
4. 操作が効かない・効きすぎる
5. 表示崩れ・文言

### 2026-08-14 AI連携（3周目の10件目）
この領域は「外部APIの失敗を日本語に」「応答の要素ごとの coerce」「好み学習の浅マージ」
「AIショートで素材を切り替えたら構成案を捨てる」を既に直してあるので、
**まだ当てていない眼鏡**（「対象を変えたら結果を捨てているか」を、**画面の中に選択UIが
無い場合**＝上部バーでプロジェクトごと入れ替わる場合に当てる）で見直した。

見つけたのは、**AIが作った結果が、別のプロジェクトを開いても残る**こと。
AIショートは**モーダル**なので閉じれば消えるが、投稿準備・サムネは**パネル**で、
タブは `active` クラスを付け替えるだけ——**中身はずっとマウントされたまま**なので、
明示的に捨てないと一生残る。しかもパネルには対象を選ぶUIが無いので、
「対象が変わった」という手掛かりが画面に出ない。

実測（**実機**・利用者と同じ操作。Aのプロジェクトを開く → 投稿準備タブでAPIキーを打って
「メタデータを生成」 → サムネタブで「均等間隔で生成」 → 上部バーの「開く」でBを開く。
Gemini への通信だけ renderer の `fetch` を差し替えて、プロジェクト名の頭文字を混ぜた
固定の応答を返した）:

| 場面 | 修正前 | 修正後 |
|---|---|---|
| ① Aで生成した直後 | タイトル案 **A案のタイトル1 / A案のタイトル2**、概要欄 **Aの概要欄**、サムネ候補 **6件** | **同じ**（生成は壊していない） |
| ② 同じプロジェクトを編集（回帰） | （測っていない） | **すべてそのまま残る** |
| **③ Bを開いた直後** | プロジェクト名は**Bのプロジェクト**なのに、タイトル案 **A案のまま**・概要欄 **Aの概要欄**・サムネ候補 **6件のまま** | タイトル案 **0件**・概要欄 **無し**・サムネ候補 **0件** |

つまり修正前は、**Bの画面でAのタイトルをコピーでき、Aのサムネを書き出せた**。
さらに「タイトルだけ再生成」は `frames`（**Aから抜いたサムネ画像**）をAIへ送っていた。

直しは `project.id` の変化で結果を捨てる形（プレビュー変換の直しと同じ判定）。
捨てるのは**AIが作った結果と抽出したフレーム**だけで、利用者が打った値
（APIキー・言語・補足情報・サムネの文字とスタイル）は残す
——AIショートで編集方針を残しているのと同じ扱い。

単体21件（`project.id` が**この直しの土台どおりに動くか**を実測: 素材・クリップ・速度・
名前・取り消し・やり直し・保存では**変わらない**（＝編集のたびに結果が消えない）、
新規作成・別ファイルを開く・自動保存の復元では**変わる**、同じファイルを開き直すと
**同じ id に戻る**、境界値は id が 無い/空文字/数値/null のとき——いずれも新しい id に
なり**捨てる側に倒れる**ことを確認）。

**検算**: 期待どおりに直ったので、①**同じ probe を修正前のコードで流し直して**
「Bの画面にA案のタイトル」が再現することを確かめた（①の値は前後で完全に同一なので、
生成そのものは壊していない）。②**回帰**として、同じプロジェクトを編集（クリップ追加＋
名前変更）しても結果が残ることを実機で確認した——`project.id` で判定しているので
編集では消えない。

**測り方の失敗を2件記録**:
1. 最初の probe はタイトルが空のまま出た。原因はコードではなく**APIキーを入れていなかった**
   ため（`handleGenerate` は鍵が無いと通信せず終わる）。入力欄に本物の input イベントを
   出して打ち込む形に変えた。
2. 回帰の測定で probe が返らなくなった。**未保存のまま「開く」を押すと `confirm()` が出て
   JS が止まる**ため（確認が出ること自体は正しい挙動）。先に保存ボタンを押す手順に変えた。

同種を洗ったところ、プロジェクトから作った結果を持つパネルは**この2つだけ**。
ゲームトレンド・YouTubeトレンド・BGM/SEは**キーワードから作った結果**で
`useProjectStore` を一度も読んでいない（プロジェクトと無関係なので対象外）。
テンプレート・プリセットは結果を溜めない。モーダル（AIショート・自動テロップ・
無音カットなど）は閉じるとアンマウントされるので残らない。
ナレーションパネルの「追加先の音声トラック」だけは**プロジェクトのトラックIDを覚える**が、
これは結果ではなく**利用者が選んだ行き先**で、選択肢に無ければ画面上も未選択になるため
今回の1件とは分けた。

### 2026-08-14 解析系（3周目の9件目）
この領域は「外れ値でしきい値が跳ねる」「無音のしきい値のフロア」「BPMの手直し導線」
「スマートクロップが画面に出ない」を既に直してあるので、**まだ当てていない眼鏡**
（「画面に出す数値を実際の出力と突き合わせたか」を、**解析が返す秒の単位**に当てる
＝既存の「マウスの移動量を速度で割り戻したか」の**表示方向**版）で見直した。

見つけたのは、**解析が返す「素材の秒」をそのまま画面に出している**こと。
無音検出・文字起こしはファイルを直接読むので秒は素材基準だが、利用者が見ている
タイムラインと書き出しはタイムライン基準で、**速度を変えたクリップでは倍率ぶん食い違う**。
削る位置は正しいので**数字だけが静かにズレる**。等倍では完全に一致するため、
毎時の検証でも開発中でも踏まない。

実測（**実機**・利用者と同じ操作。素材10秒(2〜6秒が無音)を置き、**2倍速**にしてから
「無音カット」ボタンを押し、モーダルの文字を読んでから「選択した区間を削除」を押す。
書き出しは 360p で ffprobe）:

| | 修正前 | 修正後 |
|---|---|---|
| クリップ（素材10秒・速度2） | タイムライン 5.000秒 | 同じ |
| モーダルの区間表示 | **0:02.0 〜 0:06.0 (4.0秒)** | **0:01.0 〜 0:03.0 (2.0秒)** |
| モーダルの合計表示 | **合計4.0秒** | **合計2.0秒** |
| 適用後に実際に縮んだ秒 | **2.005秒** | 2.005秒（変わらない） |
| 書き出しの尺 | 3.034秒 | **3.034秒（1バイトも変えていない）** |

つまり修正前は、**画面が約束した 4.0秒 に対して実際は 2.005秒**しか縮まなかった。

直したのは**表示側だけ**。`timelineMath.ts` に `toTimelineSeconds(素材秒, 速度)` を置き、
同じ「区間を消す」系の画面3つ（無音カット・フィラーカット・テキストで編集）を全部通した
——削除そのものは `buildCutSegments` が素材の秒で動くまま。

単体27件（等倍・2倍・4倍・0.5倍・0.25倍・3倍の理論値、境界値は 速度 0/負/NaN/±Infinity
（等倍に倒して Infinity を画面に出さない）・秒が NaN/負、`audioClipDuration` および
`buildTimedClips` と同じ答えになること、実際の場面（2倍速で 2〜6秒を消す）で
**断片が素材の秒のまま**であること・縮んだ秒が表示と一致すること、
等倍では表示も削り方も従来どおりであること、速度混在の合計（修正前は10、修正後は9.5））。

**回帰（実機）**: 等倍の同じ操作では表示が **0:02.0 〜 0:06.0 (4.0秒) / 合計4.0秒** と
**修正前と一字一句同じ**で、実際に縮んだのも 4.011秒、書き出しは 6.034秒だった。

**検算**: ①同じ probe をコードだけ入れ替えて流し、表示が 4.0 → 2.0 に動く一方で
**実際に縮んだ秒(2.005)も書き出しの尺(3.034秒)も前後で同一**であることを確かめた
（表示だけを直したことの裏取り）。②単体でも「修正前の式なら合計10、修正後は9.5」を
対にして、テストが効いていることを見ている。

同種を洗ったところ、解析結果の秒を画面に出しているのは6箇所。
**直したのは3つ**（無音カット＝位置と合計、フィラーカット＝位置、テキストで編集＝合計）。
残り3つはそのままでよい: ハイライト検出とラフカットの候補は**まだクリップになっていない
元動画の位置**（作られるクリップは等倍）、トリムのモーダルは「元動画の長さ」と並べて
出している素材基準の値。インスペクタは最初から「素材内の長さ」と「タイムラインの尺」を
**別々に**出しており、ここでも片方にだけ正しい扱いが育っていた。

**確かめられなかったこと（正直に記録）**: フィラーカットとテキストで編集は
文字起こし(whisper)が要るが、**この環境ではモデルを取得できず実機で走らせられない**。
2つの表示は単体（同じ `toTimelineSeconds` を通す）とコードの通り道でのみ確認している。

**シロと判断したもの（次回同じ当て方をしないための記録）**:
- `detectAudioLevels` の `asetnsamples=n=44100` は「素材の性質の決め打ち」に見えるが、
  時刻は `pts_time` から読むので**位置はずれない**（窓の長さが 48kHz で 0.919秒になるだけ）。
  実測で壊れるものが無いので触っていない。
- BPM の `offsetSeconds` は解析範囲の先頭からの素材秒で、`clip.startTime + offset` として
  グリッドに入る。**速度≠1の音声クリップでは倍率ぶんずれる**が、音声クリップの速度は
  分離音声が本編からミラーする経路でしか 1 以外にならず、今回の1件（表示の単位）とは
  別の話なので分けた。
- 自動テロップ(`AutoCaptionModal`)・おまかせ仕上げ(`autoFinish`)は
  `tc.start + (seg.start - inPoint) / speed` と**最初から速度で割っていた**。

### 2026-08-14 プレビュー再生（3周目の8件目）
この領域は「再生中の編集で先頭へ戻る」「PiPの余白」「音量つまみ100%超」「クロップが画面に
出ない」「枠の縦横比」を既に直してあるので、**まだ当てていない眼鏡**
（「同じ状態を作る入り口が複数あるとき、下ごしらえが全部の入り口に付いているか」＝
既存の「同じ処理を2箇所に書くと片方だけ育つ」の**呼ぶ側**版）で見直した。

見つけたのは、**プレビュー用の変換(プロキシ)が「取り込み」と「再リンク」でしか走らない**こと。
プロジェクトを**開いた**ときは誰も作らない。HEVC の変換は取り込みの裏で走り続けるので、
**変換が終わる前に保存すると `proxyPath` は保存されない**——その `.veproj` を開くと、
さっきまで再生できていた同じ素材が**プレビューで一切再生できず、回復する手段も無い**。
変換が一度失敗した場合・別の環境で開いた場合・キャッシュを消した場合も同じ状態になる。

実測（**実機を2回起動**。1回目は利用者と同じ操作で hevc60.mp4 を「動画」ボタンから取り込み、
変換の途中で保存ボタンを押す。2回目は「開く」でそれを開く。ファイル選択ダイアログは
main の `ipcMain.handle` を差し替えて固定）:

| | 修正前 | 修正後 |
|---|---|---|
| 取り込んだ直後（対照） | `videoWidth 960`・エラー無し・プロキシあり | 同じ |
| 保存された `.veproj` | 素材の `proxyPath` = **無い** | 同じ（保存の挙動は変えていない） |
| **開いた直後** | src=hevc60.mp4 / `videoWidth 0` / 「プレビューで再生できません」/ **変換中の表示なし** | 同じ表示だが**変換が始まる**（変換中の表示あり） |
| **60秒後** | プロキシ **無いまま** / `videoWidth 0` / メッセージ出続け | プロキシ**できた** / src=プロキシ / **`videoWidth 960`** / エラー無し |

つまり修正前は、**同じファイル・同じプロジェクトなのに「どうやって state に入れたか」で
再生できるかが変わっていた**。

直しは、開いた/復元したときにも取り込みと同じ判定を通すこと。判定は
**実際に読み込ませてみる**(`canPreviewFile`)——コーデック名の決め打ちは環境で答えが変わる。
見るのは**プレビューが実際に読む側**(`proxyPath ?? filePath`。保存されたプロキシの実体が
消えていることがある)、作り直しは必ず**元ファイル**から。判定部分は
`assetsNeedingPreviewProxy()` として `canPreview.ts` に出し、`proxyPath ?? filePath` の
規則も `previewSourcePath()` に1本化した。走る条件は `project.id` の変化——保存・読込を
通して保たれ、素材を足しただけでは変わらないので、取り込みのたびに走り直さない。

単体24件（対象の選び方: 0件・全部再生できる・一部だけ・プロキシで再生できる・

### 2026-08-14 テロップ・字幕（3周目の2件目）
この領域は縁取り・エスケープ・BorderStyle・縦余白・仮想キャンバスを既に直してあるので、
**まだ当てていない眼鏡**（「画面と出力で同じ位置・寸法の規則を持つなら数字は1箇所にあるか」を
**左右方向**に当てる／**入力の長さを変えて**描き比べる）で見直した。

見つけたのは、**長い日本語のテロップが書き出しで折り返されない**こと。
**libass は空白でしか行を分けない**ため、空白の無い日本語は1行のまま伸び続け、
フレームの外へ出て左右が切れる。画面(CSS)は文字単位で折り返すので**収まって見える**。
併せて、折り返す幅そのものも食い違っていた——画面は CSS の `left/right: 5%`、
書き出しは ASS の `MarginL/R=40`(1920キャンバスの **2.08%**)。

実測（**実機**・利用者と同じ操作。16:9 プロジェクトに既定スタイルのテロップを1枚置き、
プレビュー枠を `capturePage`、同じプロジェクトを 720p で書き出してフレームの画素を
**同じ数え方**で数えた。文字は全角の連続）:

| テロップ | | 修正前 | 修正後 |
|---|---|---|---|
| 全角200文字 | 画面 | 5行（インク 5.24%〜94.52%） | **同じ** |
| 全角200文字 | 書き出し | **1行**（インク **0%〜100%** = 両端が切れて読めない） | **5行**（13.75%〜86.25%） |
| 全角45文字 | 画面 | 2行 | **同じ** |
| 全角45文字 | 書き出し | **1行** | **2行** |

**最小の再現**でも確かめた（黒画像に ASS を焼くだけ）: 全角200文字 → 1行・0%〜100%、
**ゼロ幅空白(U+200B)を1文字ごとに挟んでも 1行のまま**、英語(空白区切り)は3行に折り返す。
つまり回避策として空白系の文字を挟むのは効かない。

直し方は2つで1つ:
1. 左右の余白を `@shared/textStyle` の `TEXT_MARGIN_H_RATIO` に1本化（縦と同じ形）。
   CSS からは数字を消し、ASS の `MarginL/R` は `round(幅 × 比)` で出す。
2. **libass が折り返せない並びだけ、こちらで `\N` を入れる**（`wrapAssLines`）。
   空白で区切られた並びは libass 自身が折り返せるので触らない——先回りして割ると
   二重にかかって不自然な位置で切れる。幅は全角1em・半角0.5em の**見積もり**
   （main プロセスに字送りを測る手段が無いため。実フォントより広めに見積もり、
   **切れるより手前で折る**側へ倒す）。

単体40件（折り返しの行数と「上限以下」であること・文字が欠けないこと、半角は2倍入ること、
空白区切りは単語の途中で割らないこと、元の改行を保つこと、境界値は
空文字・ちょうど上限・上限+1・0・負・NaN・Infinity・0.5em・1万文字・絵文字、
そして ASS 側で MarginL/R が比から出ること・改行数が理論値
`ceil(200 / floor((幅-余白×2)/文字サイズ))-1` と一致すること・短いテロップには改行を
入れないこと・背景ありは箱と文字の改行位置が同じこと・タイプライター/自由位置でも
折り返すこと・別解像度でも比であること）。

**検算**: 期待どおり直ったので、①**回帰**として短いテロップ（「こんにちは世界」）を
修正前後の ASS で焼き比べた——**画素数110・x=284〜355・y=320〜329 と完全に同一**
（中央寄せの短い行は余白の変更に影響されない）。②**測り方の失敗を1件記録**:
最初の実測はプロジェクトが既定の 9:16 のままなのに書き出しだけ 16:9 で回しており、
**枠の比が違うものを見比べていた**（画面 132.97x236.38 に対し出力 1280x720）。
`setAspectRatio('16:9')` を入れて測り直した。

同種を洗ったところ、**libass に文字を渡すのは書き出しの `subtitles=` 1箇所だけ**。
サムネイルの文字入れは renderer の canvas に `fillText` していて折り返しを持たないが、
**その canvas 自体が成果物**（画面 = 出力）なので食い違いは起きない。

**残りを候補に1件記録**: 見積もりが実フォントより広いぶん、行が必要より早く折れる。
実測では libass の全角1文字は **0.81em** で、200文字の出力インク幅は画面の 89.29% に対し
**72.5%**（行数はどちらも5行で一致）。字送りを実測して渡す仕組みが要るため今回は見送った。

### 2026-08-13 解析系（2周目の9件目）

### 2026-08-13 タイムラインUI（2周目の6件目）
この領域は「音声/PiPのトリムに速度換算が無かった」件を既に直してあるので、

「クランプ → スナップ」で、**スナップ先は候補の時刻そのものなので前段のクランプを素通り**する。

| 条件 | 修正前の尺 | 修正後の尺 |
|---|---|---|
| 3.9 秒に候補あり・ズーム100%（閾値 0.2秒） | **0.1 秒**（最小の半分） | **0.2 秒** |

**尺 0 秒のテロップは画面からも出力からも消える**——プレビューの判定

単体30件。「クランプ→スナップ」だと外へ出ることを修正前の呼び方で確かめてから、
`snapClamped` が収めることを対で確認。境界値は候補が空・閾値 0/負/Infinity・
min と max が同じ・raw が範囲外・候補が負（閾値の内と外）・max が Infinity・raw が NaN。

1. 最初の実測は「既定ズームで左端を引き切れば自分の終端(4.0)にくっつくはず」と読んで

2. 単体でも同じ罠を踏んだ。`snapTime(3.2, [3.0], 0.2)` を「距離ちょうど閾値だからくっつく」
   と書いて落ちた。`3.25 - 3.0 = 0.25`（2進で正確に表せる）に変えて意図どおりに測れた。

### 2026-08-13 音声（2周目の3件目）
この領域は `aformat`・`atempo` の連鎖・フェードの正規化・分離音声のフラグを既に直してあるので、
**まだ当てていない眼鏡**（「UIの選択肢が裏の実装の範囲に収まっているか」
「画面と出力で同じ規則を2箇所に書いていないか」）で見直した。

見つけたのは、**音量つまみが 100% を超えるとプレビューだけ動かなくなる**こと。
音量つまみは**トラック用もクリップ用も 0〜300%**（`Timeline.tsx` の `max={3}` が2箇所）
なのに、プレビューは `Math.min(1, ...)` で `HTMLMediaElement.volume` に入れていた。
**`volume` は仕様上 0〜1 しか受け付けない**（1超は `IndexSizeError`）ので、
クランプ自体は必要な守りだったが、その結果**つまみの上半分が画面では完全に死んでいた**。
書き出しの `volume=` には上限が無いので、そこで食い違う。

実測（**実機**・利用者と同じ操作でBGMトラックを作りつまみを動かす。画面側は
アプリが作る `GainNode`／要素の `volume` を捕まえて、実際に掛かる倍率と
`AnalyserNode` で信号のピークまで読んだ。書き出しは同じ構成を ffmpeg に通して
`volumedetect`）:

| つまみ | 画面(修正前) | 画面(修正後) | 信号のピーク(修正後) | 書き出し |
|---|---|---|---|---|
| 50% | 0.50倍 (-6.02dB) | **同じ**(回帰なし) | — | -31.9dB |
| 100% | 1.00倍 (0.00dB) | **同じ**(回帰なし) | 0.0111 | -25.9dB |
| **150%** | **1.00倍 (0.00dB)** | **1.50倍 (+3.52dB)** | 0.0166 | -22.3dB (+3.6) |
| **200%** | **1.00倍 (0.00dB)** | **2.00倍 (+6.02dB)** | 0.0221 | -19.9dB (+6.0) |
| **300%** | **1.00倍 (0.00dB)** | **3.00倍 (+9.54dB)** | 0.0332 | -16.3dB (+9.6) |

つまり**画面と出力の差は最大 +9.5dB**（約3倍）あった。信号のピークは
0.0111 : 0.0166 : 0.0221 : 0.0332 = 1 : 1.50 : 1.99 : 2.99 と倍率どおりに増えていて、
数字を入れただけでなく**実際に音が大きくなっている**ことまで確認した。

必要になったときだけ Web Audio の `GainNode` に付け替える形にした。
`createMediaElementSource` は要素につき1回しか呼べず**戻せない**ので、常時経由にすると
`AudioContext` が動かない環境で音が消える——頭打ちより悪い。**1倍を超える音量を実際に
要求されたときにだけ**付け替え、失敗したら今までどおり `el.volume` に倒す。
実測でも 100%以下では `GainNode` が1つも作られていない（＝従来の経路のまま）。

音量の式そのものも `@shared/audioGain` の `audioClipGain()` に1本化して、
書き出しとプレビューが同じ関数を呼ぶようにした。

単体44件（`audioClipGain` にトラック/クリップ音量の 0・0.5・1・1.5・2・3・NaN・±Infinity・負・
未設定の組み合わせ、`toElementVolume` の 0〜3・負・NaN・±Infinity、`needsWebAudioGain` の
境界 1 ちょうど / 1.0000001、そしてつまみ7段で「修正後の画面 = 書き出し」）。

回帰:
- **書き出しはつまみ5段すべてバイト単位で同一**（163029 / 163050 / 163005 / 162998 / 163036 B）
- ミュートは `GainNode` 経由でも効く（信号のピーク 0.0332 → **0** → 解除で 0.0332 に復帰）
- 100%以下は `GainNode` を作らず `el.volume` のまま

**副産物**: 音量に `NaN` / `Infinity` が入ったプロジェクト（手で編集したファイル）では、
修正前は `volume=NaN` がそのまま渡って**書き出しが丸ごと失敗**していた
（`ffmpeg exited with code 234`）。共通化した `audioClipGain` が使えない数を等倍に
倒すので、修正後は 1.0 と同じ -25.9dB で書き出せる。

**測り方の失敗を3件記録**:
1. 最初の実測で 300% だけ信号のピークが **0** になった。倍率の問題ではなく、
   **4秒のBGMが測り終える前に鳴り終わっていた**だけ。30秒の素材に変えたら素直に並んだ。
2. 「修正前」を測るための `git stash` が2回とも失敗していたのに気付かず、
   **修正後のコードを2回測って「前後で同じ」と読みかけた**。1回目は `cd` でスクラッチに
   居たため `not a git repository`、2回目は新規ファイル `audioGain.ts` が未追跡で
   `-u` を付けていなかったため。**stash したら「消えたか」を必ず確かめること。**
3. 単体の境界値表で、自分が書いた `toElementVolume(Infinity)` が 0(無音)を返していた。
   「0〜1に丸める」と名乗る関数が上限超えだけ無音にするのは筋が通らないので、
   NaN だけ 0 に倒す形へ直した。**期待値の表を先に書いたから見つかった。**

### 2026-08-13 テロップ・字幕（2周目の2件目）
この領域は「縁取り・影の換算」「ASS のエスケープ」「BorderStyle」を既に直してあるので、
**まだ当てていない眼鏡**（「画面と出力で同じ規則を2箇所に書いていないか」

見つけたのは、**テロップの縦余白だけが共通化されておらず、下寄せだけ数字が違っていた**こと。
書き出し(`assSubtitle.ts`)は上下とも `height * 0.08` なのに、プレビューは CSS に直接
`.overlay-top { top: 8% }` / `.overlay-bottom { bottom: 10% }` と書かれていて、
**下だけ 10%** だった。既定のテロップ位置は `bottom`(`defaultTextStyle`)なので、

実測（**実機**・利用者と同じ操作で既定スタイルのテロップを足し、プレビュー枠を
`capturePage` で切り出して画素を数えた値と、同じ内容を 1280x720 で書き出して
フレームの画素を数えた値。どちらも「非黒の行」を探す同じ数え方）:

| 位置 | プレビュー(修正前) | プレビュー(修正後) | 書き出し | 判定 |
|---|---|---|---|---|
| **下寄せ（既定）** | 下から **10.59%** | 下から **8.47%** | 下から **8.06%** | **直った** |
| 上寄せ | 上から 8.05% | 上から 8.05% | 上から 9.03% | 元から一致（回帰なし） |

**CSS からは `.overlay-top` / `.overlay-bottom` / `.overlay-center` の縦位置指定を削除**して、
数字を書き戻せないようにしてある（残すと必ず戻ってくる）。

単体38件。`textMarginVPx` の境界値（0・負・NaN・±Infinity・1・480/720/1080/2160）で
理論値と一致すること、480p〜2160p の ASS の MarginV フィールドが `round(h*0.08)` に
なること（中央は 0）、画面の 8% を px に直すと書き出しの MarginV と一致すること、
スライドイン(`\move`)の着地点も同じ規則であること。
**このうち「CSS 側に縦位置の数字が残っていないこと」の3件だけが修正前に落ちる**
（実測: `top:8%` / `bottom:10%` / `top:50%` を検出して不合格）。他の項目は書き出し側が
元から 8% だったので修正前でも通ってしまう——テストが効いている証拠はこの3件。

回帰: 書き出しの実測値は 720p で修正前と**完全に同一**（上端 y=65/中央 y=347/下端 y=629）。
ドラッグで置いた自由位置（`customPosition` = 0.25, 0.75）も、画面 74.79% ・
書き出し 75.49% と 75% 前後で一致していて壊れていない。

同種を洗って**まだ残っているものを見つけたので `BACKLOG.md` の「候補」に1件残した**:
左右余白（CSS `5%` の比 ⇔ ASS `MarginL/R=40` の出力px固定。4K では 5% 対 1.04%）と
背景箱の余白（CSS `0.15em 0.4em` ⇔ ASS `\bord6`。サイズ40で横 16px 対 6px）、
そして `fontSize` そのものが出力ピクセル固定であること。後者は既定サイズ40の
長い一文が **854x480 では幅 865px となり枠(854px)に収まらず両端が切れる**のに対し、
3840x2160 では枠の 22.5% にしかならない（文字の絶対幅は4解像度とも 865px で同じ）。
`fontSize` の意味が変わって既存プロジェクトの見た目が動くため、移行方針を決めないと
入れられない＝今回の1件には大きすぎると判断した。

### 2026-08-13 書き出しパイプライン（2周目の1件目）
巡回表が一周したので2周目。この領域は fps・音声形式・PiP余白・無音しきい値を既に直してあるので、
**まだ当てていない眼鏡**（「利用者が受け取る成果物の形式を、環境や経路まかせにしていないか」
「値の変換を交渉に委ねていないか」）で見直した。

見つけたのは、**映像の画素形式だけが何も固定されていなかった**こと。音声は
`AUDIO_FORMAT`（`aformat`）で合流の手前を全部固定してあるのに、映像側は素通しだった。
`xfade` は yuv444p を好むため、**4:2:0 の素材しか無いタイムラインでも、繋ぎを
「クロスフェード」にしただけでグラフ全体が 4:4:4 に引き上げられ**、libx264 が
**High 4:4:4 Predictive** で書き出す。エラーも警告も出ず、尺もフレーム数も音量も正しいので、
毎時の検証では絶対に落ちない。

実測①（`exportProject` 直叩き / 1280x720・4:2:0素材2本 → 480p）:

| タイムライン | 修正前 profile/pix_fmt | 修正後 |
|---|---|---|
| 繋ぎなし | High / yuv420p (971,468 bps) | **同じ**（バイト単位で同一・回帰なし） |
| **クロスフェード** | **High 4:4:4 Predictive / yuv444p** (1,213,027 bps) | **High / yuv420p** (956,833 bps) |
| クロスフェード+ぼかし背景 | **High 4:4:4 Predictive / yuv444p** | **High / yuv420p** |
| クロスフェード+PiP | High / yuv420p | **同じ**（`overlay` が 4:2:0 に引き戻していた） |
| テロップのみ | High / yuv420p | **同じ**（回帰なし） |

つまり**利用者が使った機能の組み合わせ次第で、成果物の画素形式が黙って変わっていた**。
PiP を足すと 4:2:0 に戻る、という一貫性の無さがそのまま症状になっている。

実測②（**実機**・利用者と同じ操作。素材を読み込み → タイムラインに2本 →
インスペクタで繋ぎを「クロスフェード1秒」→ 720p で書き出し）:

| | 修正前 | 修正後 |
|---|---|---|
| profile / pix_fmt | **High 4:4:4 Predictive / yuv444p** | **High / yuv420p** |
| 映像の尺 / 音声の尺 | 19.000000 / 19.000000 | **同じ** |
| フレーム数 | 570 | **同じ** |
| 音量 mean / max | -24.1 / -20.7 dB | **同じ** |
| ファイルサイズ | 2,520,133 B | **1,804,115 B（-28.4%）** |
| ビットレート | 1,061,108 bps | **759,627 bps（-28.4%）** |
| 絵の一致 | — | PSNR 47.3 dB（実質同一） |

4:4:4 は元素材に無い色差情報が増えるわけではないので、**同じ絵に +28% のビットレートを
払ったうえ、ハードウェアデコーダや一般的な再生環境が扱えない profile になっていた**。

出力の直前に `format=yuv420p` を1枚挟んで固定した。`previewProxyService` は最初から
`-pix_fmt yuv420p` を付けており、**書き出しだけが素通しだった**。

単体21件（クリップ1本 / 2本 / 8本、繋ぎの長さ 0・0.01・0.5・1e9・NaN・負、
type=none、テロップのみ、PiP 0/1/3枚、全部盛り、ぼかし背景、fillCrop、音声なし素材、速度4倍）で
**最後の映像フィルタが必ず `format=yuv420p` で終わり、その出力が `-map` されている**ことを確認。
修正前のコードに同じ21件を当てると**全件 NG**になる（＝テストが効いている）。

回帰は15シナリオで確認し、**影響の無い11シナリオはバイト単位で出力が同一**、
変わったのは 4:4:4 になっていた3シナリオだけだった。

**測り方の失敗を2件記録**:
1. 単体の偽 ffmpeg を「引数を書いて即 exit 1」にしたら、fluent-ffmpeg が spawn 前に走らせる
   `-codecs` などの能力調査まで潰れ、**グラフを組み立てる前に落ちていたのに全件 NG に見えた**。
   能力調査だけ本物に流す形にして直した。
2. 修正後の結合で、before と**バイト単位で同じ数字**が出た。焦って「効いていない」と
   判断しかけたが、原因は esbuild の**バンドルを作り直していなかった**だけだった。
   数字が動かないときは、まず「今のコードを測っているか」を疑うこと。

### 2026-08-12 AI連携（応答の取り扱い・失敗時の挙動）
Gemini の応答(ゲームトレンド・投稿メタデータ・AIショート構成案)は3経路とも

### 2026-08-12 解析系（ハイライト・BPM・無音・スマートクロップ）

同じ原因だったので、音声の全5経路（本編・`anullsrc`・PiP・音声トラック・`loudnorm` の後ろ）に
`aformat=...:sample_rates=48000:channel_layouts=stereo` を掛けて塞いだ。
検算: モノラルBGM版とステレオBGM版が 0-4s / 4-6s とも -21.1dB / -24.1dB で一致（同じ扱いになった）。
回帰: ステレオBGM・本編のみ・44.1kステレオ素材は修正前後とも -24.1dB で不変。
無音（音声なし素材）-91.0dB、PiPの発音区間 1〜4s、速度2倍のBGMが0-2sで終わることも不変。
全15ケースで映像と音声のストリーム長が一致（クロスフェード時 5.000s / 150フレームも不変）。
ffmpeg のモノラル→ステレオ変換は各chが -3dB（電力は保存）である点も実測した。
同種を洗ったところ、波形画像の `aformat=channel_layouts=mono` は画像用で意図的、
`silencedetect` は解析のみ、プレビュープロキシは既に `-ac 2`、書き出しのグラフを
組む場所は `exportProject` の1箇所だけだった。
