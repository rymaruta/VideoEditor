# バグ狩り（1時間おき / 潜在バグを探して即修正する）

このファイルは**バグ狩りロール専用**です。他のロールは書き込みません。
`BACKLOG.md` に書くと、実装・補充・検証の3ロールと毎回衝突するため分けてあります。

## このロールの立ち位置

| ロール | 見るもの | 動くとき |
|---|---|---|
| 検証 | **直近のコミットが壊していないか** | 壊れているときだけ直す |
| バグ狩り（これ） | **前からずっと壊れていたもの** | 毎回1件見つけて直す |

検証ロールは「壊れていなければ何も変更せず終了」なので、**最初から間違っていたコードは永久に拾えません**。
実際、60fps素材が常に30fpsで書き出されていた不具合は、尺が合っていてエラーも出ないため、
検証を何十回通しても素通りしていました。そこを掘るのがこのロールです。

## 1回の実行でやること

**1件だけ**見つけて、**その場で直して**、**push するまで**が1セット。
見つけて報告するだけで終わらせない。直せないものを見つけたら、次項の手順で候補に残す。

### 手順

1. **担当領域を1つ選ぶ。** 下の「領域の巡回表」で**最終掃引が一番古いもの**。
   同じ領域を続けて2回選ばない。
2. **`BACKLOG.md` の「再発防止チェックリスト」を全部読む。**
   これが探すための眼鏡です。各項目を「この領域でこれに違反している箇所はないか」という
   grep の観点に翻訳して、順に当てていく。項目数が多いので、当てた項目と結果を手元に控える。
3. **怪しい箇所を見つけたら、直す前に「本当に壊れているか」を実測で確かめる。**
   ここを飛ばすと、壊れていないものを「直して」しまう。実際に何度も起きています
   （呼び出し方を間違えて2件を誤検知、クリップ終端での分割を不具合と誤認、など）。
   実測とは、アプリを起動して同じ操作をする・ffprobe で数字を読む・DOM の値を読む、のいずれか。
4. **直す。** 進め方は `BACKLOG.md` の「実装の進め方」（設計 → 実装 → 単体 → 結合）に従う。
5. **同じ種類が他にないか grep で洗う。** 1箇所だけ直すと、残りが黙って壊れたままになる。
   （実例: 書き出しの `fps=30` を直したら、画面側にも `1 / 30` が3箇所あった）
6. **チェックリストに1行足す**（`BACKLOG.md` の「再発防止チェックリスト」）。
   既存項目と同じことを言い換えただけなら足さない。既存項目で拾えたなら、そう報告する。
7. このファイルの巡回表の日付と「見つけたもの」を更新して、コード変更と一緒にコミットする。

### 何も見つからなかったとき

**でっち上げない。** 「異常なし」で終えてよい。ただし巡回表は更新して、
**どのチェックリスト項目をどう当てて、なぜシロと判断したか**を1〜2行残すこと。
これが残っていないと、次回また同じ当て方をして同じ時間を溶かします。

### 直すのが大きすぎたとき

無理に大改造しない。`BACKLOG.md` の「候補」欄に
「◯◯の修正（バグ狩りで発見。症状は△△、原因の見当は□□）」として1件残し、
このファイルにも記録して終える。**症状と再現手順は必ず数字付きで書く。**

## 優先順位

同じ日に2つ怪しいものが見つかったら、**編集作業が止まる/出力が壊れるほう**を先に直す。

1. 出力が壊れる（尺ズレ・音ズレ・映像の欠落・書き出し失敗）
2. 編集内容が失われる（Undoで戻らない・保存で消える・参照が切れる）
3. 画面と出力が食い違う（プレビューで決めた見た目が出力で別物）
4. 操作が効かない・効きすぎる
5. 表示崩れ・文言

### 2026-08-12 プロジェクト入出力（保存・読込・自動保存・再リンク）
`saveProjectFile` が保存先へ直接 `writeFileSync` していた。`O_TRUNC` なので
**書き込みを始めた瞬間に元のファイルが空になる**。そこでアプリが落ちる・電源が切れる・
ディスクが一杯になると、**上書き前の内容はどこにも残らない**。書き終われば正常なので、
検証を何度通しても出ない。自動保存(60秒ごと)も同じ関数を通るため、
**落ちたときの復元手段が、落ちたせいで壊れる**。

実測（実機Electron / 自動保存中にアプリを強制終了。修正前後で同じスクリプト・同じ契機判定）:

| | 修正前 | 修正後 |
|---|---|---|
| 直前に自動保存できた内容 | 741バイト(clips=5) | 741バイト(clips=5) |
| 強制終了の契機 | 保存先が 741 → 6,291,456 バイトへ書き換わり始めた | 一時ファイルが現れた |
| 強制終了後の `autosave.veproj` | **10,485,760バイトの断片** | **741バイト(元のまま)** |
| 読み込み | **失敗**「ファイルが壊れているか…」 | **成功(clips=5)** |

単体22件すべてOK。1MBのtmpfsを作って**本物のディスクフル**も測った:
修正前は 389バイト → 1,048,576バイトの断片になって読めなくなり、修正後は ENOSPC が
投げられたうえで元のファイルが**バイト単位で無傷**、一時ファイルも残らなかった。
他に新規ファイルへの保存・空プロジェクト・上書き・保存先ディレクトリ無し(ENOENT)・
20回連続保存・5万クリップ・壊れた内容の読み込み(途中で切れたJSON/null/配列/数値)を確認。
回帰: 保存されるファイルは修正前後で**バイト単位で完全一致**(1448バイト)。

**測り方の失敗を2件記録**: (1)読み取り専用ディレクトリでの失敗テストを書いたが、
root で動いているため chmod が効かず素通りした→本物のディスクフル(tmpfs)に差し替えた。
(2)実機の kill テストで、修正前だけ「保存先が縮んだ瞬間」を待つ判定にしていたため
一瞬すぎて捕まらず「症状が出ない」ように見えた→両者とも「サイズが変わった瞬間」に
揃えて測り直した。**条件を揃えないと修正前が無傷に見える。**

同種を洗ったところ、main 側で `writeFileSync` しているのは他に
ウィンドウ位置(`saveWindowState`。壊れても既定値へ戻るだけで best-effort と明記済み)、
書き出し時のASS字幕(`mkdtempSync` の一時ディレクトリ内・使い捨て)、
VOICEVOXの合成音声(`randomUUID()` で常に新規ファイル名なので既存を壊さない)の3つで、
**既存の利用者データを上書きするのは `saveProjectFile` だけ**だった。
なお強制終了した場合は一時ファイル(`*.saving-*.tmp`)が保存先の隣に残る。
拡張子が `.veproj` ではないのでファイル選択には出ないが、掃除はしていない。

### 2026-08-12 タイムラインUI（ドラッグ・トリム・スナップ・選択）
音声クリップ/PiPクリップのトリム(`mediaTrimDrag`)だけが、マウスの移動量
(`px ÷ pixelsPerSecond` = **タイムライン秒**)を `inPoint`/`outPoint`(**素材秒**)へ
そのまま足しており、**速度で換算していなかった**。本編クリップのトリム(`trimDrag`)には
最初から `* prev.speed` がある。等倍では正しく動くので気付けない。
分離音声は本編クリップの速度をミラーする(2倍速のクリップから分離すると `speed=2`)ため、
**利用者が普通に踏む**経路。

実測（実機Electron / xvfb / 40px per second のタイムライン / 素材10秒・in=2 out=6 start=2）:

| 操作 | 修正前 | 修正後 | 期待 |
|---|---|---|---|
| speed=1 右へ+40px | 幅 +40px | 幅 +40px | +40px |
| speed=1 左へ+40px | 左端+40px / 終端0px | 同左 | 終端は動かない |
| **speed=2 右へ+40px** | **幅 +20px**(out 6→7) | **幅 +40px**(out 6→8) | +40px |
| **speed=2 左へ+40px** | 終端が **+20px 動く** | **終端 0px** | 動かない |

境界値も実機で確認: 右へ+400px → out=10(素材の終端でクランプ)、右へ-400px → out=2.2
(最小尺0.2)、左へ-400px → in=0/start=1(素材先頭)、左へ+400px → in=5.8/start=3.9
(最小尺。終端は 3.9+0.1=4.0 で元と同じ)、speed=0.5 右へ+40px → out=6.5(タイムライン+1秒)。
回帰: PiP(速度を持たない型)は右+40px→out=7、左+40px→in=3/start=3 で従来どおり。

**測り方の失敗を1件記録**: 最初の測定は out が素材の終端(10秒)に張り付いた状態で
ドラッグしたため「幅の増分0px」となり、症状が出ていないように見えた。
伸ばす余地を作ってから測り直して初めて 20px/40px の差が出た。
「何も起きなかった」を正常と読まないこと。

同種を洗った結果、タイムライン秒↔素材秒の換算は他に
`trimDrag`(本編/`* prev.speed` あり)・`rollTrim`(ストア側で speed 込みでクランプ)・
レーザー分割(`splitClipAtTime` がストア側で換算)・`splitAudioClipAtTime`
(`* (c.speed || 1)` あり)・音声クリップの表示幅(`audioClipDuration` で `/speed`)があり、
**すべて処理済み**。移動系のドラッグ(`audioDrag`/`videoOverlayDrag`/`overlayDrag`)は
`startTime` しか触らないので換算不要。漏れていたのは `mediaTrimDrag` の1箇所だけだった。

### 2026-08-12 ストア（履歴・ID再生成・リンク追従・一括操作）
ソースビューアの「インサート」「上書き」(`insertClipAtTime` / `overwriteClipAtTime`)だけが
`clips` の並びしか差し替えておらず、**分離音声と追従テロップの参照を作り直していなかった**。
`buildInsertedClips` は挿入点の下のクリップを2つに割って**後半に新しいIDを振り**、
上書きでは**クリップを丸ごと落とす**のに、返り値が `Clip[]` だけだったため
呼び出し側から何が起きたか見えなかった。型は通り、尺も並びも合うので気付けない。

実測（本物のストアで操作 → 本物の書き出し → ffprobe/volumedetect）:
- インサート（分離音声のある10秒クリップの5秒地点に無音素材2秒）
  修正前 後半(7〜12秒)が **-91.0dB の無音** / 修正後 **-24.1dB**（前半と同じ）。
  0〜5秒(-24.1dB)と挿入区間 5〜7秒(-91.0dB)は不変、尺も 12.000秒/360フレームで不変。
- 上書き（分離音声のある5秒クリップを無音素材5秒で丸ごと潰す）
  修正前 消したクリップの音声が 5〜10秒で **-24.1dB のまま鳴り続ける** /
  修正後 **-91.0dB**。前半 0〜5秒は不変。
- 追従テロップ（10秒クリップの7秒地点に付けたテロップ、5秒地点に2秒インサート）
  修正前 `7.00〜9.00` のまま（映像は2秒ずれるのでテロップだけ取り残される）/
  修正後 `9.00〜11.00`（追従先も後半クリップへ張り直された）。

直し方は新しい規則を作らず、`applyClipReplacement` から参照の作り直しだけを
`relinkForReplacedClip` に切り出して、インサート/上書きからも同じものを通す形にした。
消えたぶんは `removeClips` と同じ `removeLinkedAudioFor` を通す。

単体24件（境界値と回帰）すべてOK: 分割が起きない位置(先頭0/末尾10/範囲外99)では
参照を触らない、長さ0・逆順・存在しない素材はプロジェクトが変わらない(参照同一性)、
`Infinity`・負値、素材尺を超える範囲のクランプ、上書きで後続を食い尽くす場合
(音声が `9:9-10` に縮む)、リンク無しのプロジェクトでは何も足されない、
1操作=Undo1件で音声も一緒に戻る、部分上書き(IDが残る)は従来どおり。

同種を洗った結果、本編クリップのIDを変える/消す経路は他に
`splitClipAtTime` / `replaceClipRange(s)` / `applyTemplate`のジャンプカット /
`removeClip(s)` / `removeAsset` / `duplicateClips` / `pasteClip` があり、**すべて処理済み**
（`applyTemplate` はテロップを丸ごと入れ替える仕様なので張り直し不要）。
漏れていたのはインサート/上書きの2つだけだった。

副産物: 位置に `NaN` を渡すと `syncLinkedAudioClips` の `NaN === NaN` が常に false になり、
購読側の再同期が止まらず `Maximum call stack size exceeded` になる。**修正前のコードでも
同じ**（今回の変更とは無関係）なので直さず、`BACKLOG.md` の「候補」に数字付きで残した。

### 2026-08-12 IPC境界（main↔renderer・エラー処理・並行実行）
main→renderer の通知は `event.sender.send` の2箇所だけで、**プレビュープロキシ側にだけ
`isDestroyed()` ガードがあり、書き出しの進捗は無防備**だった。`send` は破棄済みの
webContents に対して `TypeError: Object has been destroyed` を投げる（Electron 実機で確認。
`win.close()` の直後は `isDestroyed()` がまだ false で、少し待つと true になる）。
投げる場所が ffmpeg のイベントハンドラの中なので `ipcMain.handle` の外、つまり
**どこにも捕まらず main プロセスごと落ちる**。
実測（1080p・40秒・実機Electron / 書き出し開始1.0秒後にウィンドウを閉じる）:
修正前 `uncaughtException: Object has been destroyed` でアプリ異常終了、書き出し先に
**48バイト・moov atom not found の再生できないファイル**が残る。
修正後は書き出しが最後まで走り、**1200フレーム / 映像40.000秒・音声40.000秒**で完走。
対照（修正前のままウィンドウを閉じない）は 14.0秒・進捗21回で完走したので、
原因が「閉じたこと」であることも確かめた。
単体: 生きている相手には境界値（0 / 100 / -1 / 33.333333 / 空文字 / null / undefined）が
そのまま届き例外0件、破棄済みの相手には1000回連続で送っても例外0件。
ガード無しの式は1回で TypeError になることも並べて確認（テストが空振りしていないことの裏取り）。
回帰: ウィンドウが生きている場合の進捗送信は修正前後とも21回、出力も同一。
Linux/Windows は最後のウィンドウを閉じるとアプリ自体が終了するため、
利用者が踏むのは**ウィンドウを閉じてもアプリが残る macOS**（`electron-builder.yml` の
ビルド対象に含まれる）。実測はその挙動に合わせて `window-all-closed` を握って行った。
同種を洗ったところ main→renderer の送信は他に無く、進捗コールバックを渡している
IPCハンドラも書き出しとプレビュープロキシの2つだけだったので、両方を共通の
`notifySender` に通す形にした。

### 2026-08-12 音声（ミックス・ダッキング・正規化・分離音声）
書き出しの音声の枝がどこも形式を固定しておらず、libavfilter の形式交渉で
**グラフ全体が一番安い形式へ引きずられていた**。`aresample=async=1` が本編の枝にあるため、
モノラル素材が1本混ざると「変換の少ない側」としてモノラルが選ばれる。
実測（48kHzステレオの本編＋モノラルBGM 1本）: 修正前 **44.1kHz・1ch**、
左だけに入れた音（素材 L -21.1dB / R -91.0dB）が中央に潰れて 1ch -20.4dB。
修正後は **48kHz・2ch**、L -19.8dB / R -25.9dB で定位が残る。
音声を分離したクリップがあると `anullsrc` の決め打ち 44100 に道連れで落ちる件、
既定ONの音量正規化を通すと `loudnorm` の内部 192kHz が漏れて**出力が96kHz**になる件も
同じ原因だったので、音声の全5経路（本編・`anullsrc`・PiP・音声トラック・`loudnorm` の後ろ）に
`aformat=...:sample_rates=48000:channel_layouts=stereo` を掛けて塞いだ。
検算: モノラルBGM版とステレオBGM版が 0-4s / 4-6s とも -21.1dB / -24.1dB で一致（同じ扱いになった）。
回帰: ステレオBGM・本編のみ・44.1kステレオ素材は修正前後とも -24.1dB で不変。
無音（音声なし素材）-91.0dB、PiPの発音区間 1〜4s、速度2倍のBGMが0-2sで終わることも不変。
全15ケースで映像と音声のストリーム長が一致（クロスフェード時 5.000s / 150フレームも不変）。
ffmpeg のモノラル→ステレオ変換は各chが -3dB（電力は保存）である点も実測した。
同種を洗ったところ、波形画像の `aformat=channel_layouts=mono` は画像用で意図的、
`silencedetect` は解析のみ、プレビュープロキシは既に `-ac 2`、書き出しのグラフを
組む場所は `exportProject` の1箇所だけだった。

### 2026-08-12 書き出しパイプライン
`fps=30` / `settb=1/30` の決め打ちを発見。60fps素材が 30fps・330フレームで出力されていた
（尺は正しいのでエラーも警告も出ない）。素材から決める `targetFrameRate` を
